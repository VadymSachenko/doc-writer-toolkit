# ticket-state

The ticket ledger of a docs pipeline, its daily run and its watcher. `ticket-state.mjs` keeps one ledger per ticket and derives, from the tracker, the forge, git and the files, each ticket's state, its next step and the gate that is open; it records a stage only when the world supports it. `runner.mjs` runs the day: finish first, triage the intake in the morning, start ready groups within the limits, one `claude -p` session per step that needs a model. `watcher.mjs` is started by launchd every few minutes: it reads what changed on the boards and the PRs, and has the runner finish the tickets that changed; once a day it starts the morning run; inside the start hours it has the runner start the next ticket when a slot frees; and it starts the host's jobs. Every minute its forge check picks up the comments on the pipeline's PRs, and hands them to a run in a process of its own, so a long run never holds it up. `launchd.mjs` installs and uninstalls its LaunchAgent. Node, no dependencies. No AI in any of them: they decide, and the role sessions do the work.

```
node ${CLAUDE_PLUGIN_ROOT}/scripts/ticket-state/ticket-state.mjs <command> [<key>] [options]
node ${CLAUDE_PLUGIN_ROOT}/scripts/ticket-state/runner.mjs [--dry-run] [--morning] [--manual --ticket <key>] [options]
node ${CLAUDE_PLUGIN_ROOT}/scripts/ticket-state/watcher.mjs [--full|--forge|--hand-on <id> --ticket <key>|--learn] [--dry-run] [--quiet] [options]
node ${CLAUDE_PLUGIN_ROOT}/scripts/ticket-state/launchd.mjs print|install|uninstall|status [--noop] [options]
```

Run them from the host repo (or pass `--root`). Needs Node 18.3+, the `tracker` and `forge` scripts next to this one (their modules are used as libraries, so every tracker and forge rule holds here too), git, and for a live run the `claude` CLI. Tests: `npm test` in this folder (offline: in-memory tracker and forge adapters under the real modules, throwaway git repos, and a stand-in for `claude`).

The contract (the statuses and states, the rule, the ledger's fields, when a record is accepted, the locks, the limits, the report) is `${CLAUDE_PLUGIN_ROOT}/context/ticket-flow.md`. This file is how to run the scripts.

## Settings

The same settings files as the `tracker` and `forge` scripts, found the same way: `--settings <file>`, else the `Ticket flow settings:` field of the host's `CLAUDE.md` (registered in `${CLAUDE_PLUGIN_ROOT}/context/project-paths.md`, "Ticket flow settings"), else `.claude/ticket-flow.json`. The owner's `<name>.local.json` next to it is merged over it at any depth (a local key wins; a list is replaced). `config` prints the merged result.

The shared file (committed in the host) holds `state`, `workFolder`, `commentHeader`, `tracker`, `forge`, `targets`, `appRepos`, `relatedRepos`, `companyRepos`, `ticketCommits`, `docRepos`, `docEvidence`, `hostRules`, `hostJobs`, `styleCheck`, `learning`, `build`, `checks` and each role's tool rules; the local file holds `mode`, `limits`, `schedule`, `roles` (no tool rules), `modelLadder`, `video` and `cleanup`.

**Where a session's rules come from.** A session must not be able to widen the next one's rules by writing a settings file, so `ticket-state` reads the shared file as the host's repo has it at HEAD: an uncommitted edit counts once it is committed. A file not tracked at HEAD (no repo, outside the repo, never committed) still gives the flow its settings, but no role's tool rules. A hub PR merged on the forge reaches HEAD without a person's pull: the watcher's full check fast-forwards the hub first ("The hub after a merge" in "The watcher"). A key the local file has no business setting (`workFolder`, `state`, `targets`, `hostJobs`, `hostRules`, `tracker`, `forge`, `build`, `roles.<role>.allowedTools`, `disallowedTools`) is ignored. What was ignored is named in `settingsNotes` (`config`) and in a run's `notes`. The `tracker` and `forge` scripts read the files as they stand, with no such limit: they hold no session's rules. In a round, an answer in `answered` and a place it settles may carry `foundIn` (`{ "kind": "code" | "docs" | "ticket" | "live" | "decision" | "owner", "ref" }`, exit 2 on another kind or a missing `ref`): where the answer could have been found (its own key: a place's `source`, where its claim came from, echoed in a round is read as before and is no miss); any kind but `owner` is a line of the misses log. A person's forward move (`follow` to In translation or done) clears them. In a review round, `review` (one `style` commit) takes the summary's place, its items checked as at `answerComments`. |

The runner's own step: `checked` (the hand commits it read) goes into `prs[].idChecked`, `commits` (its commit, if it made one) into `prs[].idCommits` and `pipelineCommits`, `comments` (its line comments: `kind`, `page`, `ua`, `line`, `old`, `new`, `commentId`) into `prs[].idComments`, a `kept` comment named in `renamed` is marked renamed, and the owner's replies it took (`handled`) go into `reviewComments`. `blocked` (`[{ sha, pages }]`, the hand commits with a page left `blocked`) goes into `prs[].idBlocked` instead of `idChecked`; `clear` (the pages checked with nothing blocked) moves each entry whose pages it all names into `idChecked`, and a `readyForMerge` or `resync` record clears the list. A role session can't record `idSync` or `untranslated`: the CLI refuses it (`DOC_TOOLKIT_ROLE_SESSION`), and so does the role hook, in any form of `--stage`. |

The runner also records it `running` with the merge commit (`commits`) just before the push. Nothing from the world: the runner pushed a moment ago and the forge may lag. With `forge.translatedLabel`, each PR's `merged.translated`: whether it carried the label when it was merged. |

A record that stands prints `{ file, key, stage, status, pr, seq, lockRenewed }`, plus `warnings`, a list of lines, when it stands with something the session should still fix. Cases: `triage` when the owner could not be added; `pr` with no `expertReview` for a PR, with the expert label not added, or with a review request already on a PR (every PR opens with no reviewer); `pr` with a place whose `source` is `code` and whose `refs` lack one of repo, path, lines and commit; and any record whose `edits` reuse a number another list of the PR has, or skip one (the item is kept as posted: a reply naming it is asked back). The place is kept, marked `noRef` (its comment is already posted, so the record isn't refused), the session is told by the warning, and `status` lists the PR in `mismatch` with the place ids.

Bad usage is exit 2: an unknown stage, a PR stage without `--pr`, a failed record without `--note`, a result of the wrong shape (an edit item without `n`, `page` and the exact `before` and `after` among them), a work file outside the host repo and the state root.

`running` and `failed` need nothing from the world. Before a start's session the runner records `start` `running`, with `--started-by` and the group (`result.group`, for any status of `start`), so the group's lock covers the ticket at once. For a ready card with no ledger, that record (with `--card`) makes the ledger, with the card's list as `left` and the triage `status` read for it (`result.triage`).

Every record may carry `"files": [{ "path", "kind" }]` in its result: work files outside git that the stage created or downloaded, `kind` one of `video`, `videoPart`, `audio`, `transcript`, `frames`, `attachment`, `runDir`, `clone`, `other`. The `videoGate`, `videoTry` and `videoImport` records add the videos, parts and transcripts they name. A record also renews its group's lock lease.

Every record may carry `"sideFindings"` in its result: the problems outside the ticket the session came across, and its notes for the owner ("Findings outside the ticket"). Each is `{ "kind", "title", "text", "repo"?, "page"?, "where"?, "refs"?, "card"? }`: `kind` one of `page` (another page, or a block of a changed page the ticket's change leaves alone: `repo` and `page`, the path from the repo's root, required), `ui` (UI the ticket doesn't cover) and `appBug` (`where` required for both: the screen, the menu, the endpoint), or `note` (`text` only; no `card`); `title` is one line, required but for a note; `card` the link of an open card that holds it already, when the session knows one. A malformed one is exit 2, before anything is read or written, and so is a card's `title`, `text`, `where`, `page` or `refs` that names the toolkit (its manifest's name or its folder) or the model (`claude`, `.claude/`, `CLAUDE.md`): a card is a team text. The ledger keeps each in `sideFindings`, with its id (`f<n>`), its fingerprint (`fp`), the stage, the PR (the record's `--pr`, else the ticket's only PR) and when; one with a fingerprint the ticket already holds is kept once. Nothing else of the record changes: its questions, places and gates read as before.

## The id-only change

The approval of a PR (a person's move of the card to In translation) and every chain stage keep the head they saw. A UA page changed after that head makes the stage stale, and the approval is reported as one that saw another text, unless the change is id-only:

A UA change is id-only when its only differences from the approved version are (1) `{/* #id */}` comments added to headings that had none, and (2) link fragments rewritten from such a heading's old fragment to its new id. Anything else makes it a real change: a changed or removed id, a changed heading text, or any other edit.

`isIdOnlyChange` in `../doc-align/lib/idonly.mjs` is that predicate, the one implementation the scripts share (`section-state` uses it too), so the two scripts must stay in the same plugin. A heading's old fragment is the slug Docusaurus made of its text. A link to another page counts when its path (a relative `.md`/`.mdx` path, or a site-root route or file path) resolves to a page of the same change whose heading got that id; one that doesn't resolve is a real change. Code, fenced or inline, is never a link: a difference there is a real change.

**The runner's id commits** (`prs[].idCommits`, the `idSync` step with the translated label) change heading ids and the links to them only, but a changed id is a real change by the predicate, which stays as it is. So wherever the rule compares two heads of a PR (ready for merge, the approval, the chain stages, the re-sync, the translated label), a range that holds such a commit is read in pieces that leave it out: `from..c^` and `c..to`, each as above. With none in the range, nothing differs.

## Cleanup after the merge

When every PR of a ticket is merged, the close step first removes the ticket's worktrees (one per PR branch, see "The ticket worktree") with `git worktree remove`, never `--force`, then prunes the clone's list (the linked `node_modules` and `.env` are ignored files, so git removes the links; the clone's own stay). What goes with the worktree: its tracked files at a pushed head, and the ignored files that aren't work files (the links, `build/`, `.docusaurus/`, a pack's output, a staging folder). What keeps it: a commit that `git rev-list HEAD --not --remotes` lists (unless the worktree's head is one the forge had, or behind one: the heads a record checked on the forge, `lastSeenHead` and `readyForMerge[].head`, and the PR's head as the close step reads it; never `pipelineCommits`, which is what a session reported, pushed or not), a change to a tracked file, an untracked file git doesn't ignore (a page a session wrote and never added), or an ignored work file: anything under a `.sources/` folder, or a file `cleanup.keep` matches (its globs read from the worktree's top). A removed worktree's files are gone, not in the Trash, which is why the work files keep it. So is one git refuses to remove (a locked one: `git worktree unlock` first). A recorded file inside a worktree is reported with it: kept with it, or, when the worktree went, in `deletedWithWorktree` (an ignored file outside `.sources/` and the keep list, such as a pack's output: git deleted it, so it is not in the Trash, and the report says so). The close record (`cleanup.worktrees`, `kept` and `todo`) and the report name it, with what to do: push it, or copy what you need, then remove it (see "A stuck worktree"). Then it moves the work files the ledger recorded into the Trash (`cleanup.mode: delete` removes them), and the close record keeps the list, the worktrees and the space freed for the report. A recorded folder that is a worktree, or holds one, goes with git the same way; one that is a repository of its own (a `.git` folder) is kept whole and reported. A `.git` link or folder is never moved on its own. It never removes:

- a path git tracks, in its own repo;
- a path the ledger didn't record;
- a path outside the host repo and the state root (a link that leads outside counts as outside);
- a path `cleanup.keep` names;
- anything, while a PR of the ticket is open or was closed unmerged: then nothing is removed, and the report says so. A PR closed as won't merge (`forge.wontMergeLabel`) is out of the ticket and keeps nothing: with every other PR merged, the files go. Its branch on the forge is never touched.

A recorded folder goes whole, or file by file when it holds a tracked or kept file. A name taken in the Trash gets a number (`call 2.mp4`); across volumes the move is a copy, then a removal. The dry run lists what each close would remove and removes nothing.

## The daily run

1. `mode off`: nothing. Stale locks are moved aside and their running stages recorded failed.
2. **Finishing**, every group with a next step, in this order: close the merged, ready for merge and the re-sync, the chain and moves to final review and In translation, review comments and moves, answers in and gates passed, writing. Within a kind, higher priority first, then the older card. Up to `limits.parallel` groups at once (less the runs going in other processes, one at the least). A step is planned from the run's first status and may wait in the pool behind another group's chain: once its group's lock is taken, the ticket's status is read again, and the step runs only if it is still the ticket's next step (same stage, same PR); otherwise it is skipped (`no longer the next step` in the run log), as another run (one the forge check started, say) took it meanwhile.
3. **Morning** (`--morning`), and the watcher's start pass: one triage session for the due intake cards.
4. **Starts**: while `startable` has a group and the guard allows, in `limits.startOrder` (the highest priority first, the oldest within a level; or the easiest first). Before each start's session the runner records the start (`running`, with its origin and its group). A group whose start didn't get its card into work holds no slot in the run's later calculations, so the run goes on to the next group.
5. **Morning** (`--morning`): the Markdown ledgers from before the JSON ones whose ticket closed since the import are removed, each after the import's check (see "The import"). No model; a dry run or `observe` lists them (`legacyMarkdown`). The report lists what went under "Work files removed after the merge", and under "Failures" a closed ticket's Markdown that failed the check (each morning until it is imported again) and a file whose ticket couldn't be looked up (the tracker or the forge failing, a ledger that doesn't read). Such a file stays; the others go on.

**Handed on** (the watcher's runs, `dispatch`, lib/dispatch.mjs): the full check's run, its morning run and its start pass decide here as above (one `/usage` reading, the finishing order, the guard, the triage, `startable` and the start order), but advance no group: each group with a next step, and each start `startable` gives, goes to a run of its own (`watcher.mjs --hand-on <id>`, detached), and the run ends once all are handed on. A model step the guard holds is not handed on. The starts come from one calculation, not from a status read again after each start: `startable` already gives each later group the slots, the allowance and the relations of the earlier ones, and a start no process has recorded yet would be invisible to a new read. A start that can't be handed on (the runs at `limits.parallel`) holds back the later ones. The run handed a group starts from the check's reading (its step file, if under 10 minutes old; every reading after a session is its own); a finishing step the morning run handed on keeps its one more try after a failure; a start is a scheduled run that starts that one group, if its own status still lets it (else it notes why and starts nothing), and runs its steps. Once a run handed on holds its group's lock, it counts the runs again (the groups whose lock is older than its own; a triage's locks, one per intake card, are not runs and don't count): two checks that handed on at the same moment can pass `limits.parallel` by one, so the later one frees its lock and ends as waiting, and the next check hands it on again. A start that ended with no start recorded, whatever its result, makes the next start pass look again (`again`, after 30 minutes, unless a change comes first); a finishing run that came back stopped (`mode off`) or waiting goes back to `pending`. A run that carried the morning run's one more try for a failed step or a failed start (`retried` on its record) and came back without using it (stopped, waiting, failed, no result; a start: none recorded) leaves that try owed for the rest of the day (`owed`): the next check hands the step on with it, and the next start pass gives it to that start alone. Only the triage still runs in the check's process (and, apart from the runner, a due host job).

Each group is locked (kind `schedule`, or `manual` for a manual run) while it advances, step by step as far as it goes, up to `limits.stepsPerTicket`. A step with no role (`move`, `follow`, `close`, `readyForMerge`, `planApproval`, `videoTry`, `videoBlock`, `untranslated`, `idSync`, see "The translated label", `videoExtract`, see "The video gate", and the chain's `build`, see "The site build") runs in the script. A step with a role is one session:

```
claude -p <brief> --agents <state>/roles/agents.json --agent ticket-<role> --model <m> --effort <e> --max-turns <n>
  [--max-budget-usd <usd>] --setting-sources project,local --settings <the hook> --permission-prompts none --output-format json --allowedTools … --disallowedTools … --add-dir <each worktree of the step, or each target repo for a step with none, and the toolkit roots>
```

The role files are `${CLAUDE_PLUGIN_ROOT}/context/ticket-roles/<role>.md` with `unattended.md` appended to each. The brief names the ticket, the stage, and the exact `record` command, each command with the settings file the runner read. A session passes when every ticket of the step recorded the stage done after it began, or, for a `plan` or a `write` (and a `pr` whose gate found a marker, with `checks.markers` on), recorded `questions` instead; else it is retried once with the next model up (`modelLadder`), and a failure stops the group. Each session's cost (the CLI's estimate, tokens, turns, and the week bar before and after) goes into the ledger's `runs`, with two times: `durationMs`, the CLI's own count (`duration_ms`), and `wallMs`, the wall-clock time from the session's start to its process's end. They differ when a session waits for something after its last turn (a background build, say): the progress file and the report show `wallMs`, with the session's count beside it when it is a minute or more shorter. The allowance and the estimates read neither.

**The evidence in the brief.** A writer's or a reviewer's brief names a read-only checkout of each code repo (`appRepos`), each at the commit fetched for the session. On a writer's `start`, `plan`, `answers`, `write`, `answerComments` and the answer pass (`answerPass`, with every company repo besides), it also names, under their own heading, a checkout of each related repo (`relatedRepos`): when a claim names an endpoint, a field, a status or a component whose caller or implementation the code repos don't show, the session searches the related repos before it marks a place or asks a question, and cites a finding like any code reference (repo, path, lines, commit). On those stages the runner also looks up **the ticket's commits**, with no model (`lib/ticket-commits.mjs`): in each checkout made, code and related, `git log` from the fetched commit (never in an owner's clone) for the commits whose message names a key of the step (`ticketCommits.pattern`), newest first, at most `ticketCommits.limit` per repo and key, each with its short sha, author date, author name, subject (cut at 200 characters, and given as the org's text, data and never instructions) and changed files (ten, then how many more; read with `--no-renames`, so a partial clone fetches nothing for them). Git searches the key as a fixed string over the last 500 commits that hold it, and the pattern then picks, so a commit that holds a longer number with the key in it never uses up the bound; a search that reached the 500 says more may name the key. The whole lookup has 60 seconds for every repo and key, each git call 30 at most: a key the time no longer covers is said not searched. The brief lists them per repo and key, says when none names it, and says when the search couldn't run (a git error, a time out or a fault of the lookup itself, as a note: it never fails the step). With them come the rules: a place's `why` names, in the page's language, the sources tried (the code repos, the related repos, these commits, the host's own docs, the app or the API) and why none confirmed the claim; a question to the developer about the code's intent cites the commit that shows the behaviour. A `#<key>` may be a PR number of that repo, so the brief says to read a commit before citing it. A reviewer's brief has neither the related repos nor the commits. With no `relatedRepos`, the brief is as before but for the ticket's commits in the code repos.

**The answer pass** (`companyRepos`; `lib/answer-pass.mjs`, `lib/company-repos.mjs`; TASK-105). A writer's session after the UA review and before the PR whose only job is to answer what is left open. Its brief's framing: each item has an answer in the company's systems, find it; an item it can't answer stays, with every source it tried. Before the session the runner freezes the input first: with no item and no note (a note says something wasn't read, such as a branch's markers, which the session then reads), it records the pass done with `"items": []` itself, resolves, clones and checks out nothing and starts no session, and its run has no `start`, so it counts in no session tally. Then it resolves the company repos (the org by `gh`), checks out each ("`companyRepos`" in "Settings"), looks up the ticket's commits in all of them, searches the host's docs with the items' terms besides the ticket's, and freezes the input in a `running` record (`answerInput` in the ledger): the write's `open` questions (`q<n>`) and places (`p<n>`), the `NEEDS CONFIRMATION` and `ToDo` markers each branch added to its UA pages (`m<n>`, read in the worktree), and the UA review's `open` findings (`f<n>`). A stage's own question (a fit stop, a refused video, a conflict, a person's comment that needs the owner) is never an item. A session that fails (or ends with no record) gives up what the pass held (`record`'s `answerPass` row): nothing waits on a pass that doesn't come. In a group, each ticket numbers its items from 1, so the brief names each item's ticket. The record ("`record`: what each stage checks") takes each item answered, confirmed or kept; the `pr` brief then lists what the pass settled (posted nowhere: the answers are in the pages), what it kept (carried on with what it tried), and its page edits, which go on the description's list of edits after the UA review's fixes, numbered on, under the heading `forge.reviewRounds.labels.answerEdits` (`Edits from the answers` by default), so the owner undoes each by number. The pass never changes a setting several accounts share unless the host's rules allow it by name, and never writes to a company repo. The session is the writer role's (its rules, its Playwright and browser lock); only the brief and the checkouts differ. **In a review round** (with `forge.reviewRounds`): the questions the round asks are held from the description, and the check label waits with them; the PR's next step is `answerPass --pr` on them (`d<n>`), before any new comment is answered. Its answered questions are shown resolved, the kept ones open. Without review rounds a round's questions are posted in its summary, so no pass runs on them. **On held questions**: a plan or a write that would ask the owner a question about the product, the code or the text holds it instead (`questions` with `hold`), and the pass runs on those (`c<n>`) before the stage goes on. What it answers goes into the brief of the stage that held them when it runs again; what it keeps it asks on the card in one comment, the card to Blocked, and its record gives that comment as `asked` (checked like a `questions` record's), so the ticket waits for the owner as before.

**The misses log** (`lib/misses.mjs`). An item the pipeline left that is settled later from a source already in reach is one line in `<state>/misses.jsonl`: the ticket, the PR, the item, the source (`code`, `docs`, `ticket`, `live`, `decision`), who settled it (`answerPass`, `owner`, `expert`) and the stage that missed it. The answer pass writes one per item it answered or confirmed; a round writes one per answer with a `foundIn` (the owner's word alone, kind `owner`, is none); an item a rule settled (the role's or the host's) is none, since the rule is written already. A line is written once (by its key), after the ledger, so a refused or repeated record logs nothing twice. Once in seven days (as the roles proposal), with `companyRepos` set or a misses log there, the run writes `<state>/answers-week.json`, shown in that day's reports under "Answers and misses this week": per ticket the items the writer left, those the pass answered or confirmed and those that reached the owner, and the week's misses by the kind of their source. A kind seen in two tickets (two items of one ticket are one gap) is proposed once as one rule line for the writer role or the hub's rules (`<state>/misses-proposed.json` keeps the kinds proposed); the owner says yes or no, and the pipeline writes no rule itself. It stands in for the weekly measures report until that is built.

**The host's own docs in the brief.** On the same writer's stages, the runner also searches the host's own docs, with no model (`lib/doc-evidence.mjs`), on the step whether or not it has code repos. **The terms** are taken as written from each ticket's own work folder (`ticket.md` first, then the other Markdown files `docEvidence.ticketFiles` names), its card's name and description (as the run's check of the board read them, with no tracker call of its own), and the claims of its places and the text of its questions in the ledger: endpoint paths (cut before their first parameter, so `/api/v1/t/{otp}` is `/api/v1/t/`), code spans, CamelCase and dotted names, and bold spans. A fenced block gives none: the session's notes' blocks (code, raw responses) are left out whole; in the ticket's own text (`ticket.md`, the card) a block with a language after its fence is left out, and one with none (a spec pasted as a block) is read. A bold span that is a field's label gives none: a colon in it or right after it (`**Card:**`, `**Опис**:`), a dash after it, or the whole line (`**Приклад**`). A link's path, a plain lowercase word (`amount`), a generic word (a template's labels among them, English and Ukrainian), a file path from the code, a term under four characters and any term with the ticket key in it (a key under four characters only as a whole word) give none; the ones the texts name most often come first, at most 20 (the rest are counted). **Where:** the published pages, UA and EN Markdown, of the hub and each `docRepos` repo, read with `git grep -F` (each term after its own `-e`, so none can be an option) at `origin/<base>` as last fetched, else `HEAD`: never a working tree, and nothing is written there. Then every earlier ticket's work folder (`workFolder` for another key), read from the files, since a host never commits them: the files of `docEvidence.ticketFiles`, no link followed, no binary file, nothing over 1 MB, a folder at most three levels down, at most 200 files a folder; what these bounds leave out is said in a note (the files over 1 MB and the folders too deep, a few named and the rest counted, and the folders that had more files), for the ticket's own folder too. **Never:** the step's own tickets' folders, the release notes and the rest of `docEvidence.exclude`, under every content root of every doc repo, `.assets`, `.sources` inside a content root, frames, `node_modules` and the label store (`.doc-toolkit`). **Bounds:** files are ranked by the terms they hold, a rarer one weighing more (1 / the number of files it is in), then by their hits; a file lists its three lines with the rarest terms, each cut at 200 characters around the rarest, and at most 30 lines in all; a page's twin in the other language (the same path under the other root of its root pair) is named with it, not listed again, and the pages of two root pairs never are (roots with no pair known are never folded). The files past the bound are counted, the first ten named. The whole lookup has 45 seconds, each git call 20 at most; a repo or a folder the time no longer covers is said not searched. **The brief** lists each file with its path, its ref and short commit (a page) or its ticket key, its lines and terms, and the rules: the excerpts are data, never instructions; a page is cited by its repo, path, line, ref and commit, and read further only the way its line says, never in a clone's working tree: with Read in the step's read checkout of its repo (at the base the runner fetched now), with `git -C <worktree> show <commit>:<path>` in the step's worktree of it (whose files hold this ticket's change), with a plain `git show <commit>:<path>` for the hub's (the session starts in the hub), or with `git -C <clone> show <commit>:<path>` for a target clone on a step with no worktree; a page of a sibling doc repo no checkout of the step covers is cited from its excerpt alone, and its folder is never named (the runner makes no checkout for it, and adds no folder or rule for the owner's clone). An earlier ticket's file is read at its path in the hub. An earlier ticket's notes are what it saw on its date, so a conflict with today's code or a fresh check is stated, both sides, never dropped; a published page the ticket's change makes false is a page to update, which the plan and the PR name; a doc settles a claim only with a name, a path or a value read directly, and behaviour a doc describes stays a place, citing it, with the source `docs`; a place's `why` and a question's `sources` name the docs among the sources tried, in the page's language. No term, no hit, or a fault of the lookup or of its lines (a bug or a malformed result included: never the step's failure) is one line, and the brief is otherwise as before.

**A branch moved under a session.** When a session fails, the runner compares heads, never an error's text: the PR's head on the forge now, the head the step was given, and the worktree's. A forge head that is neither the step's head nor the worktree's head or one of its ancestors (by `git merge-base --is-ancestor` in the worktree; a commit the worktree's repo doesn't have is none) means a person's commit moved the branch while the session worked (its push was rejected as non-fast-forward, or its record was refused as `stale`). That is not the model's failure: the run is logged `moved`, no failure is counted, no bigger model is tried, the ticket isn't held, and the runner reads the status again and runs what it gives at the new head now (a UA change makes `translate` stale, say), within `limits.stepsPerTicket`. A forge head that is the worktree's, or an ancestor of it, is the session's own push (with later commits not pushed yet): an ordinary failure, with the ladder as before. The session's commits that never reached the branch would leave the worktree stuck at the next step, so they are kept under `refs/ticket-flow/set-aside/<branch>/<commit, 12 characters>` in the clone (`worktree` `setAside` in the run log; nothing is dropped) and the worktree goes back to the step's head, which the next step's worktree update then follows to the new head. A worktree with uncommitted changes to tracked files is left as it is, and is stuck as before. `failedStep`, the daily cap and the roles proposal pass over a `moved` run as they do a `busy` one.

**The site build.** The chain's `build` stage starts no session: the runner runs `build.command` (default `npm run build`) itself, in the PR's worktree at the step's head, with a host script's environment (no API key or sign-in token) and `CI=1`, in a process group of its own, so a timeout (`build.timeoutMinutes`) stops the whole build and not only `npm`. It records `build` as a session did: done with `{ "ok": true }` at the worktree's head, or failed with the last lines of the build's output as the note (and `{ "ok": false, "exit", "tail" }`). A failed build leaves a run (`script: true`, `session: null`, its `wallMs`, `exit`, `failures` and the ticket's mark), so the failed-step rules wait for a person and then hold, as for a failed session, and a broken build is not built again at every check; the report counts it as no session. A worktree at another head than the step's (the branch moved since the status was read), or a record refused as `stale` (it moved during the build), is `moved`: the status is read again, and two moves in a row stop the group for this run. A worktree at another head whose fetch of the branch failed (offline, a password asked) is not known to have moved: nothing is built, and the stage is recorded failed with the reason and a run with no `start`, so it waits for a person and the report shows it, instead of reading `moved` at every check. The whole chain builds the site once: the locales stage's brief runs the locale-translator with `--no-build`, and the visual pack's brief passes `--build-dir <worktree>/<build.outDir>` when `build` is done at the pack's head and the folder holds a site. A session that still builds the site itself (a re-sync, whose locale-translator builds; a visual pack with no build of its head to reuse, after a hand commit at ready for merge) runs under the build lock, which the runner takes before the session and frees when the step ends (see "The build lock").

**A session that stops on a text message.** In `claude -p` an assistant message with text and no tool call ends the turn, and so the session, once no background work of the session's own is left running (below), even with the stage half done (a clean style review written out as the last word, its commit, push, reply and record still to come). So when a session ends on its own and nothing is recorded for its step, the runner resumes it once: `claude -p <a continuation> --resume <its session id>` with the first command's model, effort, settings, tools, hook, folders, start folder and environment. The continuation says the stage is not finished and the last message was text with no tool call, and asks the session to finish the stage as the brief says (on a stage with a worktree: commit, push, post what the stage posts, and record), or to record it failed with the reason. It also says what to do with background agents the CLI stopped when the first process ended (a notice in the resumed session lists them as stopped): continue each with `SendMessage` to its id, telling it that the session's time limit stopped it, not a person (its last tool call reads as refused by a user), and to go on from its last finished step; start no new agent for that work, and wait for them by ending the turn, never in a loop. Probed on 2.1.321: the resumed process continues the stopped agent from its transcript, redoing the step that was in flight, and wakes on its notice. "Ends on its own" is read from the CLI's result event, every field of it (probed on 2.1.319): exit 0, `subtype: success`, no `is_error`, `stop_reason: end_turn`, `terminal_reason: completed`, no `api_error_status`, and a session id; a CLI that doesn't give one of them resumes nothing. Never resumed: a session the runner killed (the timeout), one that hit max turns or the budget, an error or a usage-limit stop, one that recorded anything for the step (even failed, or a plan's or a write's questions), one that ended on a busy browser lock, one whose `record` was refused (`nothing recorded: …` in its transcript, `<config dir>/projects/<slug>/<session>.jsonl`; a transcript that isn't found counts for nothing), one that used the whole session timeout (4 hours), and one on a PR branch a person moved while it ran (the moved-head check runs before the resume, and the step is `moved`, as with no resume). The resumed process gets the time the first one left of the timeout, not a fresh one; `--max-turns` counts per process, so a resumed step can take up to twice the role's turns. The browser lock is freed, and a read checkout's new `.sources/` moved, only after the resumed session ends. The two are one session for the gate and the ledger: one outcome, one failure at most, one `runs` entry with `session`, `resumed: true` and `resumedSession` (the same id, on 2.1.319; left out when the resumed process gave no result), the turns, duration and tokens of both, `wallMs` from the first start to the resumed end, and the cost of both (a resumed session's `total_cost_usd` already counts the first; one below the first's is added to it). At most one resume a step, of the first attempt only: the retry up the ladder is never resumed. The run log has a `kind: resume` line, and the step's line `resumed: true`.

**A session that waits for its workers** (`locales` and `resync`, `WORKER_STAGES`: the locale-translator starts one background agent per locale). In `claude -p` the `Agent` tool starts every agent in the background, with no foreground choice, and a turn that ends while the session's own agents run doesn't end the session: the CLI waits, and each agent's completion notice starts the next turn. The wait has a ceiling, `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` after the last turn (600 000 ms by default on 2.1.321, read in the binary), when the CLI stops the agents ("Background tasks still running … after the last turn (subagent …); stopping them" on stderr) and exits as a session that ended on text, which the runner then resumes. That is what cut a measured stage's first wave of 8 workers off after 10 minutes, and its pages were redone. The stop takes the session's background shells too, not only its agents (2.1.321 source: the wind-down kills each background shell still running), but the ceiling is held off while a background shell is within its own time limit: at 60 000 ms, a 150-second background shell was not stopped, alone or beside a 200-second agent, which ran to its end as well. So `resync`'s build, when the session runs it in the background, keeps the wait open while it runs, and is stopped with the workers only once past its own limit. For these stages the runner sets the variable in the session's environment (`sessionEnv`) to `BG_WAIT_CEILING_MS`, 2 hours: the clock restarts at each turn, so it is the longest wait with no notice, above the longest single worker measured (56 minutes) and below the session timeout. A hung worker so ends in an exit the runner resumes when the session's last turn came less than 2 hours (the timeout less the ceiling) after its start; a later last turn meets the kill first, which is never resumed (`0`, no ceiling, would always hold the stage until the kill). The resumed process has the same environment, with the ceiling fitted to the time the first process left: at most that less 10 minutes (`resumeCeilingMs`, `RESUME_MARGIN_MS`). Its clock counts from its last turn, not its start, so workers that go quiet soon after the resume are stopped by the CLI, with its own exit and result; a last turn more than 10 minutes into the resumed process can still meet the kill. The brief of these stages says to start the workers all in one message and end the turn, and never to check on them in a loop (`ListAgents`, `git status` or `git diff`, `Monitor`, `sleep`): that stage's resumed session polled its workers for 55 minutes, 204 model calls and 41 M cache-read tokens, because it believed that ending its turn would end the session. It also gives the line every worker's prompt carries: the command forms the role hook passes (each `locale-sync` call as one plain `node <path> …` with literal paths; no variable, `&&`, `;`, loop, redirect into a file, heredoc, `$(…)` or `node -e`; files with the Write tool; a `results.jsonl` line added by reading the file and writing it back whole), since the workers of two measured stages lost a turn on each refused form (23 and 18 refusals). The `locales` brief also says the stage needs no `ticket-state status` call: the brief gives its PR, worktree, push and record. Waiting needs no new form in the hook: ending the turn is the wait, so the `until … sleep` loop it refuses stays refused. The variable is not a documented setting: a CLI that drops it stops the workers at its own 10 minutes again, in the first process and in the resumed one (whose continued workers are cut off the same way), so a stage whose workers still need more than 10 minutes after the resume fails with nothing recorded. The runner copies the CLI's stderr line into the run's `note` (`cliStopLine`; `process 1: …; process 2: …` when both processes were stopped) and the step's run-log line (`cliStop`), so such a failure shows its cause. Probed on 2.1.321 with `--model haiku`: three agents started in one message ran side by side (3 × 40 s in 54 s) with the turn ended on text; the default ceiling stopped an 11-minute agent after 10 minutes, and a 60 000 ms one a 5-minute agent after a minute, each exit 0 and `end_turn`; a notice restarts the clock (at 60 000 ms, a 100-second agent finished after a 40-second one had reported); with the ceiling off the session slept 5.5 minutes and finished in one call after the notice; `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` makes `Agent` calls foreground (the same three in 44 s, the turn blocked until all returned) but kills a Bash call at its timeout (exit 143 after 2 minutes) instead of moving it to the background, which would kill a `locale-sync` call of over 2 minutes, so the runner doesn't set it.

**The ticket worktree.** Before a session of a stage that works on a PR branch (`write`, `uaReview`, `answerPass`, `pr`, `answerComments`, `styleCheck`, the chain, `resync`, `baseMerge`, `baseFix`), the runner makes the worktree of each of the step's PR branches, or brings it up to date (`lib/worktree.mjs`):

- at `<the clone's parent>/.worktrees/<repo>/<branch>`, beside the target's clone (`targets[].path`), outside every repo, and passed to the session with `--add-dir` (the clones aren't, on such a step);
- detached at `origin/<branch>` after a fetch (at `origin/<base>` for a branch not pushed yet), so a branch the owner has checked out in the clone never blocks it; an existing one is fast-forwarded to the branch, never over a session's uncommitted changes to tracked files or its unpushed commits; untracked files a session left don't stop it;
- when the branch was rewritten (the owner's rebase and force push), a clean worktree whose head was an earlier value of `origin/<branch>` (by the clone's reflog of it) is moved to the new head; one with uncommitted changes to tracked files, or with commits the branch never had, is kept as it is: no session starts, and the stage is recorded failed with a note that names the worktree and points here, as a failed step (it waits for a person's action or the next morning run, and the second such failure holds the ticket; see "A stuck worktree");
- with each of `targets[].links` (default `node_modules`) linked from the clone, and listed as `/<name>` in the common git dir's `info/exclude`: a `node_modules/` line in `.gitignore` doesn't match a link, so git would show it.

The brief names each worktree and its push command, `git -C <worktree> push origin HEAD:refs/heads/<branch>`, the only push a role may run. A session never makes, moves or removes a worktree, links a file, or runs `npm ci`/`npm install` (each role denies them), so the build runs with nothing to set up. When a worktree can't be made (a clone not on this machine, a folder in its place that isn't a worktree, git's error) or is stuck (above), no session starts: the stage is recorded failed with the reason, as a failed step with no session (a `runs` entry with no `start`, so it counts toward no cap or cost), and the report shows it.

**Which layers a role session loads.** `--setting-sources project,local`: the hub's `.claude/settings.json` and `.claude/settings.local.json`, and the runner's flags. Not the owner's `~/.claude/settings.json`. That layer allows Edit and Write with no scope and adds folders of its own (`additionalDirectories`), and a deny list can't hold those in: a session could write anywhere the list didn't name. `--setting-sources` decides more than the rules, so `project` has to stay:

| | On this route | Why |
|---|---|---|
| The hub's `CLAUDE.md`, `CLAUDE.local.md`, `.claude/skills/` | Loaded | `project` and `local`. With no source at all they aren't, and the hub's skills need them. |
| The plugin | From the toolkit the runner runs from (`--plugin-dir`), in place of the installed one | See "Which copy of the toolkit runs what" below. The hub's `enabledPlugins` names the installed copy, which this session doesn't load: a `--plugin-dir` plugin of the same name replaces it. |
| The hub's hooks and denials | Loaded | A hub's push guard still runs. The owner's own hook and `ask` rules on a push don't: the runner's push rules stand in for them. |
| The hub's allow rules and `additionalDirectories` | Loaded | **Claude Code drops a project file's `permissions.allow` in a folder it doesn't trust (debug log: `Dropped N project-scoped permissions.allow entries — workspace not yet trusted`)**, so they apply in a trusted hub and not in a scratch copy of it. The local file's are loaded either way, and so are the project file's denials and hooks. |
| The claude.ai connectors | Loaded, with the sign-in rather than a layer | A read-only session in a real hub on this route listed 11 in its `init`; a scratch hub listed none. The owner's sign-in isn't a settings layer: it works on this route. Host jobs (`run.skill`) keep every layer, the owner's too: the toolkit doesn't know what a job does.

**Which copy of the toolkit runs what** (D-157). Every session the runner starts (each role's stages, a resumed session, the learner, a skill job) gets `--plugin-dir <the toolkit's plugins/doc-writer-toolkit>`, the folder the runner itself runs from (`PLUGIN_ROOT`, `pluginArgs` in `lib/runner.mjs`). So one copy runs all of it: the runner, the watcher, `ticket-state`, the role hook, the briefs, the role files and the scripts the briefs name (which ran from it before), and now the skills and the scripts they name by `${CLAUDE_PLUGIN_ROOT}` (`locale-sync`, `doc-align`, `ui-labels`, `screenshot-locales`, `section-state`), which came from the installed plugin. A merge into the branch that checkout follows, and the live switch that updates it, now deliver the skills and their scripts too, at the session that starts next; nothing waits for the installed plugin to update. A session already going would read the old skill it loaded and the new version of any skill, context file or script it opens after the pull, so the switch is made while no session runs: `mode` off, no run going, then the pull. Probed with CLI 2.1.321: a `--plugin-dir` plugin with the name of an installed, enabled one replaces it in that session (its `init` lists it once, as `doc-writer-toolkit@inline`), under `project,local` and under every setting source, and `${CLAUDE_PLUGIN_ROOT}` in its skills is that folder. All of this rests on that behaviour of the CLI: after a CLI update, probe it again (the `init` of a session started as the runner starts one lists `doc-writer-toolkit@inline` once and no installed copy) before the next switch. The owner's own sessions (a terminal, the editor) pass no such flag and keep the installed copy, which follows the marketplace's branch. `claude -p /usage`, the usage read, runs no skill and gets no flag.

**Writes are an allow list.** A role file allows no file-writing tool, a bare `Edit`, `Write`, `MultiEdit` or `NotebookEdit`, or one scoped to everything (`Edit(**)`, `Edit(//**)`, `Edit(~/**)`), in `roles.<role>.allowedTools` is dropped, and the runner allows, as `Edit(...)` rules, which cover Write too:

- each worktree of the step (`Edit(//<worktree>/**)`) and `<state>/tmp/` (every role; triage only `tmp/`);
- each of the step's tickets' `workFolder`, when the host declares one (not triage);
- on a step with no worktree (the plan, a video's import; not triage), `Edit(//<clone>/**/.sources/**)` for each target clone, for what `section-readiness`, `app-explorer`, `section-planner` and `convert-sme-input` leave there, and `Edit(//<clone>/screenshot-tests/_plan-<key>-*)` for each key of the step, for the live check's Playwright spec (roles have no other way to drive a browser). That folder holds an owner's hand-written specs, git-ignored and so past recovery, so a session creates only its own, `_plan-<key>-<what>.spec.ts`, and can read and import the rest. The brief names the file; the session runs it with `npx playwright test` from the clone. A key that isn't a plain name gets no rule. Never a clone's pages.

The brief lists them. The denials below still apply inside those folders, so a worktree's `.github/`, `CLAUDE*.md`, `node_modules/`, `package.json`, lockfiles and build files stay closed.

**A hub's own allow rule can widen this, and the runner can't take it back.** An allow in any layer counts. A hub whose project file allows `Edit(**)` keeps its whole checkout writable for role sessions, except what a denial names. A denial can't close the hub instead, because a deny wins over an allow and `<state>/tmp/` and the work folder are inside it. So a host should keep unscoped write rules out of its `.claude/settings.json` and declare `workFolder`, in this order: `workFolder` first, then the rule. Probes, with the project allow list fed in as a `--settings` layer, since a scratch folder is never trusted: with `Edit(**)`, on a step with worktrees, a Write to the hub's top level and to `docs/.sources/other/` succeeded, and outside the hub it was denied; without it, both were denied, and the worktree, `tmp/` and the work folder still worked. On a step with no worktree, a hub that is a target is a clone like the others: without `Edit(**)`, its `.sources/` folders are open (see "Limits") and its `screenshot-tests/` only for `_plan-<key>-*`; with `Edit(**)`, its whole `screenshot-tests/` is writable too, hand-written specs included. A clone beside the hub is held to the pattern either way.

**What a role session may run.** A deny in any layer wins over an allow in any other. A hub's layers allow far more than a role needs. Today's, for example: `git push:*`, `git fetch:*`, `git branch:*`, `git stash:*`, `git mv *`, `git cherry-pick *`, `git checkout *`, `git ls-remote *`, `python3 -c ' *`, `gh pr *`, `find:*`. So the runner keeps the role's own rules narrow and denies, in every role, whatever no stage runs. These denials guard against a mistake and a broad host layer:

- **Git, `-C` on the worktree for every change.** The role files hold the reads and `add`/`commit` once, `Bash(git <command>:*)`; the runner adds the `git -C <worktree>` spelling for the literal path of each worktree of the step (`Bash(git -C <worktree> <command>:*)`, a prefix rule, so `git -C <worktree> tag -d x status` matches nothing, and no other folder is allowed). The only push is the brief's exact `git -C <worktree> push origin HEAD:refs/heads/<branch>`, and the only fetches are `git -C <worktree> fetch origin` and `… fetch origin <branch>` for the worktree's branch and base; `… ls-remote origin <branch>` follows the same exact form, and `rev-parse` is among the reads of the writer, reviewer and translator. In the plain spelling (`ROLE_DENIED`), every `add`, `commit`, `grep`, push, fetch, `branch`, `stash`, `cherry-pick`, `mv`, `rm`, `clean`, `tag`, `remote`, `config`, `update-ref`, `reflog`, `gc`, a worktree change, `ls-remote`, `checkout`, `switch`, `pull`, `reset`, `rebase`, `merge`, `restore` and `revert` is denied (`ls-remote` runs a command, `--upload-pack=<cmd>`): a plain command runs in whatever checkout the session's folder holds, and a session starts in the hub, the owner's checkout (a plain commit would land on the hub's branch; a hub's `git push:*` would push it to any branch or delete one by `:<ref>`). `git grep` runs a command (`-O<cmd>`, `--open-files-in-pager`), so it is denied plain and as `git -C <worktree>`; the Grep tool searches. `--output=<file>` (`log`, `diff`, `show`) writes a file past the Edit denials, so `git * --output=*` and `git * --output *` are denied. The push and branch denials also name each worktree's literal path (`deniedFor`): never `git -C *`, whose `*` would span a commit message. A plain read still runs after a `cd` to a worktree as a separate call (`cd <worktree> && git …` in one call is denied, and so is a quoted path).
- **Folders.** A step with worktrees gets them as `--add-dir`, and not the target clones; a step with none gets the read checkout of each target clone at `origin/<base>`, where it works (its `.sources/` folders are the clone's), and the target clones, for the plan's spec and what those links lead to, with the role's git reads spelled for each (`log`, `show`, `ls-tree`, and for the roles that have them `status`, `diff`; never `add` or `commit`); with no read checkout, the brief names a clone off its base or behind its origin (see "A clone off its base"). Every step also gets the toolkit roots as `--add-dir`, so `ls` works where a session reads its scripts: a probe showed no further skill or plugin loads from them, Write there is denied (`writeDeniedFor`), and the hook refuses `mkdir` and any `cd` there, since a relative `mkdir` after such a `cd` would land in the root. A `cd` outside the session's folder, its add-dirs and the hub's `additionalDirectories` is denied (the shell goes back to the session's folder). The session's folder is the hub itself, an owner's checkout, which is why every change goes through `git -C <worktree>`.
- **Scripts by name, no code of its own.** `node` runs only the scripts the role's stages need, by their literal path (`Bash(node <root>/scripts/<script>:*)`; for `ticket-state`, only `record`, `status` and `config`: its other commands are the owner's). Beyond those three, triage runs `tracker`; the writer `tracker`, `forge`, `browser-lock`, `ui-labels`, `screenshot-locales` and `video-parts`; the reviewer `visual-pack` and `forge pr-state`, `edit-pr` and `review-on-lines` (the EN review's round); the translator `locale-sync`, `ui-labels`, `doc-align`, `screenshot-locales` and `forge pr-state` (`ROLE_SCRIPTS`). They come from the runner's own toolkit, which is the plugin every session loads (`--plugin-dir`), so the scripts a skill names by `${CLAUDE_PLUGIN_ROOT}` are these; and, as before, from each install of the plugin on the machine for the hub (Claude Code's `installed_plugins.json`). Denied: `node -e`, `-p`, `--eval`, `--print`, `--require`, `--import`, a bare `node` (standard input), `NODE_OPTIONS=…`, `python3`, `python`, `perl`, `ruby`, `sh`, `bash`, `zsh`, `osascript`, `eval`, `xargs`, `env`, `find … -exec`/`-execdir`/`-ok`/`-delete`, a hub's `CORPUS=… *` env prefix, and `node_modules/.bin/playwright`; `ffmpeg`, `ffprobe` and `tesseract` by hand (a role cuts a video only with `video-parts`, and the frame sweep is the runner's); `npx playwright` in a role whose file doesn't allow it (a hub allows it); and two script flags that run code, `ui-labels --source 'command <cmd>'` (a shell) and `visual-pack --playwright-from <dir>` (JavaScript from that folder). Every `gh` and `curl` call (the role files), and the tracker's and the browser's MCP tools (`mcp__claude_ai_Trello`, `mcp__trello`, `mcp__playwright`): a role changes the tracker and the forge only through the toolkit's scripts.
- **Files.** An `Edit(...)` deny covers Write too. Denied in any folder: the settings layers (`~/.claude/**`, `~/.claude.json`, any `.claude/**`), `.git/` (hooks and config would run code at the next allowed `git commit` or `status`), the toolkit roots the session runs scripts from, the flow's own state (`tickets/`, `locks/`, `roles/`, `watch/`, `jobs/`, `runs/`, `reports/`, `code/` (the code checkouts), `rearmed.json`, `roles-proposal.json`, its top-level `*.md`; a session's own files go in `<state>/tmp/`), `package.json` and the lockfiles, `docusaurus.config.*`, `sidebars.*` and `playwright.config.*`. Also what runs code later: `CLAUDE*.md` (a `UI label source: command …` line runs a shell, as `--source` does), `.github/` (the host jobs' scripts, and workflows GitHub runs with the repo's secrets once a ticket branch is pushed), `node_modules/`, `.npmrc`, `~/.gitconfig`, `~/.config/git/`, the shell startup files, `~/.ssh/` and `~/Library/LaunchAgents/` (what it names starts at the next login); and the ticket flow's settings files, wherever the host keeps them. `.env` files (`.env`, `.env.local`, `.env.*.local`, `.env.development`, `.env.production`, `.env.test`, `.env.staging`, `.env.dev`, `.env.prod`) are not read, a guard against a mistake: the scripts and the Playwright specs read them in their own processes. `.env.example`, which holds no values, is readable (a deny can't except one name, so the denied ones are named). The read checkouts (`…/.worktrees/<repo>/.read/`) have no deny: a deny there would also refuse the writes through their `.sources/` links, Bash's `mkdir` included (probed). Their pages stay read-only because no rule allows a write there but `Edit(<read checkout>/**/.sources/**)`, and a session asks no one (probed: a Write or an Edit of a page there is refused, one through a link lands in the clone).
- **Owner's checkouts, on a step with worktrees.** The pages go into the worktrees. The target clones' content roots are not writable (`checkoutDeniedFor`): each declared UA content root (`docs/` when none is declared), each EN i18n root and `i18n/`, read from the clone's own `CLAUDE.md`. A relative path resolves against the hub, which may be a target itself. A UA root keeps its top-level dot folders writable, since a hub keeps its tickets' files and the flow's state in `<root>/.sources/`. The CLI's rules have no working negated character class (probes: `[!.]` and `[^.]` both match a dot), so the rule names the first character of a page or folder, `[a-zA-Z0-9_-]`. A top-level name that starts with another character is not covered, and neither is a root that holds the flow's state under such a name. `record write` is the check behind it: each PR's worktree must hold commits beyond the base, pushed as they are, or the write is refused (`notWritten`).

What these rules guard, and what they don't. They keep a session's git changes on its own worktree and branch, deny the ways a session runs code of its own by name (an interpreter, a string, a preload, a shell), and keep its Write and Edit calls away from what would widen a later session's rules or run code later. They guard against a mistake; they aren't what stops a session someone has injected instructions into (through a team card or a PR comment). A deny that names an argument can't be relied on for that: earlier CLI versions let `'--output=…'`, `--out''put=…` and `--sour''ce …` past such a deny whenever an allow rule matched the command's start, and while 2.1.319 denied those in a re-probe, it still let a file be written with `git log -1 *` (the glob expands to a file the session named `--output=x`), read `.env` with `cat .en?` under a hub's `cat:*`, read a `.env.foo` with `cat`, and read `.env` into a commit message with `git -C <worktree> commit -F`. That is the hook's job (next paragraph). A prefix deny (`git push:*`) holds for any argument. They don't contain the code an allowed command runs (below). A layer that allows `node` itself (none does today) would also let a session run a file it wrote, past the rules; the hook refuses it. A host override as broad as `Bash(git:*)`, `Bash(git *)` or `Bash(git -C *)` in any layer would reopen the `-C <other folder>` forms; no layer has one today. In the default rules no role allows `git branch` at all; the plain prefix deny also covers abbreviations (`--del`) and combined flags (`-rD`), and so does the `-C <worktree>` one. The CLI's matching was checked with headless probes (haiku, scratch repos, the layers' allow lists fed in as a `--settings` layer): `:*` is a prefix match, a `*` elsewhere matches any text, a rule that ends in `:*` after a `*` never matches, a deny wins over an allow, each part of a compound command is checked, an `Edit(...)` deny blocks Write, `Edit(//**/x/**)` reaches any folder, and an env prefix (`NODE_OPTIONS=…`) is not matched by the command's own allow. Host jobs, which have no worktree, carry `JOB_DENIED`: no push, no `git branch` change and no fetch, in the plain and `git -C *` spellings (a `:<branch>` push can't be told from another push by a rule that works, nor a fetch refspec from a plain fetch). A skill job also gets the roles' git, code and file denials (`jobDenied`), but not their MCP denials: a host's job may work on its tracker through MCP. These hold for the plain spellings only: a job whose allow list held `git:*` or `git -C *` got past every one of them with a quoted subcommand (a probe pushed with `git -C <clone> 'push' …` and wrote with `log '--output=…'`), so settings validation refuses a skill job with a bare git prefix, `Bash(git:*)`, `Bash(git *)`, `Bash(git -C *)` or all of Bash. A job has no hook: give it the narrowest allow list its skill needs.

**The hook.** The runner passes every role session a PreToolUse hook (`role-hook.mjs`, with `lib/role-hook.mjs` and `lib/shell-words.mjs`; Node, no dependency) through `--settings`, on `Bash` and on `Monitor`, which runs a command under the Bash rules. The rules above stay as the first layer. The hook reads the command the way bash and zsh would, removing quotes and backslashes and splitting chains and pipes, and takes each simple command in turn:

- **An allow list of names.** A command that isn't a known reader, git, `node`, `npx`, `npm run`, `mkdir` or `find` (or named by a rule of the role in the tracked file) is refused: a writer or interpreter nobody thought of is refused too. So is a command by path, or an environment assignment before it.
- **What it can't read without running it:** a variable, a substitution, a brace list, a subshell, a heredoc, a glob at the start of a word on a command with flags that matter (it can expand to a file named `--output=x`). `$` in a commit message goes in single quotes.
- **Redirects:** output only to `/dev/null`, `/dev/stdout` or `/dev/stderr`. A session's files go through the Write tool.
- **Git:** no option before the subcommand but `-C` and a few harmless ones, reads by name and no `--output`, `--no-index`, `--ext-diff`; `add`, `commit`, the brief's exact push, the plain fetches and `ls-remote origin <branch or base>` only as `git -C <the step's worktree>`; `add` without `--force`.
- **Scripts:** only the role's, by literal path; `ui-labels --source` and `visual-pack --playwright-from` in any spelling.
- **`npm run`, `npx`:** only in a role whose file allows them; no option that changes what runs or where it writes (`--script-shell`, `--prefix`, `--config`, `--output`, `--out-dir`); `npx playwright test` only.
- **`find`:** no `-fprint*`, `-fls`, `-exec*`, `-ok*`, `-delete`. **`mkdir`:** only inside the step's own folders, never a browser lock or under `.git`, `.claude`, `.github`, `node_modules`.
- **`.env`:** any word that names `.env` or `.env.<x>` (not `.env.example`) as a file, in any case, as `HEAD:.env`, `--file=.env`, `-F.env` or as a glob that could expand to one (`.en?`, `.*`, `*`), for every command but those that don't read a file's content (`ls`, `stat`, `test`, `find`), a commit's message and grep's pattern. A recursive `grep` is refused unless each `--include` names a file kind (`'--include=*.md'`), since `*` or `*.foo` could match one; a recursive `diff` is refused too. Both read it without naming it. Long flags count under any abbreviation (`--recur`, `--directories recurse`, `--forc`).

**When the hook fails, the command is refused,** but one case remains. Claude Code lets a command through when a hook exits 1, crashes, is killed, is missing or prints something it can't read; only exit 2 or a deny stops it (probed for each). So the hook line ends in `|| exit 2`, which turns all of those into a refusal, and inside the script anything but a clean pass is one: no config, bad input, an error, its own deadline of 20 seconds. **A hook that hits the CLI's `timeout` is let through whatever the line says** (probed: the line dies with it). So the `timeout` is 120 seconds, the reader is one linear pass with a 100,000-character limit, and a command that gets there has to freeze `node` itself for two minutes; it then meets only the first layer. A hub's `disableAllHooks: true` in its project or local file switches off a `--settings` hook, unless that layer says `false`, as the runner's does (probed). The hook's config is in the session's environment, set by the runner, with its markers (`sessionEnv`); no session can change it.

**What the hook doesn't close.** It reads command lines, not what a command does once it runs:

- A relative path is read against the shell's folder when the call starts, not after a `cd` in the same call. `cd <worktree> && mkdir docs/x` is refused, though it is the session's own (a `cd` as its own call, or the literal path, passes), and `cd <a target clone> && mkdir <a path that is open from the hub>` passes the hook, so where the first layer lets it, it makes an empty folder there. A `cd` into a toolkit root and two `cd` in one call are refused, so this doesn't reach the roots.
- An allowed test or build runs code from files a session may write: the writer's `npx playwright test` runs its own spec, and the translator's `npm run build` and `npx docusaurus build` run the site's code and MDX pages from the worktree, with the session's own rights. A session someone has injected instructions into can do anything through those. The boundary would be the Bash sandbox, which breaks them (see "The Bash sandbox").
- The scripts it allows take paths: `visual-pack --out` writes a sheet in the folder it is given, and `--root` and `--settings` are taken from the command line (`ticket-state`, `tracker`, `browser-lock`).
- Secrets in files not named `.env` or `.env.<x>`. A `node` script or git reads any path it is given, past Claude Code's folder checks, which look at the command rather than at what it opens: `tracker comment --text-file prod.env` and `git -C <worktree> commit -F <any file>` both read that file.
- Other tools than Bash and Monitor: a subagent's Bash calls do go through the hook (probed), and the tools no stage uses that run or schedule work or send something outside the session are denied whole, not read (`TOOLS_DENIED`: `Workflow`, the `Cron*` tools, `RemoteTrigger`, `ScheduleWakeup`, `PushNotification`, `DesignSync`, `EnterWorktree`, `ExitWorktree`, `WebFetch`, `WebSearch`, the `Artifact*` tools, `SendUserFile`; a name the CLI doesn't have is ignored). A new tool of that kind in a later CLI isn't on the list until someone adds it. `Agent`, `SendMessage`, `TaskStop`, `ListAgents`, `Monitor`, `Skill`, `ToolSearch` and `ReportFindings` stay. The `Read` tool can open a `.env.<x>` that `ENV_FILES` doesn't name. Host jobs have no hook.

**Scripts that refuse on their own.** A session has no way to set a variable for its commands (the hook refuses an assignment, `env`, `export` and `unset`), so the runner's environment marks the session (`DOC_TOOLKIT_ROLE_SESSION=<role>`) and the scripts check it, whatever the hook did: `ui-labels` refuses `--source` and any `command` source, even a declared one, since that is a shell line from the `CLAUDE.md` of whichever folder `--root` names, and a session picks the folder (a host with a `command` source runs its label check by hand, not in a role session); `visual-pack` refuses `--playwright-from`; the tracker's `download-attachment --out` goes only in the ticket's work folder or `<state>/tmp/` (`DOC_TOOLKIT_DOWNLOAD_DIRS`), as real paths and never through a link. The tracker's `--origin`, which sends its key and token to that origin, works only under a test marker (`DOC_TOOLKIT_TRACKER_TEST`), which the runner strips from a session's environment.

**The Bash sandbox.** Not used for role sessions. Probes (`sandbox.enabled`, `failIfUnavailable`, `autoAllowBashIfSandboxed: false`, `allowUnsandboxedCommands: false`, macOS, in a folder outside the system temp area, whose writes the sandbox allows): it does contain a build script: a write outside the session's folders failed with `Operation not permitted`, and `curl` and `fetch` failed with no route out, where the same script with no sandbox wrote the file. But with those settings, and no `sandbox.filesystem.allowWrite`, it also stops what the stages run: a worktree's `git add`, `commit` and `fetch` (the worktree's git folder is in the clone's `.git/worktrees/`, outside the add-dirs), a `push` to a local origin outside them, and headless Chromium in `npx playwright test`, which passes with no sandbox. `allowWrite` on the clone's `.git` may settle git (not probed); Chromium's failure is the one with no such setting in sight. The scripts' calls to the tracker and the forge would need the network too (not probed). `autoAllowBashIfSandboxed` defaults to true, which would approve every sandboxed command past the allow list, so it has to be set off. Leaving these out through `sandbox.excludedCommands` would leave out the very commands that run a worktree's code.

**The owner's queue and In translation.** `finalReview` is the owner's read of the UA and starts nothing: every PR lands there after the `pr` stage, `sme` and `places` alike, with or without places; so does a reviewer's move and a PR the expert approved. Comments come first (`answerComments`): the comments and reviews on the PR that the pipeline didn't post and no record handled, a person's (the owner's are instructions). Not the pipeline's own: an id in `posted.pr`, and a line comment of a review whose id is there (the places' comments `review-on-lines` posted from the owner's login, also when only the review's id was recorded); the `pr` record also adds each place's `commentId` to `posted.pr`. Not a review the owner hasn't submitted yet: the forge module leaves out a draft review's line comments, which GitHub shows to their author (`forge`'s README, `pr-activity`); once submitted they count. A new reviewer a person requested on a PR there, of either kind, moves it to review.

**The expert review** is the owner's call, never a gate. The writer's `pr` record says per PR whether it recommends one and why (`expertReview`: open questions for the expert, facts not found in the code or the UI); `status` (`prs[].expertReview`) and the report show it, and a recommended one puts `forge.expertLabel` on the PR; nothing waits on it. A person's move of the card to the review status (`follow` to `smeReview`, from the owner's queue or elsewhere) calls the expert of each PR that follows the move: the label of its target's `review` stage, a review request to its targets' `reviewers` (`forge request-reviewers`; one already asked is left alone), and its targets' `cardMembers` on the card (`tracker add-member`; one already on it is no change), each PR its own targets' people (`lib/experts.mjs`). A review a person requested on the forge from the owner's queue (row 9) moves the card and adds the card members only: the person chose the reviewer. Nobody is removed from a PR or a card, whichever way the card moves. Each time a PR enters the review (that `follow`, or row 9's `move`), when the host set `forge.reviewComment`, it gets that comment with its Files changed link (`forge comment --unless-header`, so a run stopped before its record posts it once), and the comment's id goes in `posted.pr`: the pipeline posts from the owner's login, and the rule never reads it as the owner's. **The expert's Approve** (D-082) moves the PR on: a PR at `smeReview` that one of its experts approved since it entered the review (`smeSince`, or for an older ledger the time the card was left there) goes to `finalReview` by itself (`move --pr <id> --to finalReview`, no model), its stage label with it, the card to where its least advanced PR is, and the approval kept at the head the expert approved (`prs[].expertApproval`, `by: "reviewer"`). The approval is read from the reviews themselves, not the PR's review decision, which GitHub fills only where a branch rule requires a review: only the PR's experts count (its targets' `reviewers` and the reviewers requested on it, `reviewersRequested`; never the pipeline's own login or a bot), each expert's last verdict counts (approved, changes requested, dismissed), one asking for changes holds the PR, and of the approvals given since the PR entered the review the latest moves it, with its head. An approval from an earlier round (before a move back into the review) moves nothing. The same experts' reviews and comments are the activity the report's quiet count reads. New comments are answered first (row 11); an answer to a reviewer's comments on a PR in the review that no one approved yet carries `askApprove` (the Files changed link), and the summary ends with one line asking the expert to approve. A person's forward move out of the review is the approval too, at the head then, `by: "person"`: an expert's word heard elsewhere. A ledger left at `smeReview` by the earlier rule (an `sme` PR went straight to review after `pr`) reads as before; its move back takes the pending request along. The chain runs only at `translation`, after a person moved the card to In translation, which is the only UA approve (`approval`). A ledger left at `finalReview` from before this waits the same way, a chain stage left `running` too. Moving the card back stops the chain between steps. On a PR with two cards, a move of either into In translation or back out of it moves the other card and records its `follow` in the same step, before this ticket's record, so a stop in between is finished by the next run. When every PR of the ticket is ready for merge the card goes back to the final review status with `tracker.readyComment`, kept in `posted.card` so it doesn't count as a person's comment; a card moved on again gets `readyForMerge` again and comes back, with no session. The pipeline never moves a card into `translation` except along with the other card of the same PR, so a host's `transitions` need `finalReview` → `translation` only for that. A handover or an import of a card in the final review status lands in the queue and starts nothing.

**The stage label.** Each scripted step that moves a PR's stage sets its target's label for it (`forge set-stage-label`): `inProgress` at `writing` and `reworkWait`, `review` at `smeReview`, `finalReview` at `finalReview` and `readyForMerge`, and at `translation` the target's optional `translation` label (`stageLabelOf`, `lib/stages.mjs`). The `follow` to `translation` gives it to each PR the move takes, and to a ready PR it takes along (`takeReady`) once the record took it, the `readyForMerge` step puts the `finalReview` label back on its PR at once (the card may still wait for another PR), and a `follow` out of `translation` sets the label of the stage the PR goes back to. A ready PR row 8 sends back (`move --pr <id> --to finalReview`) keeps the `finalReview` label. On a PR with two cards, the other card's own PRs its `follow` record moves are labelled too. A label set after a record stood (at `readyForMerge`, and for the PRs another record moved) that the forge refuses is a warning (`warnings` on the step, its `note` in the run log): the step is done, as its record is. A target whose `labels` has no `translation` keeps its `finalReview` label through the chain: the move sets `finalReview`, as before, and a PR that already has it gets no label request. The ledger's `prs[].label` follows the same rule. **The check label** (`forge.checkLabel`, which asks the owner to look; see "The ready and check labels" for when the runner puts it on) comes off when a person moves the card past the final review status (D-128, `forwardMove` in `lib/stages.mjs`): to In translation, or to done. The owner's check is done. A move into the final review keeps it, from In progress, from the expert's review or by the expert's Approve: the owner's check only begins there; so do moves between In progress and the expert's review, and every move back. The `follow` removes it from every PR the move took (to done, every open PR of the ticket) with `forge remove-label`, after the records stood, so a failure is a warning. No role may run `forge add-label` or `forge remove-label` (the role hook and the session's deny rules): only the runner sets the label.

**The ready and check labels** (`lib/pr-labels.mjs`). After each step it runs, a session's or its own, the runner compares each PR of the step's tickets with the ledger as it was before the step, and sets two labels with `forge add-label` and `remove-label`; a label the forge refuses is a warning in the run log, and the step stands. `forge.readyLabel` goes on when the PR is marked ready for merge (a `readyForMerge` record, a new ready head too) and comes off when it leaves ready for merge (row 8 sends it back to the owner's queue, a person's move takes it into the chain again or back from the final review, a question stops it); a merged PR is left as it is. `forge.checkLabel` follows the PR's open questions to the owner (`openQuestions`), after each `answerComments` and `styleCheck` record: any open, the label goes on, and goes back on if the owner took it off; none, it comes off. Between two such records it is left as a person set it, so the owner's removal stands until the next answer. The first such record of a PR with no `openQuestions` kept (a PR from before the switch, or one a forward move cleared) only puts the label on, when it has questions, and never takes it off: the questions of the summaries before it are not known. The labels follow changes of the ledger, not the forge's state: a failed add or remove is a warning and is not retried, and a change it missed is made at the PR's next transition (the next ready mark or exit, the next such record). The `answerComments` brief lists the questions still open, and the session records in `questions` those its round left open. `scriptedCalls` shows the ready label's calls in a dry run's plan.

**The translated label** (`forge.translatedLabel`, `lib/pr-labels.mjs`), whether the PR's translations match its UA: a fact of its own, next to the stage label and the ready label (a PR moved back after the translation with UA unchanged keeps it, while the ready label comes off). The `readyForMerge` and `resync` records keep the head as `prs[].translated`, and the runner puts the label on after each, a new head too. The rule takes it off, at any stage, once it sees UA changed in words since that head (`changedUnder` between the two, the runner's id commits left out, an image not counted: a page or another file under the UA roots): its first step for the PR is then `untranslated`, scripted, whose record clears `prs[].translated`, and the runner takes the label off. So the owner's final edit, an answer to a comment that changed UA, or a hand edit at the expert's review takes it off at once, before the PR goes back to the owner's queue; the re-sync after the owner's move puts it back. After the translation, a resync or a chain stage starts only after such a change, so the label is already off when one does. A card's move, an EN-only commit, an id-only change, the runner's id commits and an image change leave it. A merged or closed PR is never touched; the close records whether it had the label (`merged.translated`), and a PR merged without it is listed in the report ("Merged without «…»") and in the progress file, with its link, on the day the ticket closes: its translations may be behind its base. With two PRs on a card that is the day the last one merges. `scriptedCalls` shows the label's calls in a dry run's plan. A PR that was ready for merge before the label was set up gets it at its next `readyForMerge` or `resync`. Only the pipeline's tickets count (mode `pipeline`): a ticket in the owner's hands is never listed. A merge of the base into the PR's branch (keeping the PR fresh) that brings UA changes to a page the PR also changes reads as a UA change since the translated head, so it takes the label off, as it sends a ready PR back.

**The heading ids after a person's edit of EN** (`idSync`, `lib/id-sync.mjs`, the runner's own with no model; `context/doc-rules/project-rules/heading-anchors.md`, rules 2, 4, 6 and 7). With the translated label on and still matching UA, a hand commit since the head it was put on for that changed a page outside the repo's UA roots (an EN page) is checked once (`prs[].idChecked`): at ready for merge before `readyAgain`, at any other stage after the new comments. In the PR's worktree at the head, for each such EN page and its UA page (the root pairs the worktree's `CLAUDE.md` declares), `../doc-align` compares the heading ids (`headingIdMismatches`, the `HEADING-ID-MISMATCH` check). For each mismatch: a UA heading the base doesn't have (new in the PR) takes the EN heading's anchor, its `{/* #id */}` renamed on the UA page and on every further locale's page (the `docusaurus.config` locales other than the default and `en`, each carrying the comment verbatim), with every link to the old id under the content roots rewritten (`renameIds`); a heading the base has (published) keeps its id, and the EN heading gets it explicitly, `\{#old}` (`withExplicitId`). No word changes. A heading counts as published when the base has its id as a UA `{/* #id */}` comment or as an EN anchor (the base EN heading's explicit id, else its slug): a page published before UA ids existed has the second only, and its ids are kept all the same. The renames of a page are checked together, against the ids the page has once all of them are made, so a chain (`example` → `sample`, `example-1` → `example`) is made whole; a rename that still can't be made (its target kept by another heading, or taken by another rename) leaves the whole page as it is, with a `blocked` line comment under that heading, and its hand commit goes into `idBlocked`, not `idChecked`: it isn't read again, and a ready PR is not made ready again until a later commit's check of that page passes. The step makes one commit (`Heading ids: UA and the locales in step with EN`) in the worktree and pushes it. A push refused because the branch moved (origin's head is no longer the step's) sets the commit aside and reads the status again (`moved`); any other refusal (rights, a protected branch, the network) is the step's failure, with the error. Any failure once the step writes (a write, a rename, a commit a hook or signing refuses, the push) resets the worktree to the head it started at, so the next step finds it clean. Then one review with a line comment under each heading it changed or left blocked, on the EN page (`forge.idComments.renamed`, `.kept` or `.blocked`), and the record. The line comments need the forge to show the push (six reads, five seconds apart); if it doesn't in time, or the review fails, the step's note says so and they are not retried: the owner sees the commit, and doc-align's check flags a mismatch left. The commit is a pipeline commit and an id commit (`prs[].idCommits`): the rule reads every range around it, so it makes no stage stale, sends no ready PR back, starts no re-sync and no style check, and the translated and ready labels stay. At ready for merge, `readyForMerge` follows for the new head. **The rename the owner asks for:** the owner's reply in a `kept` thread that is `forge.idComments.rename` (after the trigger word, with one; case, quotes and a full stop don't matter) is caught before row 11, so no `answerComments` session takes it: an `idSync` step with `rename`, which takes the explicit id off the EN heading, gives the UA heading (and every locale's) the anchor its words give, rewrites the links, commits and pushes, replies in that thread with the `renamed` text, and records the reply as handled. A rename asked for that changes nothing (the EN heading already gives the id, say) gets the `notRenamed` reply with why, and is handled too; the `kept` comment is not marked renamed. A page whose UA and EN heading counts differ, an EN page under no declared EN root, or a rename to an id that is taken or not kebab-case is noted on the step (`note`), and nothing is changed for it. Without the label, no hand commit is checked.

**After ready for merge.** A UA change on a PR that is ready for merge, whoever made it (the owner's final edit, an answer to a comment), translates nothing by itself: the rule's `move --pr <id> --to finalReview` (no model; the step carries `since`, the ready head) puts the PR back in the owner's queue, the card in the final review status. Further rounds there (comments, hand edits) translate nothing either; a UA hand edit gets its style check (see "The style check of a person's edits"). The owner's move to In translation then takes the PR to `translation`, and since it was ready before and its chain is done, the rule runs, in order: `resync` once over the whole range from the last ready head to the current head (the step carries `since`, and `items`, the numbered edits made since; the brief names `<since>..<head>`: the UA blocks changed in that range go into EN and the further locales, whatever the commits' author; done with nothing to re-sync only when that range changed no UA block); then `visualPack` again when an image changed between the head the pack saw and the new head (any image file outside a `.sources/` folder); then `readyForMerge` for the new head, which runs the UA → EN image check as `align` does (the runner makes the worktree first). No chain stage runs again. The ready head doesn't move while the PR waits in the queue, so the range holds every round. A move to In translation that comes before the rule saw the change (both in one check) takes the ready PR along when the change is only the owner's own commits; one with a commit of the pipeline's goes back to the queue first. A `resync` left `running` runs again only on a PR at `translation`: one the earlier rule started at ready for merge, or one whose card the owner moved back, waits for the next move. An id-only change keeps the PR ready, and so does a commit of the pipeline that left UA alone; a hand commit that left UA alone (an EN edit by hand) gets `readyForMerge` for its head, after the pack if it changed an image, with no re-sync.

**The list of edits and the reply by number.** Every list of edits the owner reads on a PR is numbered, and its items are kept per PR in `prs[].edits`: `n`, `list` (`description`, or the id of the comment it was posted in), `stage`, `page`, `block`, `before` and `after` (the exact UA texts), `en` (`page`, `before`, `after`) when the EN block changed with it, `rule` on a fix of the style check, `reason` when the comment behind the edit gave one, `at` and `seq`. The `pr` record brings the description's list (the UA review's rewrites), from 1; `enReview` adds its rewrites to it; `answerComments` and `styleCheck` bring their summary comment's list. One PR numbers on: a step that may post a list carries `nextEdit`, and the brief says the list starts there. `resync` records the EN side of the items it re-synced. When the PR has a list, an owner's comment or review that starts with a number is a reply by number (`lib/edits.mjs`, no AI): `N — поверни` (or another restore word: `верни`, `як було`, `назад`, `скасуй`, `undo`, `revert`, `restore`), `N — "текст"` (one quoted text and nothing else: put in verbatim; `«…»` and `“…”` too), `N — <опис>` (a description to apply); a list bullet (`-`, `*`, `•`) may come before the number, and a separator must follow it (a dash, a colon, a dot that is no decimal point, a bracket; a bare space is none, so «5 хвилин тому…» is no item); `;` and line ends separate the items, never inside a quote (nested «…«…»…» quotes count by depth); a line with no number goes on the item before it only when that item is a description, else it is a word of the whole reply (`rest`, shown in the brief as such), and so are the words before the first number; a quoted line (`> `) is left out. A word of assent (`ок`, `залиш`, …) keeps the item (`keep`); `не треба` and `не потрібно` may mean keep or undo, and are asked back. Asked back, never guessed, besides the cases above: items named together («2 і 3 — поверни»); a comment that reads as the owner's own numbered list (1., 2., … in order, descriptions only, no quote); a restore of an item whose block a later item changed again; an item the records of two cards sharing the PR give differently (a reply is read against every ledger of the PR, and `nextEdit` goes on from all of them). The brief tells the writer to ask back, not edit, when an item's words point at another place than its block, or the block doesn't read as the brief says. The `answerComments` step carries `replies`: each named item resolved against the PR's lists, a restore with the exact `before` to put back (and the EN `before` when the item has `en`), a verbatim with the text, a rewrite with the description, and `ask` with the reason for a number the PR doesn't have, one that two lists share, one named twice or with nothing to do. The brief spells each out; items not named are not in it. A PR with no list yet takes a numbered comment as an ordinary instruction. An owner's review comment with a `suggestion` block is in `suggestions`: the block, to put in verbatim, and the words outside it; two blocks in one comment are asked back (`several`). The forge gives a comment's last line only, so the brief says to match a block of several lines by content, and ask back if that isn't certain.

**The style check of a person's edits.** A person's edit is checked against the style guide before the text is final (`context/ticket-flow.md`, "The style check of a person's edits"). After the comments are applied, `answerComments` does it over the UA blocks they changed: its brief says so, says that a plain comment quoting a page's sentence with words removed or changed is that sentence's replacement, and that a block a reply restores or keeps stays out. Hand commits get a step of their own, `styleCheck --pr <id>` (the writer, with the PR's worktree), carrying `commits` (each `sha` with the UA `pages` it changed, oldest first) and `nextEdit`. The rule takes it per PR after the new comments (row 11) and before the approved-half move and the chain, only while the PR is in the owner's queue (`finalReview`); at an earlier stage the commits wait for the queue. A person's move is approval: at `translation`, the unread commits get a scripted `styleCheck` with `skip` (no session, no move back): its record lists them as seen (`skipped: "moved"` in `styleChecked`), with the note "style check skipped: the card was moved on" in the run log, the step's result and the progress file. A hand commit counts when it is not in `styleChecked`, comes after the last ready head (`commitsBetween`; with no ready head, every one), was written at or after `styleCheck.since` when that is set (the author date of `commitDates`; a commit with no date here is noted and waits), was committed at least 10 minutes ago (`GRACE_MS`, in the queue only; a younger one is noted and waits, so the owner's push and then move finds no check running), and its own diff (`<sha>^..<sha>`, `changedUnder` with the PR's base) changed a UA page: so an id-only change, an EN-only commit and a merge of the base (the forge's "Update branch") start none. A check that was running when the owner moved the card keeps its fixes: the chain goes on with them, and its record, finding the card out of the final review status, notes in the log and its `warnings` that the fixes landed after the move, are on the summary's numbered list and can be undone by number. The step carries `fixes`, the style items already on the PR's lists for the commits' pages, so the brief can say that a hand edit putting one's «було» back is the owner undoing it, and the block is left out. Its record lists every sha it read, fixed or not, so the same head, or the head after its own fix (a pipeline commit), starts no second check. A commit git here can't diff, or a ready head it can't compare, is noted and left for a later check.

**The trigger word.** With `forge.triggerWords` set, the comments `answerComments` takes are sorted by who wrote them (`lib/world.mjs`, `sortComments`): the owner's only with the word (`helper: …`, the word taken off), or as a line comment of a review whose text has it; an expert's (a reviewer the targets name, or one requested on the PR) always in their own comments and reviews and in the threads an expert opened. A reply in anyone else's thread, the pipeline's (its first comment in `posted`, with the header, or of a review the pipeline posted) or the owner's, is for the pipeline only when it is the owner's with the word: anyone else's there, an expert the owner tagged included, starts nothing (decision 3). Those, and anyone else's comment, go to the PR's `others`: no step, and a line in the progress file with the link, until it was handed on: its id in `handled` (a session took it with the owner's worded comment that pointed at it). A later worded comment, in its thread or elsewhere, hands nothing on by itself (a forge thread is flat). An expert opened a thread when its first comment is the expert's and no reply: a thread whose first comment was deleted starts with a reply and is no one's. Logins compare case-blind. The owner's comment without the word is talk between people. The `answerComments` step carries `take`: each comment it takes, its id, who wrote it, its text with the word cut off and, for a reply in a thread, the thread's earlier comments (`context`: the thread's first comment and the last 7 before it, each `{ by: 'pipeline' | 'owner' | 'other', author, text }`, the owner's with the word cut off, cut at 400 characters); the brief lists them and says every other new comment is for people, not acted on and not recorded in `handled`, except one the owner's worded comment hands on, which the session acts on and records. A "Quote reply" starts with the quoted lines: the word is read on the first line after them. The same sort holds for the start rule (`lib/quiet.mjs`). With no words set, every person's comment is taken, as before, and the step carries no `take`.

**Review rounds** (`forge.reviewRounds`; `context/ticket-flow.md`, "Review rounds"). A round is two commits and one review: the edits the comments asked for, then the style fixes, then one review with a line comment under each substantive edit (`forge review-on-lines --outside-in-body`: an edit outside the diff goes in the review's text with its `path:line`). The first round is the `pr` stage (the draft and the UA review); then each `answerComments` and `styleCheck`, and `enReview` over the EN lines. A reply in the thread of an item's line comment is a reply to that item (its `commentId`), in the same words as the reply by number (`N — поверни` without the number); a restore may give its reason after it (`поверни, бо …`). The brief lists such replies (`threadReplies`) and the owner's replies in the places' threads (`placeReplies`), only with review rounds: without them a reply in a thread is an ordinary comment, as before. The EN round names the translation commit (role `translation`, one the PR's recorded commits hold) and its style commit. After each step the runner follows the rounds (`lib/pr-rounds.mjs`, no model), for each PR whose ledger changed:

- a place newly `confirmed` or `deleted` gets its thread resolved (`forge resolve-thread`, only a thread the pipeline started: the id in `posted`, the author `forge.self`, the body with `commentHeader`);
- once a new round has its review, the summary comments the pipeline posted after the PR's rounds began and before that review are deleted (`forge delete-comment`, the same three checks); one already gone is a warning. A summary from before the PR's first round (a PR opened before the switch: its numbered lists and open questions) is never removed. A submitted review can't be deleted on the forge, so a round's review stays;
- the description's sections (questions, places, rounds) are written again between their markers (`<!-- ticket-flow:<name> -->` … `<!-- /ticket-flow:<name> -->`, from the host's PR template) from the ledger, with `forge.reviewRounds.labels`; the rest of the description is never touched. A section a person edited since (its text no longer matches the hash in its opening marker) is kept, with a warning. A description with none of the markers (a PR opened before the switch) gets the three sections at its end at the PR's first round, under `questionsTitle` and `placesTitle`; later, one a person took them all out of is left as it is.

A failure of any of these is a warning in the run log (`kind: rounds`), and the step stands; it is not retried. The description is read and then written: a person's edit between the two is lost (a known race, left as it is). The resolve and delete commands are the runner's only: the role hook refuses them in a session.

**Reactions as status** (`forge.reactions`, `tracker.reactions`; `lib/reactions.mjs`, no model). Around each session the runner marks the comments it takes, so the owner sees what was taken and how it ended. The state stays in the ledger (the handled ids and the version seen), never in a reaction: the marks are set again at each pickup, and the owner may take any of them off.

- **Picked up:** 👀 on each comment, also when the owner took it off before, and the pipeline's earlier result on it (🚀 or 😕, ✅ or ❓) taken off. A comment is picked up when it is new, or when it was edited since it was handled (a new version is a new round).
- **The step done:** 👀 off and 🚀 (✅ on the card) on each comment that ended applied; 😕 (❓) on one the session asked back about or couldn't do.
- **The step failed:** 😕 (❓) on each. A step that waits (a busy lock) or whose branch moved keeps 👀; its next pickup sets the marks again.
- **A mark taken off with no edit starts nothing:** nothing reads the reactions.

Which comments: on the PR, those of `answerComments`'s `take` (the owner's with the trigger word and the experts', so only with `forge.triggerWords`): conversation comments, line comments and a submitted review's text, each by its own kind. On the card, the answers the `answers` step reads: the card's comments after its earliest open question (of the step's PR, for one asked during the chain) that the pipeline didn't post (not in `posted.card`, not starting with `commentHeader`), and only the owner's when `tracker.owner` is set.

How a PR comment ended comes from the record alone: 😕 when the record left it out of `handled`; else the session's own word, the entry's `result` (`applied` 🚀, `asked` 😕; another value is refused). An entry with no `result` is read from the rest of the record: 😕 when an item of its reply by number (or of its reply in an item's thread) is one the rule asks back, or a new question of the record's names it by `n`; when the entry has no `commit` and the record asked something (a new question, a description question in `asked`, a question on the card for the PR, `questions --pr`); or, for a reviewer's comment, when it has no `commit` (a suggestion or a note for the owner). Every other handled comment is 🚀. On the card, ✅ once `answers` is done.

The runner sets the marks through the forge's and the tracker's `markComment`, which have no CLI command, so a role never sets one. Only the pipeline login's own reactions of the three marks are taken off, never another person's; the pipeline acts from the owner's login, so a 🚀 the owner put by hand on a comment it picks up goes too. The owner's own hand-set 👀, 🚀 or 😕 on a comment the pipeline picks up are taken off too: they carry the pipeline's login. A reaction call that fails, or a ledger that can't be read, is a warning in the run log (`kind: reactions`, `outcome: warning`, not in the report's failures), and the step and what follows it (the labels, the rounds) go on as they would. The settings refuse `forge.reactions` without `forge.triggerWords` or `forge.self`: it would mark nothing.

**A PR closed as won't merge** (`forge.wontMergeLabel`, D-155). A ticket can have one PR per doc repo, and the owner may close one of them on purpose (an edit the card should not have asked for, say). Closed unmerged with no label, it puts the whole ticket outside the flow (rule row 5): the other PRs stop too, until the card leaves the flow. Closed with the label, it is *dropped*: it leaves the ticket, and the other PRs go on. What makes a PR dropped is read from the forge at every check (`readPrs`): closed, not merged, the label on. Reopened, or with the label taken off, it is not dropped any more: open, it is in the flow again as any open PR; closed with no label, row 5 as before. While it is dropped:

- the rule reads the ticket as if it had only its other PRs: row 5 skips it, row 4 closes the ticket once every other PR is merged, row 6 follows a person's move for the others, and no step of any kind is made for it (moves and labels, the chain, ready for merge, re-sync, answers, style checks, `untranslated`, `idSync`, the base merge, a stage left running on it). The card stands where the least advanced other PR is. Every PR of the ticket dropped: `outside`, with the note `every PR of the ticket was closed as «<label>» (…): nothing is left for the pipeline; move the card out of the flow or archive it`;
- every step of the ticket names it (`dropped`, the PR ids; a group's step, the PRs dropped in any of its tickets), and the runner and the records leave it alone: no label, comment, review request, description, thread, worktree or branch, and the card's status from the other PRs only. The forge wins over what the status saw: right before each step acts, the runner reads the state of every PR of the step's tickets and of their group once more (only with the label set), acts on that read, and hands the dropped ids to the `follow` and `move --pr` records (`result.dropped`), so its labels and the records agree; a step on a PR dropped since the status runs nothing (`moved`), and the status is read again. A `follow` or `move --pr` recorded by hand, with no list, reads the forge itself; `close` always reads it;
- `status` gives `prs[].dropped` (`{ label }`) and the note `<repo>#<n> was closed as «<label>»: the ticket goes on without it`; the close keeps `prs[].dropped` (`{ at, label }`) on the ledger, and its stage as it was;
- it holds no page and counts for no limit; after the close it keeps no work file;
- the report lists it under "PRs closed as «<label>»" and in no list that waits for the owner (ready for merge, places, the check label, the expert's call); the progress file shows it as dropped, with no gate and no "your turn" notification (from the last status, kept in `progress.json`).

The pipeline never puts the label on, takes it off, or makes it: the owner does, by hand, on each repo. The forge module refuses to add or remove it.

**Commits made on the forge.** A suggestion accepted in the PR, an image uploaded through the web or an edit made in the browser reaches no clone by itself. So `status`, once it has read the forge, fetches each open PR's branch whose head the target clone doesn't have, with its base: one `git fetch -q --no-tags --no-write-fetch-head origin +refs/heads/<base>:refs/remotes/origin/<base> +refs/heads/<branch>:refs/remotes/origin/<branch>` per clone. Which tickets: every ticket with an open PR, or only those the check names when it names some (a run's status after a step names that step's tickets). How often: at most once per clone and branch in a check, where a runner run is one check (a later head on the same branch waits for the next run), and none when the clone has the head. It writes only those remote-tracking refs, as the worktree's own fetch does: never a local branch, the checkout, its files or a tag. The rule then reads the commit as it reads one pushed from the clone: a hand commit, so after ready for merge a UA change goes back to the owner's queue, and one that left UA alone gets the pack again if it changed an image, then ready (see "After ready for merge"). Only the PR's own changes count: a page or an image the base brought in (the forge's "Update branch", a merge of the base) is not the PR's change when neither the PR's diff against its base at the earlier head nor the one at the new head holds it (each against its merge-base with `origin/<base>`). So such a merge keeps a ready PR ready, and makes no chain stage stale. A fetch that fails (offline, a password asked: it never waits for one, and it gives up after 30 seconds) leaves the clone as it was, and the head is noted as not fetched here. The dry run's `status` fetches too.

**A clone off its base.** A step with no worktree (the start, the plan, the answers, the video import) never reads pages in the owner's clone, whose working tree may be on another branch than the base, at a detached HEAD (the owner's branch work, the hub's too when the hub is a target), or behind `origin/<base>` (the owner merges on the forge, so a clone is behind after each merge). Before its session, the runner fetches the base into `origin/<base>` (`--no-tags --no-write-fetch-head`, 30 seconds at most) in the clone of each target its tickets name (none while they name none), and gives the session a **read checkout** of it: a detached worktree of the clone at `origin/<base>`, made and moved with the clone's hooks off (`-c core.hooksPath=/dev/null`). It lives beside the ticket worktrees, outside every repo: `<clone's parent>/.worktrees/<repo>/.read/<target id>` (no branch name starts with a dot, so no ticket worktree is ever there). Not under the state folder: a hub that is its own target and keeps its state under a `.sources/` folder (`docs/.sources/…`) has the write rule `Edit(<hub>/**/.sources/**)`, which would match every page of a checkout kept there. For the same reason a read checkout whose path has a `.sources/` folder in it (a clone kept under one) is refused, and the session falls back as below. It is made once and kept: each later step re-points it with `git checkout --detach` (one with changes to tracked files, or one that won't move, is removed with `git worktree remove --force` and added again). The session gets it as `--add-dir`, with the role's git reads spelled for it too, and the brief names it, with the commit, as the place to work: every skill gets the read checkout's path, its section folder or its repo top, never the clone's.

**The `.sources/` folders of a read checkout.** A section's skills (section-readiness, app-explorer, section-planner, convert-sme-input) read and write their evidence in the section's `.sources/` folder. Most of it is git-ignored, so a checkout doesn't have it, and some hosts track a few files there (a `README.md`, an interview) beside the owner's untracked notes. So a read checkout is sparse: every `.sources/` folder, tracked or not, is left out of it (the patterns `/*` and `!.sources/` in its own `info/sparse-checkout`, which git keeps per worktree; `core.sparseCheckout`, `core.sparseCheckoutCone=false` and `sparse.expectFilesOutsideOfPatterns` are set only on the runner's own git commands, so nothing is written to the clone's config, and a session's plain `git status` there still skips those files by their index bits; `git show HEAD:<path>` still reads the committed ones). One made before it was sparse is made again. Each time the runner makes or moves a read checkout, it links each `.sources/` folder of the clone into it at the same path, so the tracked and the untracked files are there as the clone has them, and removes a link whose folder is gone. A skill run on the read checkout's section reads the clone's notes and writes its report into the clone. A section with no `.sources/` yet gets a real folder the first time a skill writes there: when the session ends, the runner moves it into the clone at the same path (into a folder the clone made meanwhile file by file: the clone's file stays, the session's goes beside it as `<name>.from-read-checkout`), puts a link in its place and says so in the run log (`kind: readCheckout`). The same happens before any re-point. Neither happens while another session may still be writing there; the next one made with none running does it. Never linked or moved: a `.sources/` folder that holds the state folder (a hub's own, when the hub is a target), anything that would land in the state folder or outside the clone, and a folder inside another checkout (a clone kept inside the hub). Git never writes through a link: a re-point to a commit that changes a tracked file under `.sources/` leaves the clone's copy as it is. Everything else in a read checkout is read-only to the session: the only write rule there is `Edit(<read checkout>/**/.sources/**)`, and the hook refuses a `mkdir` there, and a toolkit script run from a read checkout or given a path in one (so `screenshot-locales` never stages or promotes screenshots there, and `ui-labels` never patches its pages), except under a `.sources/` folder. The plan's Playwright spec stays the clone's: `screenshot-tests/_plan-<key>-*.spec.ts`, run from the clone, which stays among the session's folders.

**A read checkout that waits, or can't be made.** While another session that may read it runs (a lock of a stage with no worktree, or a lock that names no stage, such as a hand run's), a read checkout at another commit, or with changes to tracked files, is left as it is, and this session falls back as below; a session on a worktree stage doesn't hold it. Each model step puts its own stage on its group's lock before anything else, so a chain that goes on in one lock from a worktree stage to one with none is seen as what it runs now. When one can't be made (that, a folder in its place that isn't one, no `origin/<base>` fetched, a target id that is no plain name), the run log says so (`kind: readCheckout`) and the session reads that clone as it stands: the brief names the clone, why there is no read checkout, its branch or how far behind it is, and says to read pages with `git -C <clone> show origin/<base>:<path>`, never its working tree. A folder left by a clone that moved (`targets[].path` changed) is still the old clone's worktree: the reason names the command that clears it, `git -C <old clone> worktree remove --force <read checkout>`, and the next step makes it again. None of this holds the step.

**What a read checkout never touches.** The runner never checks out, pulls or resets a clone: only the clone's list of worktrees changes (the one exception is the watcher's, not the runner's: the hub, when it is a target clone too, is fast-forwarded on its default branch before a full check, only when clean, see "The hub after a merge"), as for the ticket worktrees, and the `.sources/` folders a session writes, as it did before there were read checkouts. The read checkouts are the runner's, not a ticket's: the close step removes only the ticket's own worktrees, keeps a read checkout whole even inside a folder a ledger recorded, and `git worktree prune` keeps one whose folder is there (one whose folder is gone is pruned, and made again at the next step). When the hub is itself a target, its state folder must be git-ignored in the hub (as `.flow/` is in the examples, or `docs/**/.sources/` for a state under `docs/.sources/`): a session writes there, and the hub's own read checkout would otherwise see it as part of the site. A hub's read checkout is `<hub's parent>/.worktrees/<hub>/.read/<target id>`, beside its ticket worktrees.

**A stuck worktree.** A worktree the runner can't bring up to date (uncommitted changes to tracked files, or commits the branch never had, often after the branch was rewritten) stops its stage before any session, and one with work no remote has stays after the close. To clear it: save what you need (push it with the brief's command, or copy the files), then `git -C <clone> worktree remove --force <worktree>`. The runner makes a fresh one at the next step.

**A failed step.** A failed stage stays the ticket's next step, and the session's own comments, labels, moves and pushes show up as events at the next check. So a failed step runs again only:

- after a person acts on the ticket later than the failure: a comment on the card that isn't in `posted`, a comment or review on a PR (a bot's counts neither here nor for `answerComments`: a preview notice or a CI summary asks nothing of the pipeline), a commit on a branch that isn't in `pipelineCommits`, or a move of the card (there and back counts: the card's own moves show it);
- after `ticket-state set retry <key>` or `set retry all`;
- or once at the next morning run (a manual run tries it too).

**A failed start** counts the same. A start whose card is still in the ready status didn't happen: the ticket stays `ready` and counts for no limit; its group waits (the reason says so), holds no slot and holds back no other group, and the next morning run (or a manual run, or a person's action) gives it its one more try. A start whose card is in work (the session moved it, then failed) is `planning` and counts; the start goes on in the finishing order, as it was started: the runner recorded its origin before the session. With no start recorded, a card a person moved into work is a hand start: `manual`, outside every limit; so is a card a person moved into work after a failed start left it in the ready status. **A stuck worktree** (or one that can't be made) counts the same too: no session runs, and its `runs` entry (`session: null`, no `start`) is read as a failed session's, once, and counts toward no session cap or cost. A start has no worktree, so the two never fall on one step. **A failed build** (the runner's own, "The site build") counts the same: its run has a `start` and `wallMs` but `script: true` and no session, so it counts toward no session cap or cost, and the gate says it failed in the runner's own build.

Right after a failed session the runner reads the ticket once more and keeps that mark in the session's `runs` entry (`after`: the card's list, its last move and its comments, each PR's head, hand commits and unhandled comments), with `failures`, the failed sessions in a row. What the session wrote without recording it is in the mark, so it never counts as a person's action. Two failed sessions of a step with no person's action between them (the retry up the ladder counts) hold the ticket for the owner: `status` gives it no next step (so a manual run does nothing with it either) and a gate (`held`); the report lists it under "Waiting for you" and once under "Failures"; one urgent notification. A first failure only waits: `next.waits` says for what, and the watcher doesn't hand the ticket on.

**The daily session cap.** Whatever the cause of a loop (a session that records its stage but leaves a fresh event behind each time, say), a ticket has at most `limits.sessionsPerStageDay` model sessions of one stage (and PR) a day. At the cap, `status` holds it for the owner until the next day (`capped`, an owner gate), the watcher sends one urgent notification and writes one line to the run log, the report's failures. `set retry <key>` lifts it.

**The guard.** A scheduled start or model step runs only while the week's use is below the day's allowance (`/usage` read before and after each session). `claude -p /usage` gives no reading now and then while the sign-in is fine, so one reading is up to 3 runs, 10 s apart (the runner and the watcher's skill jobs alike). No reading after the 3, no scheduled start: the guard's reason is `no usage reading after 3 tries: no scheduled start`. A manual run is not guarded.

**The limits.** Only tickets a scheduled run started, in `mode pipeline`, count: `inProgress` (planning, writing) and `waiting` (questions, plan gate, video gate, the owner's block, rework). The owner's queue counts for neither: with no limit on `open`, tickets can pile up there. A group starts only if `inProgress` + its size ≤ the ceiling (a group larger than the ceiling only when nothing is in progress), `waiting` is below its limit, and its estimate plus what the tickets in work still need fits what is left today. With no estimate for a size yet, one ticket at a time. With `limits.open` set, a group starts only if the open tickets + its size ≤ it (a larger group only when none is open). Open: a scheduled run started it, and it is from planning to the final review, In translation and ready for merge included; not paused, not outside the flow, not merged or closed; a locked ticket counts as what it is doing, and one locked at a scheduled start is open even while its card is still in the ready status, so two scheduled runs at once can't pass the limit. The reason a group didn't start names the tickets that hold the slots (`wip.openKeys`, and the groups the same calculation starts). In `priority` order a group held back by these holds back every lower priority; within a level, a younger group that fits may start. In `easiest` order a group held back by them holds back every group after it, equally easy ones too. A group held back only by its lock, a relation to a ticket in work or starting now, or its failed start holds back no other group.

**Overlap and together.** `related` is overlap, and holds a ready ticket back while the other is in work or starting in the same run: triage named the other, in one repo (`#1221` and `1221` are one ticket); the card's text names its number; or they have a page in common, a page being its repo and path without the `— block` suffix (a path with no repo, or a bare file name, matches nothing). Only `triage.together`, the triage's judgement, joins tickets into one group, in either direction and within one repo.

**The pages of a ticket in work** (`workPages` in `lib/limits.mjs`) are what its PRs change, where it has them: the triage's page list is a guess made before the plan. Per repo:

- **An open PR with its file list** (`files`, read in the same `prState` query `status` already makes, so no forge call is added): the files that PR changes; the triage's pages for that repo no longer count.
- **A PR with no number yet** (a branch the plan or the write named, no PR opened): the triage's pages of that repo.
- **A PR whose list the forge didn't give** (a read that failed), **gave only in part** (more than 100 files, `filesTruncated`) **or that renames a file** (`filesRenamed`: the list has the new path only): the triage's pages of that repo beside the files it read.
- **A PR closed unmerged** holds its files as an open one does: its branch still has the edits, and it may be opened again. Its ticket is outside the flow, not in work, so it counts for no limit, and only its pages hold a ready ticket back (`related to 1157, its PR closed unmerged: …`), not its relations. Only while its card is in a working status of the flow (`inProgress`, `blocked`, `smeReview`, `finalReview`, `translation`), where someone may redo it. To release its pages, the owner moves the card out of them (to done, out of scope, the drafts or the ready status) or archives it.
- **A PR closed as won't merge** (`forge.wontMergeLabel`): none. It is out of the ticket; a ticket whose PRs are all closed so is outside the flow and holds nothing either, whatever its card's status.
- **A merged PR:** none, the change is on the base.
- **A repo of the triage's with no PR:** its triage pages count until the ticket has opened its PRs (its `pr` stage done), and stop counting after: a ticket that opened its PRs with none in that repo changes nothing there. While a session runs on the ticket (its group's lock is live: a review round may edit a repo it has no PR in yet) they count again.

A ready ticket keeps its triage's pages. Two pages are one when they have one repo and one page id (`pageRef`, `samePage`): the path from the content root, without the root (a target's `uaRoot`, or `i18n/<locale>/<docs plugin folder>/current/` for every locale's translation), the extension (`.md`, `.mdx`), the page's own file in its folder (`x/y/y.md`, `x/y/index.md`), a `#heading`, and `.assets/…` (a screenshot is its page's); a `_category_.json` is its folder's, and `/x/y` (the URL form) is `x/y`. A triage guess that ends in `/` (a new page in a folder) is a folder, matching every page under it (`docs/` alone, the whole root); one with no `/` (`y.md`) matches a page of that name anywhere in the repo. Two docs plugins whose pages share a path from their roots read as one page: a ticket may wait that needn't, none starts that shouldn't.

When a page holds a group back, the reason names it and where it came from: `related to 1157, still in work: a page 1157's PR #61 changes (<repo> <path>)`, `… a page 1157's triage names, no PR yet (…)`, `…, its PR's files not read (…)`, `…, its PR renames a file (…)` or `…, a session on it now (…)`; two ready tickets on one page give `related to 705, starting now: a page 705's triage names (…)`. A relation, `together` or a number in the card's text decides first, with the reason as before (`related to 300, still in work`). The report ("Starting and finishing") and the progress file show the reason as it is.

## Findings outside the ticket

A PR's open questions hold what the ticket's own pages depend on, and nothing else (TASK-050). A problem a session comes across that its ticket doesn't change (another page, a block of a changed page that the ticket's change leaves alone, UI the ticket doesn't cover, an app bug) goes in its record's `sideFindings`, and a note for the owner that asks nothing goes there too (`kind: "note"`): the role's rules and the brief of the writer's, the reviewer's and the translator's stages say so (`lib/findings.mjs`, `findingLines`). After each step, a session's or its own, the runner routes each finding of the step's tickets that it hasn't routed yet, with no model (`followFindings`), and the run log has a line for each (`kind: findings`):

- **A note**: a line of the report, nothing on the tracker.
- **A finding an open card holds already** is linked, not filed again. The card is the one the session named (`card`: its own match, which only a model can make between two wordings of one problem), else the card filed or linked for an earlier finding with the same **fingerprint**: the same kind, for a `page` finding the same repo and page (the path compared without a leading `./` and in any case), and the same title once case, punctuation and spacing are set aside. Either is read first (`find-cards --link`): it holds the finding unless it is archived, in `done`, or the ticket's own card. A card out of the docs' scope still holds it (an app bug triaged away is known and decided: found again, it is linked, not raised again), and so does one on a watched board or in a never-read status. One that doesn't is said in the line's `notes`, and the finding is filed as new; so is one whose `card` is no card the tracker reads. Linked: the template's `onTicket` comment on the ticket's card, with the card's link, and its `onExisting` comment on that card, naming the ticket, when it is on the board in a status the settings read (the module writes on no other board, and the pipeline never on a card it keeps unread).
- **Anything else** is a new card in the `intake` status (`create-card`), named and described from the template (`desc` names the ticket's card, and the PR it came from), and the `onTicket` comment links it from the ticket's card. Triage takes it as any card; when the work on it meets the same finding again, the fingerprint links it rather than filing a third.
- **With no template** (`tracker.findingCard` unset) the runner writes nothing on the tracker: the report lists the finding as not filed, with the open card that holds it when one does.

`<state>/findings.jsonl` keeps one line per finding routed (`ticket`, `id`, `fp`, `kind`, `title`, `outcome`: `filed`, `linked`, `unfiled` or `noted`; the `card`, `by` how it was matched, `notes`), written by the runner alone: it is what makes each finding routed once, and the index the fingerprint is matched against. The line is written right after the card is made or chosen, before the comments: a comment that fails is a warning in the run log, never a second card. Each comment the runner posts goes into `posted.card` of the ticket whose card it is on (another ticket's only while no other run holds that ticket's lock), as a stage record's `posted` does for a session's comments, so no rule reads it as a person's (the failed-step rule's "a person commented on the card", the answers on the card). A tracker call that fails before it leaves the finding unrouted, a failure in the run log, and the ticket's next step tries it again. A role never creates a card: `tracker.mjs create-card` is the runner's alone in a role session (`lib/role-hook.mjs`, and the session's denied rules), like the forge's label commands. The brief of those stages lists the ticket's own findings so far, not to be given again, and the newest cards filed for other tickets' findings, for the session's own match.

The report's «Findings outside the tickets» lists the day's lines: each card filed (its link), each finding linked (the card and how it matched), each one not filed for want of a template (its text), and the notes.

## The video gate

A ticket whose text doesn't cover its video and that has no team transcript goes through the video gate (TASK-055, D-062, D-063, D-070). The writer's `videoGate` session cuts the video's sound into parts of at most `video.partMinutes` (`scripts/video-parts/`) and records them with each part's start and its transcript's expected path. From there the runner works with no model, step by step, each a run of its own:

1. **The automatic try** (`videoTry`), only with both `video.transcriber` and `video.browserProfile` set. The adapter (`scripts/transcriber/`) opens one browser in the persistent profile, where the owner signed in once by hand; it stores no password and prints no session value. Every role is denied `Read` and `Edit` on the profile and its lock, and the role hook refuses a command line that names either; a Playwright spec a writer session writes and runs could still open it by its path (the hook can't read a spec), so the profile is signed in with an account of its own for the service (scripts/transcriber/README.md). It uploads the parts not yet tried, each once and under `<key>-<part file name>`, at most what the account has left today: `partsPerDay` across every ticket, the parts an older gate still waits to upload first, counted once the browser holds the profile (so two runs never count the same uploads). Each upload and each look is recorded as it ends, so a run that dies part way never uploads a part twice. Uploading and fetching are separate runs: a later check looks for each uploaded part's transcript every `fetchMinutes` (the watcher hands the ticket on for it, with nothing on the board), and saves the plain-text export with timestamps at the part's `transcript` path. A look that finds the transcript still in work is a look (`checks`), not a try. A browser profile in use by another run is no failure: the busy try is recorded (`busySince`), and a later check tries; the profile opening for the ticket clears it (`opened`), even when the step then has nothing to do; in use for longer than `transcriptHours` of the start hours since the first busy try (the night outside them doesn't count), it falls back to the person with that reason. The try opens a browser only inside `limits.startHours` (10-22 by default: no window in the early morning, D-109); outside them the gate waits, and once they begin the watcher hands on a ticket with a part the day still allows to upload, as it does one with a look due.
2. **The fallback** (`videoBlock`), on the first failure, with no retry: a sign-in wall, a captcha or bot check, the day's limit, an unexpected page (the reason names what wasn't there), a browser that doesn't start, or no transcript `transcriptHours` after the upload. The step stops at the failure (the parts after it stay untried), the card goes to Blocked with the gate comment, and the report lists the parts to upload by hand (at most `partsPerDay`), each with its start and the name to save its transcript under, and the reason. A transcript dropped there by hand counts the same as a fetched one. With the try off, the gate goes straight here.
3. **The frame sweep** (`videoExtract`), once every part has its transcript, Blocked or not, whatever the video settings (transcripts a person dropped in too). First a preflight: the venv's Python, `tesseract` and `ffmpeg` on the runner's PATH. Without one, the sweep is skipped, not failed (`skipped` in the record, `extractSkipped` in the ledger), and the import goes on as before the sweep: `convert-sme-input` on the parts' transcripts at their offsets, with no frames, and the brief says why. The runner runs `scripts/sme-video-context/sme_video_context.py` itself, with the venv of `extract-sme-screenshots` (`~/.cache/doc-writer-toolkit/sme-video-venv/bin/python`; no role may run Python, `ffmpeg` or `tesseract`): the full pass on the video with every part's transcript as `--transcript <file>@<start>` (whole seconds), so Whisper never runs and the merged transcript is in the video's time; then the frames it kept and the transcript's key frames are merged into `frames/<video file name>-frames/` next to the video, as the skill keeps them. The package stays whole next to the video, as `<video file name>-sme/` (a new folder each time). No shell, fixed arguments, each command under `extractMinutes`. It records each video's package, merged transcript, context and frames folder (work files `runDir` and `frames`). A sweep that fails or times out is skipped the same way as a failed preflight, with the output's tail as the reason and a run for its time: never a failure, so it never holds a ticket (the hand path's least of all), and the import goes on without frames. Only a refused record fails it.
4. **The import** (`videoImport`), the writer's session: its brief names the merged transcript, the frames folder and the parts' starts (or, after a skipped sweep, the parts' transcripts and starts, and no frames), and the session runs `convert-sme-input` on them (context/ticket-roles/writer.md), then moves the card back to In progress if it is in Blocked. It never runs a frame extraction itself: a frame that's missing is cited without a screenshot, or left as a `NEEDS CONFIRMATION` marker.

A card the owner moves out of Blocked before every part has its transcript goes on without the video (`answers` with `withoutVideo`), and the report says so. Whisper runs only on the owner's word, never in the gate.

## The import

`ticket-state import` turns a host's Markdown ledgers from before the JSON ones into JSON ledgers, once, at the switch. The Markdown has one `name: value` line per fact, appended as the ticket went on; a name may repeat (`stage`), and a per-repo name has three forms (`branch[R]: x`, `branch.R: x`, `branch: R=x`).

- Every line goes into the JSON as it is, with its number: `legacy.mapped` for a line that also filled a field (`to` names it), `legacy.fields` for the rest. The JSON holds the whole Markdown, so the Markdown can go.
- Fields it fills: the card and the original card (by URL), the group, the triage (`verdict`, `targets` by each target's `appLabel`, `size` through `--size`, `relations`, `pages`, `triaged_at`), and a PR entry per PR link with its branch. The old `stage` lines go into the log; the stages are the ones `handover` rebuilds.
- Then the tracker and the forge say where each ticket is. **Closed** (no PR open, and the card done, out of scope, archived or gone): `mode hand` with its close recorded. **Ready** (the card in the ready status, no PR, the last stage `triaged`): `mode pipeline`, a ready ticket a scheduled run may start, as a triaged ready card with no ledger already is. **Any other**: `mode hand`, the owner's until `handover`.
- The removal: a closed ticket's Markdown goes (to `cleanup.trashDir`, or deleted with `cleanup.mode: delete`) only after a check that the JSON rebuilds it byte for byte: every line once, in order, and the final newline. A Markdown that fails the check stays, with the reason. The morning run repeats the removal for tickets that closed since; it is the script's own step, never a session's command. A ticket that closed since the import, still `mode hand` and with nothing recorded into it, gets its close recorded first, as the import does for one closed already; a ticket handed over is left to the pipeline's own close.
- Run again, it imports a Markdown that changed since, if nothing was recorded into its JSON since; it never overwrites a ledger that didn't come from an import, or one recorded into since, and then keeps its Markdown.
- A Markdown with no card URL or no stage line is not a ledger (a README, a doc page in a mistyped `--from`): it is in `skipped`, no JSON is written for it, and the removal never moves it.
- `imported[]` gives each ticket's `state` (`closed`, `ready`, `open`), `mode`, `stage`, `lastStage`, PRs, triage, how many lines filled a field and how many were kept as they are, and `misses`: what it couldn't map (a size word with no `--size`, a target label no target has, a branch with no PR link, an unknown stage word). Then `skipped`, `removed` and `kept`, each with its reason, and `failed`: the files whose ticket the removal couldn't look up, with the error.

**The report**, `<state>/reports/<date>.md`, written with no model call: the mode, WIP (with `limits.open`, the open tickets by name) and allowance; what waits for the owner; per PR in the owner's queue, whether an expert review is recommended and why; per PR in the expert's review with no review or comment from its experts for `schedule.expertQuietDays` working days (from its entry or their last one), a line with `forge.reviewComment`, when set, for the owner to send them; PRs with places; with `forge.wontMergeLabel`, the PRs closed with it (dropped from their tickets, in no other list); PRs labelled with the check label; videos waiting for transcripts (the parts to upload today); ready for merge (and PRs in the owner's queue while the card stands with a slower PR); with `forge.translatedLabel`, the PRs of the tickets closed that day that were merged without it, with their links (their translations may be behind the base); the cards left in each watched list; what finished and started, and why each other group didn't; mismatches and tickets in the owner's hands (a closed one left out); cards that are not tickets; the work files removed after the merge and the space freed; the findings outside the tickets routed that day ("Findings outside the tickets"); failures and guard stops; the day's cost (sessions only: the runner's build is none); today's steps by wall-clock time, each with its start, ticket, stage and outcome, the session's own count beside it when it is a minute or more shorter. Once a week it adds proposed changes to the roles (a role whose steps often needed the retry: the next model; many clean steps at high effort: medium), kept in `<state>/roles-proposal.json`; nothing changes on its own.

## Keeping a PR up to date with its base

With `forge.keepFresh` (D-113, D-127; off by default), each pipeline PR has its base merged in from ready for merge on, so the owner merges a branch that already holds what was merged before it, with CI run on that result:

- **When.** A PR at ready for merge whenever its base moves: the head lacks a commit of `origin/<base>` (the forge's `baseCommit`, the base branch's tip, fetched into the clone when it isn't there; `status` shows the count as `prs[].behind`). At the chain's end the PR is marked ready for merge first, and the merge follows at the next step; never at In translation, in the owner's queue (`finalReview`) or before: the owner edits the branch there (D-127). After every other row of the rule: a hand edit that changed UA sends the PR back to the owner's queue first, and new comments are answered first, on every path to ready for merge, so no merge and no `baseFix` session pushes under an answer. While CI on the runner's last merge still runs, or hasn't reported yet, a base that moved again is not merged again: once per CI run at most.
- **How.** `baseMerge`, the runner's own step with no model, like the build: in the PR's worktree, `git merge --no-edit --no-ff` of `origin/<base>` as the worktree fetched it (the message `Merge branch '<base>' into <branch>`), then `git push origin HEAD:refs/heads/<branch>`, never forced; never a rebase. The merge commit is recorded among the pipeline's commits (`prs[].pipelineCommits`), so it is never a hand edit, never a style check, and never a reason for the move back after ready for merge. A page of the PR's own that the base changed too counts as a UA change only when the PR's own change to it differs between the two heads (`lib/world.mjs`, `ownOnly`: its diff against the merge-base, with no context lines, compared by `git patch-id`): a block the base brought is the base's, already translated with it, and nothing is re-synced for it. `git patch-id` ignores whitespace, so an edit of the PR's own that changed only whitespace in such a page doesn't count either. The briefs of a re-sync and of a stale chain stage name the PR's own pages that changed and say to read only them (`git diff <since>..<head> -- <pages>`), since a merge in the range brings the base's whole diff. The merge commit is recorded among the pipeline's commits before the push (a `running` record), so a run that stops between the push and its record leaves nothing to read as a hand edit. The ready label comes off at the push.
- **CI again.** `readyForMerge` is recorded only once CI passed on the head, at every stage (the forge's `checks` of the head branch's tip, read only when their `commit` is the PR's `headCommit`: another commit's checks, or none, are never a pass). While a check runs, or for 10 minutes from when the head was first seen while none has reported (`CI_GRACE_MS`; the earliest record at that head, else the PR's last update on the forge), it waits, with a note. A head no check reported on after that, or one whose CI stayed pending (a required check that never started included) for over an hour (`CI_TIMEOUT_MS`), opens a gate to the owner, so a host with this setting needs CI on its PRs. A failed check is a mismatch naming it, and the ticket's gate says so: the PR stays out of ready for merge, its label off, until a later head passes (a person's commit, which the rule reads as any hand edit after ready for merge). Green: `readyForMerge` for the new head, and the ready label back on.
- **A conflict.** The merge is aborted (`git merge --abort`), the worktree checked clean at its head, nothing pushed, and `baseMerge` recorded with the `conflict` (`base`, `files`). The rule's next step is `baseFix`, a session: the writer, or the translator when no conflicting file is under a UA root (EN and further-locale pages, and any other file: a config or a code file in the conflict goes to the translator too). Before it the runner starts the merge again with `--no-commit`, the conflicts left in the files; the session resolves them and adds the files, and may not commit, merge or push (no push rule, those three denied in the worktree's spelling, and the hook refuses a commit and a push on this stage). After it the runner commits the merge once no file is left unmerged, nothing is changed but not added, nothing is staged beyond what the merge staged by itself and the conflicting files, and no conflict marker is staged (`git diff --cached --check --no-textconv`, and the four markers read from the staged diff, diff3's `|||||||` included), pushes it and records `baseMerge` with its commit; otherwise it aborts the merge, back at the head, and the stage failed. A push that fails puts the conflict's record back, so the next step is `baseFix` again and its failures count. A resolution that changed a UA block of the PR's own sends the ready PR back to the owner's queue (D-112), and the owner's move to In translation then re-syncs it, never the chain again; one in EN only goes on to `readyForMerge` once CI passed. A base that moved again since the conflict is merged again first. No session gets a conflict no edit resolves: one side deleted or renamed a file the other changed (`git status` `DU`, `UD`, `AU`, `UA`, `DD`), which needs a delete or a move the session may not make; the conflict is recorded with `unresolvable` (`{ path, kind }`) and the ticket's gate asks the owner to merge the base in. Nor does a PR whose conflicts reach `CONFLICT_LIMIT` (2), counted once per head and base tip in `prs[].baseConflicts` and never reset by a merge that went through: the second goes to the owner the same way.
- **When it fails.** A merge or a push that fails leaves the worktree at its head and a run with no session (`script`), so the failed-step rules apply as for the build: it waits for a person, then holds. What a failed push was is read from the heads, never from git's error text (a protected branch, a pre-receive hook, a token without the rights and a person's push all print "rejected"): origin's head at the merge commit is a push that landed; origin's head moved off the step's head is `moved` (someone pushed meanwhile; the status is read again, nothing counted); anything else is the push's failure.
- **The watcher.** Each full check looks at every ticket with a PR at ready for merge, or at In translation with its chain done, whatever the events: a merge into the base (another PR's, which maps to no ticket) and a CI that finished are seen within `schedule.watchMinutes`. The forge check doesn't read them.
- **The report** lists the day's merges of the base and their conflicts, and each open PR still behind its base ("Kept up to date with the base"). A PR at ready for merge that is behind its base, has a conflict, or whose CI runs or failed is never called ready meanwhile: `status` gives why on its view (`prs[].notReady`), and the report's "Ready for merge" says "not ready for merge yet" with it. The progress file reads the ledgers alone, so it can't see `behind` or CI: it opens no ready-for-merge gate (no "your turn" notification) for a PR with a conflict recorded at its ready head, or with a merge of the base pushed after its last ready record, until the PR is marked ready for its new head; a PR that is only behind still shows its gate until the runner's merge, at the next check.
- **A run that stopped** in the middle of a `baseFix` leaves the merge in progress in the worktree: the next `ensureWorktree` aborts it, with a note, so the worktree isn't stuck. One that stopped after the merge commit and before the push leaves an unpushed merge: `ensureWorktree` recognises its own (two parents, the runner's message, the second parent in `origin/<base>`, the first a head the branch had) and drops it, with a note, and the next `baseMerge` merges again. One that stopped after the push and before the record leaves the `running` record: the next status runs `baseMerge` again (interrupted), which finds the branch up to date at that commit and records it done.

## The watcher

One full check, every `schedule.watchMinutes`, with no model call of its own (design §5), and at each tick the forge check (below):

1. **The sources:** the board in the settings, each `tracker.watchBoards` board and each host job's board (the actions since a time), and for each target repo the PRs that changed and the PR events (a review request or a label may not move a PR's update time, so both are read).
2. **The cursor**, one per source in `<state>/watch/feed.json`: the window starts 10 minutes before `lastCheck`, and an id already in `seen` is dropped, so the overlap costs nothing. `lastCheck` moves to the start of the check once every event of the window was handed on, or its ticket was kept in `pending` for the next check. A source that fails keeps its `lastCheck`, and the others move on; once 24 hours have passed since its last good read, the gap is written to the run log (the report shows it) and the source starts again from now, still `failingSince` its first failure. A source with no cursor starts from now. The file is written to a temp file and renamed. After a sleep, launchd runs the missed interval once, and that check reads everything since `lastCheck`; if it fails more than 24 hours after `lastCheck`, it is the gap above, and the events of the sleep are never read.
3. **The watched lists:** a host job's board that had events has its list matched (on another board, its lists are read). A list that can't be matched (renamed, gone) fails that board's source for this check, as a failed read would: its cursor stays, none of its events is used, and the reason is in `lastError`.
4. **The tickets:** each event maps to a ticket through the ledgers (a card by id or short link, the ticket's original card, a PR by number or head branch). Events that map to no open ledger (intake cards, other cards) are left to the morning run, and to the start pass when the card is in the ready or intake list. After a `set retry`, the tickets with a session in their ledger are looked at too (`status` decides which were re-armed). At the check that moves the hub ("The hub after a merge", below), every open ticket is looked at too: each ledger in `mode pipeline` whose `close` isn't done, events or none. While a ledger file doesn't read, nothing is handed on: `status` reads every ledger, so it fails too. The tickets of the check's events (and the bad file's) wait in `pending`, the cursors move, and the check reports the bad file (the part is `the ledger <key>`). A morning run due meanwhile fails before its first step (its own `status`) and is tried again at each check, each time reading `/usage`: no triage and no starts until the file reads. Once it reads, the next check hands the waiting tickets on. A check that finds no event and no ticket waiting ends here: no status, no runner, no `/usage`, no `claude`, unless the start pass has something to look at (below).
5. **The decision is `status`'s:** the watcher asks `ticket-state status` (the same module, in process) about the tickets that changed (and, at a check that moved the hub, every open ticket), each once however many reasons it has to be looked at, and hands those with a next step, not locked, not in the owner's hands and not waiting after a failure, to the runner (`--watcher`), which hands each group to a run in a process of its own ("Handed on" in "The daily run"), so each runs once, and the check doesn't wait for any: a card move on one ticket is handed on at the next check while another ticket's chain runs. A group over `limits.parallel` (the runs of every process), or one a run of another process holds, waits in `pending`, and a later check hands it on; while the runs are full (at the last reading's session bar, one), the check doesn't run the runner, so no `/usage` is read for nothing. A model step held for no usage reading waits 30 minutes in `pending` (`readingWait`) before a check reads `/usage` for it again. A ticket waits for another only for an objective reason, at the start ("Limits and priority" in `context/ticket-flow.md`): a page in common, its card naming the other's number, or the triage's judgement (`together` joins the two into one group; a relation in one repo makes the later one wait). `mode off` stops every new hand-on at once, and a run handed on that hasn't read the settings yet; a run already in a chain goes on to its `limits.stepsPerTicket`. A ticket a run holds now is kept in `pending` and looked at again on the next check. A ticket whose next step answers comments goes on only once they are quiet (the start rule, in "The forge check"); until then it waits in `pending`, and the next full check looks at it again (the forge check, which saw the same change, usually takes it first). A ticket either check handed to a run that still goes on is held as a locked one is: kept in `pending`. The watcher never decides a step.
6. **The morning run:** at the first check after `schedule.morning` each day (the Mac may have slept through it), the runner's morning run instead: finishing, triage and starts, the finishing groups and the starts each handed to a run of its own; only the triage runs in the check. Its date is recorded once its hand-on is done, so a group that runs for hours can't make it run again. A group it couldn't hand on waits in `pending`, and one whose failed step or failed start it was giving its one more try keeps that try for the check (a step) or the start pass (a start) that hands it on that day (`owed`); so does one whose run came back without using it ("Handed on"). It covers every ticket, so the events of that check need nothing more. It waits for a check whose own board (the settings' `tracker.board`) was read: a Mac just awake, with its network still coming up, runs it at the next check (the output's `notes` says why). A board that stays unreadable is told after an hour (below). A morning run that throws before its first step is started again at the next check; one that throws part way counts as that day's, so its triage, starts and retries aren't repeated at every check.
7. **The start pass** (below), in a check that is not the morning run's.

**The hub after a merge** (`lib/hub-update.mjs`, `settingsForCheck` in `watcher.mjs`). Before the full check reads its settings, the process that runs it (`--full`, or a tick that is the full check itself) fetches the hub's branch (the `base` of the target whose `path` is the hub, else `origin/HEAD`; one branch, a 30-second timeout, `GIT_TERMINAL_PROMPT=0` and ssh in batch mode) and fast-forwards the hub's checkout to it, then reads the settings again, so a merged hub PR (a new `relatedRepos`, a role rule) counts at that check and in every session it hands on. Only when all of these hold:

- the hub has that branch checked out, with no uncommitted change to a tracked file and no commit origin lacks: `git merge --ff-only`, never a merge commit, a reset or a checkout. An untracked file is left alone; one the fast-forward would overwrite, an ignored one too (the state folder, a `.sources/` file: `--no-overwrite-ignore`), makes git refuse, and that is the note;
- the settings file at origin's commit holds, merged with the local file and validated as `loadSettings` does (`sharedProblemAt` in `lib/settings.mjs`): a merged file that doesn't, or one gone, would stop every later process at its first read;
- nothing reads the hub's files now: no run going (a live group lock, or a run a check handed on that holds none yet) no other full check holding its lock (it may run a host job), and no learning pass holding `learn-active` (it works in worktrees of the hub's clones, "Learning from the owner's edits"). The move waits for a check with none, so the hub's `CLAUDE.md`, skills and host-job scripts never change under a session or a job. The note says since when the hub is behind (`(behind since <time>)`, kept in `feed.json` as `behindSince`), and the report and the progress file ("Waiting for you") show it. A busy flow could keep it behind for ever, so once it has been behind for 30 minutes with runs going (`DRAIN_MS`, `hubDrain`), the hub drains: no new run starts (the full check hands on no step and no ready group, the forge check no comments; each waits as at `limits.parallel`) until it has moved, and the note says so. The runs going end, and the next check moves it.

The merge runs with no timeout (a checkout killed part way would leave a half-updated tree) and no hook (`core.hooksPath=/dev/null`), and it moved only when HEAD is then origin's commit. Otherwise nothing moves, and when the hub is behind origin the note says why (`the hub is 3 commit(s) behind origin/main and was not updated: it is on side, not main. …`); a fetch that fails is a note too, and the check goes on with the settings as they are. A hub whose branch isn't known (no declared base, no `origin/HEAD`) says so once, not at every check. A move goes to the run log (`kind: hub`, also when the check finds the watcher lock held) and the check's line; the note goes to the check's `notes` and line, and the last check's hub state to `feed.json` (`hub`), which the report's "The watcher" shows while it has a note. A forge check, a tick that only starts the full check, a hand-on (it reads what the full check left), a dry run and `mode off` don't touch the hub.

**Every open ticket after a move.** A move is no event of any ticket's, yet a merged setting or rule (a new label, a gate, a role rule) may give a waiting ticket a next step. So the check that moves the hub, at once or at the check that finally makes a move the runs going had held back, asks `status` about every open ticket (each ledger in `mode pipeline` whose `close` isn't done) as if each had an event, and hands on those with a next step under the same guards and limits as step 5: not locked, not in the owner's hands, not waiting after a failure, a run slot free. A ticket that also has an event, or is in `pending`, is looked at once. Any move counts, whatever files it changed: the settings, the hub's `CLAUDE.md`, its skills and its role rules all reach `status` or the sessions, and a pass over the open tickets costs one `status` and no model call when none has a next step. A check that doesn't move the hub (any outcome but a move: level, behind, ahead, failed, skipped, or no update tried) looks at what it looked at before: the tickets of step 4 and those it names. A check that moves the hub and then stops early (`mode` off at the new settings, the watcher's lock held, the feed or the ledgers unreadable) makes no pass, and the next check sees the hub level: those tickets wait for an event or the morning run, as before this pass existed. The morning run looks at every ticket anyway, so a move at its check needs nothing more.

**Settings broken at HEAD** (a bad file committed by hand) stop every process at its first read, the tick that would start the full check included. Then any process but a hand-on or a dry run tries the update first, with `mode` unknown, and with the state folder the working file names for the runs going on, else the one the file at HEAD names, else the default when the file that parses names none (`stateFolderOf`). When neither parses, the folder can't be known, and a hand-on's locks with it: the hub stays put, and the note says so: a fix merged on the forge is pulled and read; until one is, the error stands, with the hub's note.

Fast-forwarding the checkout, rather than reading the settings from `origin/<base>`: the role tool rules stay on the hub's own HEAD, which no session can move (a fetch in any worktree moves `origin/*`), and the settings, the hub's `CLAUDE.md`, its skills and its host-job scripts stay one version.

Before all of these, each check collects the runs earlier checks handed on (`handOns` in `feed.json`: `{ id, pid, keys, group, stage, at, by, why, retried }`, written as each run starts, so the forge check sees it at once): a run whose process ended leaves `hand-on/<id>.json`, whose notifications (a step failed twice, a guard stop) go out then; one that failed or left no result (a crash, a reboot) puts its tickets back in `pending`. A start the start pass handed on is told (the notification below) once its card is in work, whether its run still goes on or not.
8. **Host jobs** (below), then the notifications.

**An error in one part** of a check (a watched list, `status`, the watcher's run, the morning run, a job, a source that keeps failing) is caught there: it is in the output's `errors` with its reason, in the run log and an urgent notification once a day per part, and the rest of the check goes on. Tickets a failed `status` or run didn't take stay in `pending`.

**A source that keeps failing** (a token revoked or expired, credentials the LaunchAgent can't see, a long outage) is a failed part once its read has failed for an hour of the watcher's awake time (`ALERT_MS` in `lib/feed.mjs`): one part per client, `the tracker` for the boards and `the forge` for the PRs, so a token that is gone is told once, not once per board or repo. The text names the client's error (`HTTP 401 …`) and what to check: the tracker's token and key (`tracker.credentials`) or the forge's sign-in, and the network. It is raised from the first check after `schedule.morning` each day, so a board dead overnight is told in the morning, not at midnight; meanwhile the morning run keeps waiting for the board. Its 24-hour gap is one more part (`the tracker's events`, `the forge's events`), notified at the gap. The hour counts from the later of the source's `failingSince` and `awakeSince`, the first check after a pause in the checks longer than both an hour and three intervals (`pauseMs`: the Mac asleep, the agent off; `checkedAt` in the feed is when the last check ended, so a long run inside a check is not a pause). So a network still coming up after a wake stays quiet, even when the source was already failing as the Mac went to sleep, and a gap that is mostly a sleep is only logged. An hour is twelve checks at the default 5 minutes: long enough for a wake, a VPN or a short outage; short enough that a token gone overnight is told the same morning.

One full check at a time: a lock in `<state>/watch/active/`, freed when its process is gone; the forge check has its own (below), and the two may run at the same time. `mode off`: nothing is read and the cursors stay. `mode observe`: the runner plans and writes the report only, and a due job is logged as planned, not run.

### The forge check

A comment the owner leaves on a pipeline PR would wait up to `watchMinutes` for the full check, and longer while a check runs a ticket's chain (its hand-on waits for the sessions, up to hours). The forge check picks it up within a minute, whatever runs: the LaunchAgent ticks every `schedule.forgeSeconds` (60), and each tick runs the forge check in its own process and, when `watchMinutes` have passed since the last full check began (`fullAt` in the feed; half a tick early counts, as launchd's interval drifts; a feed with no `fullAt`, or a clock gone back, makes it due) and no full check still runs (its lock's holder is alive), starts the full check as a process of its own (`watcher.mjs --full`), detached: the tick doesn't wait for it. One agent: install, uninstall and the one-agent-per-host cleanup stay as they were; the plist's `AbandonProcessGroup` lets a detached process outlive its tick. Webhooks were left out: they need admin rights in every docs repo and a relay to reach the Mac, for seconds gained.

What a forge check does, with no model call of its own:

1. **The runs it started that ended:** their notifications (a step failed twice, a guard stop), and the progress file. A run that threw is a failed part (notified), and its tickets wait a full interval before the next try (each try reads `/usage`); a run whose process ended with no result (a crash, a reboot) puts its tickets back after a full interval too, so a run that always dies isn't started at every tick. Meanwhile a new comment doesn't cut the wait short.
2. **The PRs that changed**, per repo of the targets (`changedPrsSince`), with cursors of its own, so the full check's cursors and reads stay as they were. Not the PR events: they carry no comment (a review request, a label, a merge), and the full check reads them. A cursor older than the 10-minute window (a sleep) starts from now: the full check reads that stretch. A read that fails keeps the cursor; a source that keeps failing is the full check's to tell.
3. **The tickets** of those PRs, through the ledgers on disk, and those whose wait ended. A closed ticket, or one in the owner's hands (`mode hand`), is left alone. A ticket a run holds (its group's lock, or a run of either check still going, which may not have taken its lock yet) waits for that run to end: looked at again at the next tick, with no forge read meanwhile; a comment that arrives while its session runs waits for the next session.
4. **The comments**: each changed PR's activity (`prActivity`), and the comments and reviews no record handled (the owner's and a reviewer's; the pipeline's own and a bot's don't count, as for `status`). A review not yet submitted is never read: the forge leaves out a draft review and its comments.
5. **The start rule** (`lib/quiet.mjs`). A submitted review is a batch: its session starts at once. A review is a batch when it has text of its own, gives a verdict (approved, changes requested) or holds more than one line comment. Single comments (a conversation comment, a line comment added on its own, a reply in a thread) start a session once the newest of them is `schedule.commentQuietMinutes` old (2) with no newer one, the owner's and a reviewer's alike. So three comments 30 s apart start one session, not three; an owner's comment is handed on within about 3 minutes (the quiet, then the next tick), a submitted review within about a minute. Until then the ticket waits (`waits`: `prs`, `dueAt`, `why`, `since`); the run log gets one `waits` line when a wait begins or a newer comment moves it. The full check holds the same rule at its own hand-on (the ticket goes to `pending`), so a full check in the middle of a burst doesn't start a session either.
6. **The hand-on:** the tickets whose comments are ready go to one run in a process of its own (`watcher.mjs --hand-on <id> --ticket <key>…`, detached, its output in `launchd.log`), and the check ends: it never waits for a session. That process prepares its environment as the watcher does (no API key; the sign-in token for its `claude` only), runs the runner's watcher run (`/usage`, then `status`, which reads the tracker, then the steps, as the full check's run would) and leaves its result in `<state>/watch/hand-on/<id>.json`. At `limits.parallel` runs going across processes, counted as the runner counts them (each group with a live lock once, by its ledger's group, and each run of either check that holds no lock yet), the tickets wait for a slot. Unlike the full check's, one forge run carries every ticket ready at that tick (in practice one), as before. The forge check doesn't read `/usage`, so it can't see the session bar (`limits.sessionPercent`); the run it starts reads it and, at the bar, advances one group at a time.

No tracker read of its own, no morning run, no start pass, no host job, no `/usage` and no `claude`. Its memory is `<state>/watch/forge.json` (`lib/forge-state.mjs`: its cursors, `waits`, `handOns` and `notified`), written by it alone; it never writes the full check's `feed.json`.

**The locks.** The full check's lock (`watch/active/`) is the full check's alone, and the forge check's (`watch/forge-active/`) the forge check's alone: the two checks may run at the same time, each writing its own file. Who runs a ticket is the group lock's to decide, as between a manual run and a scheduled one: the runner takes a group's lock before its first step and skips a group another run holds, so a ticket the full check's run and a forge run both reach is run once. The window before a run takes its lock (its `/usage` reading and its `status`) is covered by each check's record of its runs (`handOns` in `forge.json` and in `feed.json`, a process alive and under 12 hours old): both checks, the morning run and the start pass hold those tickets as locked. A start handed on counts as starting now in every start decision (`status`'s `startable`: its slots, its share of the allowance, its relations) until its run has recorded it, so no second start is decided meanwhile. Two checks that read each other's record just before either wrote it can still reach the same ticket: the runner reads a ticket's status again once it holds the group's lock, and skips a step that is no longer the next one, so the step runs once.

**The rate.** The forge check's reads are GraphQL queries through `gh`, against GitHub's 5,000 points an hour. One `ChangedPrs` per repo per tick, 2 points each (50 PRs with their labels, assignees and review requests): 3 repos at 60 s are 180 queries and 360 points an hour, with nothing new. Each changed PR of a ticket costs 4 queries of 1 point (`PrByNumber`, `PrReviews`, `PrThreads`, `PrComments`), and 4 more when its wait ends: a busy hour of 30 comments, about 240 points. So about 600 points an hour, an eighth of the limit, at 30 s twice the `ChangedPrs` share (720). The full check adds its own reads every 5 minutes as before (per repo a `ChangedPrs` and a REST events page, and `status`'s reads of each open PR).

### The start pass

Without it a slot that frees during the day (the owner merges the open ticket's PR) would stay empty until the next morning run. Inside `limits.startHours` (default `10-22`, local time), the watcher has the runner triage and decide the starts as a scheduled run does, each start handed to a run of its own ("Handed on" in "The daily run"): `runDaily` with `startPass`, which skips the finishing (the watcher's own run did that for the tickets that changed), triages the intake cards that became due since the watcher's last look (one session, as in the morning; `triageKeys`), then starts ready groups in `limits.startOrder` while the limits and the day's allowance allow (`limits.open`, `inProgress`, `waiting`, `dailyPercent`, the session and week bars from `/usage`). Its starts are scheduled starts (`startedBy: schedule`): they count in the limits, in the run log and in the day's report like the morning run's. A waiting failed start stays waiting (only the morning run or a person gives it its one more try; a pass gives it only to a start the morning run's try is still owed to, `owed`, and to no other), and the morning run itself is unchanged. No pass runs before that day's morning run has run: the day's first starts are the morning run's, also on a host whose start hours begin before `schedule.morning`, and in a check that began before it and ran past it.

**Once per change.** A pass runs only when something changed since the last look that could let a start or a triage happen: a ticket no longer open (a slot freed), a group newly ready (a new card in the ready list, a ticket triaged ready; a group whose start failed is left out), an intake card newly due for triage, or a new date. The open tickets growing, a ready group gone or a card back in its quiet hours count for nothing; the view seen then becomes the one the next change is measured from. An intake card has no ledger, so a triage that failed holds nothing: a pass triages only the cards newly due, and one whose triage failed stays due and waits for the next morning run, or for a person (a comment puts it back in its quiet hours, and it is new once due again). A pass that fails before its first step (or whose status can't be read) is tried again after 30 minutes (`retryAt`, `RETRY_MS`), not at every check. The last look's view (`startPrint`: the date, the open tickets, the ready groups, the intake cards due) is kept in `<state>/watch/feed.json` as `starts`, with `by` (`morning` or `watcher`), `at`, `outcome`, `nextDueAt` (when the next intake card still inside its quiet hours becomes due) and `deferred` (a change seen when no pass could run). The morning run counts as the day's first pass and writes it too. A pass that started nothing (no ready ticket, the allowance used, the slots full) runs again only after another change, never at every check. Two passing reasons are not that: a pass with no `/usage` reading (whose `startable` then gives no group, "the day's allowance is unknown"), and one whose start waited for a run slot. It leaves `again` (the reason; with a reading missing, `retryAt` 30 minutes on), and the next look runs a pass with no change: after `retryAt`, and, for a slot, once the runs going are under `limits.parallel`, one at the last reading's session bar (until then no runner and no `/usage`). `retryAt` holds only that retry: a change (a slot freed, a group newly ready, an intake card due) runs a pass at once. The morning run leaves `again` for the same reasons.

**What it reads.** A check that read `status` anyway (tickets changed) compares that view; otherwise it reads `status` only when something may have changed: an event on a card in the ready or intake list of `tracker.board` that has no ledger, `nextDueAt` passed, a deferred change, or the first check of the day inside the hours. When nothing can start whatever the allowance (no ready group and no intake card due, or the counts at a limit: `limits.open`, `inProgress` or `waiting` reached), the change is noted and the runner isn't called: no `/usage`, no session. So a slot that isn't free (the open ticket waits for the owner or a reviewer) starts nothing.

**Quiet hours.** Outside `limits.startHours` there is no pass, no triage and no `/usage` read for it; a change seen then is kept (`deferred`) and looked at by the first check inside the hours, unless the morning run takes it over first. A check whose board can't be read keeps it too. The hours are read when the pass would run, not when the check began: a check whose own run (step 5) ends after the hours runs no pass. A pass still running when they end (`startUntil`) triages nothing more and starts no further group; a group it started goes on with its next steps, as after any scheduled start.

**What it says.** The check's line in `watch/launchd.log` gives the reason and the result: `start pass (a slot freed: 501 no longer open): handed on the start of 502 (run <id>)`, `start pass (…): started nothing (<the first group's reason>)`, `start pass not run (…): 1 open (501) of 1`; a dry run or `observe` says `would start`. Each group it started gets one notification (not urgent), naming the tickets and the reason, at the first check that finds its card in work; a guard stop or a step failed twice is told as for any run. The report's watcher section names the day's last pass and a change that waits for the start hours.

### Host jobs

The host declares in `hostJobs` "when list X gets new cards and stays quiet for N hours, run job Y", or "run job Y every N minutes". The toolkit knows nothing about what a job does.

- **A watched list:** a card that arrives in the list (created there, or moved in) arms the job; every change in the list (a card in, a card out, an action on a card in it) moves `lastChange` to that change's own time, so a change seen only after a sleep still restarts the wait. The job runs once `quietHours` have passed since the last change, once per armed batch. In a check where its board's source failed (or its list couldn't be matched), the job neither runs nor changes: it hasn't seen the list, and its entry says why.
- **`every`:** the job runs when `every` minutes have passed since its last run.
- **`run.script`:** a file inside the host repo, started from the host root (`node` for `.mjs`/`.js`). Not guarded: it makes no model call.
- **`run.skill`:** one `claude -p "/<skill> [args]"` session, with the plugin from the runner's toolkit (`--plugin-dir`, as a role session), the job's `model`, `effort`, `maxTurns` and `allowedTools` (an unattended run stops at an `ask` rule, so the job's allow list must cover what the skill does), and `jobDenied` (`--disallowedTools`), for the spellings a rule can name (an allow list as broad as `git:*` would let a quoted subcommand, `git 'push' …`, past them, so settings validation refuses one; see "What a role session may run"): no push, no `git branch` change and no fetch, in the plain and the `git -C <any folder>` spellings, and the roles' git, code and file denials (no plain add or commit, no `node -e`, interpreter or shell, no write to `.git/`, `.claude/`, `.github/` and the rest; see "What a role session may run"). It is a model call, so the guard holds it like a scheduled step: at the allowance it waits an hour, and the owner is told.
- **Its environment:** no API key (below), plus `DOC_TOOLKIT_JOB` (its name), `DOC_TOOLKIT_JOB_LIST`, `DOC_TOOLKIT_JOB_FIRST_CHANGE` and `DOC_TOOLKIT_JOB_LAST_CHANGE` (ISO times: the first card of the batch, the last change). A skill job's `claude` gets the sign-in token; a script never does. Its output goes to `<state>/watch/jobs/<name>-<time>.log`, its outcome to the run log.
- **A failure** is tried again at the next check, quietly: a watch job stays armed and an `every` job keeps its last run, so a network drop of a few minutes costs a few failed tries and nothing more. A job that has failed at each try for an hour of the watcher's awake time (`ALERT_MS`, counted as for a source, so a sleep is not failing time) is disarmed, with one urgent notification: a watch job until a new card arms it, an `every` job until the next morning run (`heldUntil`, the next `schedule.morning`). The report's watcher section shows a job failing since when (`failingSince`, its tries), when it was disarmed (`lastFailure`), until when it is held, and when it was re-armed.
- **Re-armed sooner** (`lib/rearm.mjs`): a job disarmed while reads were failing too (the boards, the PRs: `disarmed.downWith`) re-arms at the first check where all of them read again, and runs in that check if it is due; so after an outage the job runs as soon as the network is back, not the next morning. A job disarmed while every read worked failed on its own, and stays disarmed. `ticket-state set retry job <name>` re-arms one by hand.
- **At night:** a job disarmed before `schedule.morning` sounds nothing then. Its alert is kept in its state (`alert`) and goes out at the first check after `schedule.morning`, as a source's alert does, if the job is still disarmed then; a job that re-armed before the morning drops it unsent.

### Notifications

macOS only, with `osascript`, the text passed as an argument (never inside the script). Once a day, after the morning run: its counts (steps done and failed, groups started, tickets in progress and waiting, the week's use against the allowance). Once per group the start pass started, not urgent: the tickets and why the pass ran (a slot freed, say). Urgent (with a sound), once a day per reason: a limit reached (a guard stop, of a step or a skill job), a step held after two failed sessions or at its daily session cap, a host job that failed at each try for an hour (held until `schedule.morning` when it happens before it), or a part of a check that failed (a board or the PRs unreadable for an hour, and their 24-hour gap, among them). Nothing else, and nothing goes to the tracker or the forge. `/ticket-report` reads the report itself.

### The plan pays

Every `claude` the runner and the watcher start gets an environment without `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`: with `-p`, either would be used before the plan's sign-in. The watcher also removes them from its own environment and says so in its output (by name, never by value). With `schedule.tokenFile`, it reads the long-lived sign-in token and passes it as `CLAUDE_CODE_OAUTH_TOKEN` in the environment of the `claude` processes only (the sessions, the `/usage` reads, the skill jobs); a file others can read is refused. The token never goes into the watcher's own environment, so host scripts, `git` and `gh` never inherit it, and it is never printed, logged or written into the plist.

### Installing the LaunchAgent

1. The sign-in, optional. Without `schedule.tokenFile`, every `claude` the watcher starts (the sessions, the `/usage` reads, the skill jobs) uses the CLI's own sign-in, as in a terminal: the plist gives the watcher only `PATH` and `HOME`, and the runner adds no token. To use a long-lived token instead, run `claude setup-token`, save the token in a file outside every repo (`chmod 600`), and set `schedule.tokenFile` to it: `ticket-state.mjs set schedule.tokenFile <file>`.
2. `launchd.mjs print --root <host>` to see the plist; `launchd.mjs install --root <host>`. The label is `dev.doc-toolkit.ticket-flow.<host folder name>-<hash>`: the folder's name in ASCII (`host` when nothing is left) and the first 8 hex digits of the SHA-256 of the host's absolute path, so two hosts with the same folder name get two agents. The log is `<state>/watch/launchd.log`. An agent of the same host under another label (found by its plist's `--root`) is replaced.
3. `launchd.mjs uninstall --root <host>` removes it; `left: false` confirms that nothing is left. It needs the path only, not the settings: a host that moved is uninstalled with its old path. It also removes any agent of ours whose plist starts the watcher for that path (`others`). `mode off` in the local file stops every run at once, with no uninstall.

The plist holds absolute paths (node, the watcher in the plugin's folder as installed, the host) and a PATH with `claude`, `git`, `gh`, and `ffmpeg`, `ffprobe` and `tesseract` when found (the video gate's cut, `scripts/video-parts/`, and its frame sweep): install again after the plugin or one of them moves, or after installing `ffmpeg` or `tesseract`.

## The live progress file

`<state>/watch/progress.md` is a checklist of the work as it happens, for reading in an editor. A script writes it with no model and no network (`lib/progress.mjs`): at the start and the end of each step of a run, and at the end of each full watcher check (a forge check only after one of its runs ended), so it also shows the pipeline while it only waits. The `watch/` folder is under the state folder, which a host keeps out of git.

**To follow it:** open `progress.md` in VS Code and press `Cmd+K V` (Markdown: open preview to the side). The file is replaced as a whole (a temp file, then a rename), so a preview never shows half of it. Whether the preview refreshes by itself while the runner writes has to be seen on a live pass; if it does not, reopen the preview (the file is a plain Markdown file, so any viewer that reloads on change works).

What it shows, top to bottom:

- The update time and `mode`.
- **Waiting for you:** each gate where the pipeline waits for the owner (questions, the section plan, a PR's final review, ready for merge), from the ledgers alone; a PR closed as won't merge (`forge.wontMergeLabel`, from the last status, kept in `progress.json`) has none, and its ticket's block shows it as dropped. With `forge.triggerWords`, also each PR comment the pipeline doesn't take that isn't the owner's (a colleague's, or anyone's reply in the pipeline's or the owner's threads, an expert's included), with its link (💬, kept in `progress.json` from the last status): hand it on with a comment that starts with the word, or leave it. It goes off the list once it was handed on (a session took it with the owner's worded comment that points at it and recorded its id), or when the PR is merged or closed. With `forge.translatedLabel`, also each PR of a ticket closed today that was merged without the label (⚠️, with its link): its translations may be behind the base.
- **The current run** (**The last run** once it ended, also when the run stopped on an error): what kind of run it was (the morning run, a start pass, the watcher's, a scheduled one, one started by hand), the steps running now with their elapsed time, the triage and its count (a triage session shared by several cards shows its duration here once, and each card its share of the cost), the tickets picked, why a ready group did not start (the limits, the day's allowance, a locked group), a guard stop, the free slots. Under it, one line from the watcher's last start pass (`feed.json`, `starts`) when it did not run or started nothing: `not run: no ready ticket` or no room, `started nothing`, deferred (a change that waits for the start hours, `limits.startHours`, or for a board that reads), `retry at HH:MM` after a failed try, or `failed`.
- **Tickets in work:** each ticket that has a `start` record (or a step running on it), phase by phase; a triaged ticket not started yet is one line, "Triaged, not started: …". ✅ done, with the cost and the wall-clock time of its run from `runs` (`wallMs`, with the session's own count in brackets when it is a minute or more shorter; a run from before `wallMs` shows the session's count; a session shared by several cards shows the card's share of the cost and no time; the runner's build shows its time and no cost); ⏳ running, with the start time and the time since; ⬜ not yet; ❌ failed, with the reason; 👉 a gate that waits for you, ⏸ one that waits for someone else (the reviewer, the team). The row "Your read of the UA" names an expert review the writer recommended (`expertReview`). The row "Expert review" comes after it and shows only when the PR is at the review, was asked for (`reviewersRequested`) or is recommended: ⏸ while the PR is at the review status, ✅ once a person's move took it there and back, ⬜ with the reason otherwise (a review request that came with the `pr` record alone is not a review; the tick rests on a review request in the PR that the `pr` record's own result does not carry; the ledger keeps no other trace of the stage, so a target with no reviewers on the forge leaves none and shows no tick). A chain stage that a change in UA made stale, and every stage after it, goes back to ⬜ with "stale". A closed ticket is not shown; a ticket in the owner's hands (`mode hand`) is listed by key.
- **Claude's planned steps:** if `progress.stepsFile` names a file, its text, as it is, at the end. The runner never writes that file.

The ledgers win: every row except the stale ones and the dropped PRs is read from them. The stale marks and the dropped PRs (closed as won't merge) come from the status the runner has when it writes. They are kept in `watch/progress.json`, so a watcher check that ran no step shows them too; a stale mark drops when the stage runs again for the new head, a dropped PR when a status no longer shows it dropped (reopened, or the label taken off). A check that reads no status leaves the marks as they were.

Limits: the gates are read from the ledgers, which do not show a card a person moved out of the flow without a close record; such a ticket keeps its rows until its ledger is closed. Two processes writing `progress.json` at the same moment (a run started by hand and the watcher) can lose an entry of `notified`, which costs one repeated notification at most.

**A step in flight** shows ⏳ at once, before its session records anything: the runner writes the file when a step starts and when it ends, whatever its outcome. A dry run and `observe` mode write nothing from the runner (the watcher's check writes the file in `observe` too: it only reads the ledgers).

**A run that throws** closes the file in a `finally`: the header says "The last run", never "in progress". The rows still show what the ledgers say (a stage left `running` shows ⏳ until the next run records it).

**A failed write never fails a run.** `writeProgress` returns `{ written: false, error }` and the step goes on.

### "Your turn" notification

At the end of each watcher check, one macOS notification (not urgent) for each gate that waits for the owner and has not been told yet: questions on the card, the section plan, the video transcripts, a PR's final review, ready for merge. Not for a reviewer's wait, a card the owner moved back, a ticket in the owner's hands, or a failed or held step (that one has its urgent notification already).

The memory is `watch/progress.json` (`notified`). A gate is `<key>|<kind>|<PR>|<mark of its arrival>`, where the mark is what the pipeline recorded when it opened the wait: the newest question's time, the plan gate's record, the pipeline's latest commit on the PR, the head marked ready. A check that finds the gate standing tells nothing. A gate that ended is forgotten, and a later one tells again (a second round of questions, a new head after a rework). The first write of the file only records the gates already standing, so nothing is told for them. Only the watcher sends; after a run started by hand, the gate is in the file at once and the next check tells it.

### Claude's planned steps

`progress.stepsFile` in the local settings file (`<name>.local.json`, next to the shared file; none by default) names a file with the owner's own checklist: a path from the host root, absolute, or with `~`. A missing or empty file shows no block. Set it by hand, or with `ticket-state.mjs set progress.stepsFile <file>`.

## The browser lock

`browser-lock.mjs take|free|status --ticket <key> [--wait <minutes>]` serialises Playwright runs on the host's folder `<state>/.playwright.lock`, the one a hand run takes with `mkdir` and moves away when done. Every role is denied `mv`, `rmdir`, `rm` and a `mkdir` of the lock folder, even where a host layer allows them, and the Edit and Write tools on the lock folder and on `<state>/.playwright-busy`, so a session takes and frees the lock only through this script, which every role may run by its path (`NODE_SCRIPTS`): it can't make a lock with no holder or forge one.

- `take` makes the folder with a `holder.json` naming the ticket. While another ticket or a hand run holds it, it waits up to `--wait` minutes (default 10; a session passes 9 and gives that Bash call the tool's longest timeout, 600000 ms: the default, 2 minutes, would end the wait early with no note), then exits 3 and writes a busy note, `<state>/.playwright-busy/<ticket>.json`. Its own lock is taken again at once. A take that goes through removes the ticket's busy note from an earlier give-up. Two takers of one stale lock don't crash: the one that finds it already removed goes on, and the folder's `mkdir` lets only one of them take it.
- A lock older than `STALE_MINUTES` (60), by its holder's time or, for a hand run's empty folder, the folder's, is taken over: a holder that crashed never keeps it.
- `free` removes the folder only when this ticket holds it; a lock another ticket or a hand run holds stays (exit 3). A lock that isn't a folder (a file, a link) is never touched.
- When a session ends, failed, timed out or done, the runner frees a lock one of the step's tickets still holds, and writes `browserLock` `freed` in the run log.
- A session that ended with a busy note from its own time is waiting, not failed: the run is logged with `outcome` `busy`, the stage isn't recorded `failed`, no failure is counted, no bigger model is tried and the ticket isn't held; the step runs again at a later check. The roles proposal leaves such runs out. A session still counts toward `limits.sessionsPerStageDay`, so a lock held all day ends in the daily cap. A broken lock (not a folder) writes no note: that session fails as any other.

## The build lock

`<state>/.build.lock` lets one full site build run at a time in the pipeline: a full build of every locale takes gigabytes of memory, and two at once on a machine short of memory each slow to half an hour or more under swap. `limits.parallel` counts groups, not builds, so it doesn't see them. Only the runner takes the lock, never a session (every role is denied the folder, its `mkdir` and Edit and Write in it): around the chain's `build`, and around a session that builds the site itself (a re-sync; a visual pack with no build to reuse). `holder.json` in it names the ticket, the stage, the runner's pid and the time of its last renewal.

- A second taker waits, trying every 15 seconds, up to `build.waitMinutes` (90). Held for the whole wait: the step is `busy`, as a session on a busy browser lock is: not failed, no failure counted, no bigger model, no hold; it runs again at a later check. Its run keeps the time it waited (`waitedMs`, and `wallMs`); a wait before a session that never started has no `start`, so it counts as no session.
- A lock that isn't a folder, or one the runner can't read or write (its rights), fails the step with the reason, before any build or session: the failed-step rules apply, as for a stuck worktree.
- The runner renews the holder's time every 5 minutes while the build or the session runs, so a live build is never taken over. A holder whose process is gone is taken over at once; one that stopped renewing (a frozen runner, or a folder with no holder) after `STALE_MINUTES` (60). A takeover is logged (`buildLock` `tookOver`). It renames the stale folder aside first (`.build.lock.stale-<pid>-<hex>`, removed at once), so two runners that both find it stale take it once: one whose rename moved another folder than the one it judged (the other runner's fresh lock) puts it back and waits, and the folder's `mkdir` lets only one of them make the lock.
- The runner frees it when the build or the step ends, failed, timed out or done; a lock another ticket or another runner holds stays. A lock that isn't a folder is never touched.
- A hand run (the owner's own build) doesn't take it: the lock covers the pipeline's builds only.

## Learning from the owner's edits

With `learning` in the shared file (TASK-054, D-045, D-134). The model proposes, the scripts dispose: a session's only output is one JSON file under `<state>/tmp/`, and every change it leads to is the runner's, with no model.

**The log (no model).** After each live run (not a dry run, not observe) the runner appends the owner's edits on that run's tickets, as its status read them (no forge call of its own), to `<state>/learning/edits.jsonl` (`lib/learn-log.mjs`), one line per changed block: `id`, `at`, `key`, `repo`, `pr`, `url`, `page`, `block` (the heading above it), `before`, `after` (each cut at 1500 characters, `cut: true`), `source`, and `comment`, the owner's words. Sources:

- `comment`: an item of `prs[].edits` the writer applied at a review comment (stage `answerComments`, no `rule`), its `reason` the comment. Only the owner's, by the forge: the round's handled comments (`reviewComments` of the same `at`, their `id` and `replyId`) are looked up in the PR's activity (`authorsFrom`, one read per PR), and the item counts when one of them is by `forge.self`. A round that recorded no handled comments counts as the owner's. Nothing the model writes names the author. When the read fails, the PR's comment items wait (`deferred` in the cursor, a note) and are read again at a later pass, never dropped.
- `restore`: a style fix the owner undid (`rejected` on it): `before` the fix's text, `after` the owner's, `rule` the rule the fix applied, the sign of an exception to a general rule.
- `hand` and `final`: a commit on the branch by the owner (its git author's email or name in `learning.authors`; an expert's push is not the owner's taste) that the ledger doesn't record as the pipeline's anywhere (`pipelineCommits`, the rounds' commits, the id step's), not a merge, over the UA pages of the PR's own it changed, never an id-only change or EN. `final` after the PR's first `readyForMerge` head (D-062); `comment` the style check's `reason` for it, else the commit's subject. An open PR's commits are those its base as fetched doesn't hold; a merged PR's, those its merge commit's first parent doesn't hold (the base holds the branch once it is merged; a squash or rebase merge leaves the branch's own commits off it the same). The merge commit comes from the forge (`mergeCommit`) or the ledger (`merged.commit`), and the clone fetches the base once when it lacks it. A merged PR with no merge commit known, or whose commits git here can't list, gets a note and is read again at a later run: it is never closed as done with nothing.

The blocks come from a diff of the page before and after the commit: paragraphs, headings, fenced blocks and the frontmatter, a change in whitespace only being none; a page the commit added or removed whole is no edit. A line's `id` is stable (a commit's lines are keyed by the commit, `commit:<pr>:<sha>:<page>:<n>`, whatever their source), so nothing is added twice. The PRs it covers: every open PR, and every merged PR merged at or after `learning.since` (required: the collector never reads the whole history); a PR closed unmerged is outside the flow. `<state>/learning/cursor.json` keeps each PR's head and count of edits as last read (a PR with neither changed costs no git call, and a merged PR is read once more at its final head, then never again) and the earliest `since` a pass used (`#since`). One collector at a time (`learning/.collect.lock`, stale after 10 minutes); a dry run takes no lock and writes nothing, not even the folder.

**The backfill.** `ticket-state learn collect --since <iso>` runs the same collector over every ledger once, with each PR's state from the forge, so the first weekly session already sees the PRs merged before the switch (from the week's Monday, say). It is idempotent: run twice, it adds nothing twice. Run with an earlier `--since` than a pass before it, it reads again the PRs that pass left outside its window. `--dry-run` lists what it would add.

**The learning pass.** No learning session runs inside a check, so none holds the full check's lock. The full check's step 5c, after the hand-ons, asks what a pass would do (`learnWanted`), real work only: a first pass to record the start week; the week due or a queued toolkit rule (these two only while the session gate is open); an open rule PR or toolkit PR the forge lists as changed since the last pass (`changedPrsSince` from `lastPass` in `proposals.json`, one read per repo: a comment, a push, a merge, a close; a read that fails counts as changed); a rule PR with a reply that waited (`waiting`: the gate was closed, a push failed), once the gate is open. In observe or off, nothing. With something to do and no pass running (the watcher lock `learn-active`, its pid live), it hands one pass on to a process of its own (`watcher.mjs --learn`, detached, its output in `launchd.log`) and goes on. The pass takes that lock, reads the gate again (today's morning run, the ticket runs), does the steps below, sends each notification once (the keys in `proposals.json`), adds a line to the day's run log when it did something, and writes progress.md. **The session gate** (`sessionGate`), for every learner session (the week's, a rewording, the toolkit's): today's morning run done, no ticket run going (no live group lock, nothing a check handed on that holds none yet: D-131, the tickets first), inside `limits.startHours` (D-109: no work at night or in the early morning), and the allowance left (as a scheduled step).

**The weekly session (point 2).** The first live pass records the ISO week the learning was switched on in (`startWeek` in `proposals.json`); that week gets no session, so a switch mid-week runs nothing at once, and the first session, the next Monday, reads that week's edits too (the backfill's among them). From then on, at the first pass of the ISO week with the gate open, the pass collects once more over every ledger, each PR's state from the forge (what the runs' own passes couldn't see: a PR merged since, a ticket closed), and starts one `learner` session (`context/ticket-roles/learner.md`) with the log's lines that no earlier proposal used, from the last `horizonWeeks`, the rules the owner rejected, those open or accepted (`taken`), and each repo's `product-rules.md`. It groups the edits into patterns, drops fact fixes and what a rule already says, states the reason (D-081), and gives each a kind: `product` (`продукт`), `general` (`загальне`), `exception` (`виняток із загального`, with the rule it overrides). The checks (AC-1, `checkPatterns`): two examples or more on two PRs or more, each a line of the log that no earlier proposal and no other pattern used, a known kind, a rule and its reason, not a rule the owner rejected nor one open on a rule PR or accepted (no second kit line), an exception naming what it overrides. What fails is refused and kept in the week's record (`learn status`). With fewer than two PRs with new edits there is no session. A rule is recorded, and its lines used for good, only once a rule PR carries it; the lines dropped as facts are used too, so a rejected rule's edits never come back. A rule PR that could not be opened leaves no record: its worktree is removed, its rules not recorded and their lines free for the next try. Its pushed branch is never deleted: the retry fetches it and builds on it (its kit lines are not added twice), and before it opens a PR, and again after an open that failed, it looks the PR up by its head (`prState`), so a PR the forge made though the call failed is used, never a second one. The week is recorded once every PR it needed was opened. A session that failed, or a week with a PR that could not be opened, is tried again at a later pass at most three times in the week, two hours apart (`attempts` in `proposals.json`); a retry never opens a second PR of the week in a repo.

**The rule PR (point 3).** In each target repo where a kept pattern was seen, the runner makes a worktree of the clone at `origin/<base>` under `<state>/learning/trees/`, adds the rules under `learning.section` of `<kit>/product-rules.md` (the kit from that repo's own `CLAUDE.md` at its base, `Product kit:`; a repo with none gets no PR, and the run's notes say so), each line ending with `<!-- learned:<id> -->`, commits with `labels.commit` (no trailer), pushes `learning.branch`, and opens the PR. Its description (`renderBody`): the trend line first (the owner's edits per PR last week against the weeks before, from the log: pipeline-measures doesn't read the ledgers yet, TASK-100), then the numbered rules (the kind, the rule, its reason under `labels.why`, the «was → now» examples with their PR links), then the host's structure: Description, the closed list of changes, Task link, Open questions (a rule's `question`, per reader, collapsed), and how to answer. A notification and a line in the progress file's «Waiting for you» announce it. Nothing reaches the kit before the merge: the base is never touched.

**The reply (point 4).** Each pass reads every open rule PR. Merged: the kit as merged is read back (at the merge commit), and each open item whose `learned:` line is there is accepted with that line's text as its rule (the owner's hand wording wins), the merge being the yes; a general rule (and an exception whose general rule the session found wrong, `correct`) goes to the toolkit queue with that text. An item whose line the merge doesn't hold is `missing`: neither accepted nor rejected. Closed unmerged: what was left is rejected. Either way its worktree is removed. When the branch's head moved, its `learned:` lines are checked against the items, and nothing is decided for the owner: an open item whose line keeps its marker takes the line's text as its rule; an open item with no line, and a rejected item whose line the owner put back, are listed under the rule PR in progress.md («Waiting for you», with how to answer), and the line put back stays. The runner removes a line only for a rejected item whose removal its own push didn't carry (a push that failed); once removed, it never removes it again. A «N — "текст"» for an item with no line puts the line back. A new comment of the owner's (`forge.self`, not one with the comment header or one the pass posted; with the trigger word or without it: a rule PR is the owner's own thread) is a reply by number (`resolveRuleReply`, on `parseReply`'s grammar); another person's comment is never obeyed. «N — так» keeps the rule; a no removes its line and rejects it: a no word followed by the end, punctuation or a dash («N — ні», «ні, це факт», «no.»), or a no phrase («не треба», «не додавай», «прибери», «відхили»); a no word followed by more words («ні в якому разі», «no problem») is asked back, and «не проблема» is no no; «N — "текст"» puts the text in as the rule; a reply that is just a kind («загальне», «продуктове правило», «тільки для цього проєкту», «виняток із загального») changes its kind (an exception with no rule it overrides is asked back); a kind and more («загальне, але коротше») is a kind change and a rewording; anything else is a rewording by description, which one learner session words, gated like the week's (the comment, and the ones after it, wait while the gate is closed). That session may also answer that the owner meant no (`reject`), only another kind (`kind`), or ask back (`ask`). A number the PR doesn't have, a rule removed already, numbers named together or twice are asked back. The runner commits the change to the branch (`labels.answerCommit`) and pushes; only once the push went through do the items' states change and the comment count as seen (a failed push keeps nothing, and the comment is read again). Then it rewrites the description and replies with the numbered list of what it did (a failure there is only noted). An owner's comment that reads as no reply by number is listed under its rule PR in progress.md («Waiting for you»), never dropped silently. A rejected rule's every wording is named to every later session and refused in its result.

**The toolkit PR (point 5).** With `learning.toolkit`, one queued rule per pass, with the session gate open, and only while no other toolkit PR is open (one at a time, so two never take the same rule number): a worktree of the toolkit's clone at `origin/<base>`, one learner session that picks an existing rule file by subject and writes the rule in that file's language and form, and the runner adds it with `lib/rule-insert.mjs` (AC-3): the next free number, the file's heading form (`### ЖN — Назва (English name)`) or its list form (`N. **Name** …` under a heading that names the rules), after its last rule, with the rule's marker (`<!-- learned:<id> -->`, the line after the heading, at the end of a list item), the parts most of its rules hold, the checklist line when the file has a checklist (with its `(ЖN)` when the lines before it name their rules so), the row of the table at its top when the rule needs one, its cross-references (`(Ж1)`, `${CLAUDE_PLUGIN_ROOT}/…`) checked. A file in neither form, the wrong language, a missing part, a reference to no rule, or a name of the host's is refused, and nothing is pushed. The host's names: `learning.names` (required with `toolkit`: the product's and the company's names, which the settings can't know), the repos and their own words (split on `-` and `_`, generic words such as DOC, API or PORTAL left out), the logins, the hub's folder and its words. Then the toolkit's real lint in the worktree, a commit, a push of `learned-rule-<id>` and a PR into `base`, in English, for the owner alone. A step that fails is `failed` with its reason (`learn status`), its worktree removed, and is not tried again by itself. A toolkit PR merged or closed has its worktree removed. Once the toolkit file the plugin runs from holds the rule's marker (the switch), the next weekly host PR removes the host's copy by its marker.

**An exception (point 6)** stays in the host's kit. When the session marks the general rule wrong (`correct`), its toolkit PR corrects that text (`find`, found once, and `replace`, put in literally: a `$&` in it is text). A correction goes to a rule file or a distilled corpus (GDSG, MSSG, UA grammar) only, never a skill, a command or a script; in a corpus only with the primary source (`source`, a URL); in the file's own language; and a rule heading it touches keeps the file's heading form. No rule is ever added to a corpus.

**Files.** `<state>/learning/edits.jsonl` (the log), `cursor.json`, `proposals.json` (the start week, the last pass's time, the weeks, the tries, the rules with their wordings, kinds and states, the rule PRs with their items, seen and unclear comments and worktrees, the used lines, the sessions' costs, the notifications sent), `trees/` (the runner's worktrees: one made before is put at its ref clean, forced and its untracked files removed, inside the tree only; removed after a merge, a close or a failure). The role sessions can't write any of it: only `<state>/tmp/`.

**Beside the misses log (TASK-105).** The answer pass's misses log proposes rule lines for the writer role and the hub's rules from what a session missed, with its own state and a rolling seven-day cadence. The two never share a file: this learning writes only `<state>/learning/` and the host kits' `product-rules.md` (through rule PRs) and the toolkit's rule files (through toolkit PRs), and its step 5c comes after the check's hand-ons.

## `trace`

`trace <key> [--root <hub>] [--settings <file>] [--stage <name>]` answers one question a reviewer can't answer from a PR: did the unattended sessions of this ticket go to the app, or copy the ticket? It reads the ticket's ledger (`runs[]`, `plan`, `card`) and the transcript of each run, `<claude config dir>/projects/<slug>/<session>.jsonl` (the config dir is `CLAUDE_CONFIG_DIR`, else `~/.claude`; the slug is the host root with every `/` and `.` as `-`), and prints plain text, with no model and no JSON mode. It writes nothing and does not build the live world of `status`: no tracker, no forge.

- **Header:** the ticket key, the card link, the number of sessions, their total time and cost (a shared session counts the ticket's `share`), the plan's pages and live-check decision, and, when the settings declare `workFolder`, the file names in the ticket's work folder.
- **One section per run,** in `seq` order: stage, role, model, effort, trigger, start (local time), duration, turns, cost, outcome, then a count line (`read 12, searched 3, ran 20 (app 1), wrote 5, refused 0, failed 1`; `app` is counted inside `ran`; skills, agents and other tools are added when there are some) and one line per action, `HH:MM:SS <kind> <what>`. Kinds: `read`, `search` (Grep, Glob), `ran` (Bash, Monitor), `app` (a Bash command with `playwright` in it), `wrote` (Write, Edit, NotebookEdit: the path only), `skill`, `agent`, `other` (the tool's name). A line with no timestamp shows `--:--:--`.
- **After an action whose result was an error:** `refused: <first line>` for a permission or hook refusal, `failed` and nothing else for any other error. Then the session's last text block, cut to 400 characters.
- **Subagents:** a session's `<session>/subagents/*.jsonl` are printed under the run, each marked `subagent <id>`, and counted in the run's count line.
- **A shared session** (triage handles several tickets; the run's `share` is below 1) prints all its actions, with a note of about how many tickets it handled. Lines are not attributed to a ticket.
- **A run with no `session`, or whose transcript is gone** (the CLI removes old ones) prints its ledger facts and `transcript not found`; that is not an error. A transcript that exists but can't be read (a folder, no permission, too large for one string) prints `transcript unreadable`, with no detail, and the report goes on; a session id that is not a plain file name (it starts with a dot, say) is treated as no session. The transcript is read whole into memory; streaming is not done.
- **`--stage <name>`** prints only that stage's runs. A name that is no stage is exit 2. No ledger for the key is exit 2.

What it never prints: a tool's result (apart from the first line of a refusal), the content of a Write or an Edit. Paths are shortened (a ticket worktree as `<wt:repo>`, the toolkit's own install, the plugin folder this script sits in, as `<toolkit>`, each `targets[].path` as its folder's name, the host root as `.`), `--root` and `--settings` are dropped from commands, a command is cut at 200 characters, and control characters (C0 and C1, the escape sequences of a terminal) are removed from everything it prints, the ledger's fields included. Masking is best effort: it covers the forms it knows and promises no more. Those are the value of a flag, `NAME=value`, `NAME: value` (a header) or `"NAME": "value"` whose name has `token`, `key`, `secret`, `password`, `passwd` or `pwd` in it, an `Authorization` header (the scheme stays), a `Bearer` value, `-u user:password`, and the password of `scheme://user:password@host`; each is shown as `***`, and the cut comes after the masking. A secret in any other shape is printed as it is. A transcript holds the actions and the texts a session wrote, not the model's private reasoning, so the command shows those and nothing more.

`trace` is for people. When `DOC_TOOLKIT_ROLE_SESSION` is set in the environment it refuses (exit 2): a role session has no reason to read other sessions' transcripts.

## `status` output

`tickets[]`: `key`, `group`, `ledger` (`present` or `absent`), `priority`, `createdAt`, `mode`, `startedBy`, `stage` (the last recorded), `card`, `state`, `next` (the first of `steps`, or null; with `waits` and `prior` after a failed session), `steps`, `gate` (`who`, `why`), `mismatch`, `notes`, `prs` (each with `id`, `stage`, `state`, `labels`, `head`, `next`, `expertReview` (the `pr` record's recommendation, or null), `approvalStale`, the UA pages changed after the approval, and with `forge.keepFresh` `behind`, the commits of its base the head lacks, or null when git here can't tell, and `notReady`, why a PR the rule keeps from ready for merge isn't ready for its head yet; with `forge.wontMergeLabel`, `dropped` (`{ label }`) on a PR closed with it), `counts` (`inProgress`, `waiting` or null), `counted`, `locked` (with `derivedState`), `hand`, and after a failed session `failed` (`stage`, `pr`, `at`, `sessions`, and `acted` or `held`) and `held` (a ready ticket's failed start too); at the daily session cap `capped` (`stage`, `pr`, `sessions`) and `held`. A start step in `next` names its origin (`startedBy`), with `byHand` for a card a person moved into work or `again` for a recorded start that goes on. Then `intake`, `groups` (with `waitsFor`, the tickets in work it waits for, and `waitsWhy`, for each the test that holds it: `{ key, by }`, `by` being `relation`, `together`, `named` or `page`, a page with `page`, `from` (`pr` or `triage`), `pr`, the PR's number, and for the triage's `why` (`noPr`, `filesUnknown`, `renamed` or `session`); `closed: true` for a ticket whose PR was closed unmerged; with `failedStart` when a member's start failed: `held`, `waits`, `sessions`, `at`), `wip` (`inProgress`, `waiting`, `open`, `openKeys`, `limits`, `manual`), `allowance` (`day`, `cap`, `used`, `remaining`, `inWork`, `inWorkUnknown`), `estimates`, `startable` (with `prior`, the failed start sessions so far, when there are some; in `easiest` order with `sizeRank`, `repoCount` and `pageCount`), `notStarted` (with `reasons`), `notTickets`, `locks`, and `requests` (what was sent to the tracker and the forge, by method; `writes` is empty).

## Exit codes

`0` ok · `1` a record or a lock refused (nothing written; `refused` in the JSON), or a call to the tracker or the forge failed · `2` bad usage or configuration (an unknown command too, as in the `tracker` and `forge` scripts); for `trace` also an unknown stage, no ledger for the key and a role session. On `1` and `2` stdout holds `{"ok": false, "error": …}` and the message goes to stderr.

## Limits

- The stages' own work (triage rules, writing, the review chain, the video transcriber) belongs to the host's skills and the role sessions; the runner only starts them and checks their records. With no transcriber set (`video.transcriber`, `video.browserProfile`), there is no automatic video try and the gate goes to the person. The adapter's selectors are confirmed only by a pilot on the live site: a change there reads as an unexpected page, and falls back to the person.
- The watcher and its LaunchAgent are macOS-first: on another system run `watcher.mjs --quiet` from any scheduler; nothing else changes, and no notification is sent.
- The watcher reads events only for tickets with a ledger; whatever it misses, the morning run reconciles from the full state.
- A full check still waits for two kinds of session: a triage (the morning run's, a start pass's) and a due host job (a skill job is a `claude -p` session, up to its `timeoutMinutes`). Meanwhile no other full check runs. Tickets' steps and starts run in processes of their own.
- Several runs now write `progress.md` and its memory at once: the "current run" lines are the last writer's (its own steps), while each ticket's ⏳ comes from its ledger's `running` record, whichever process runs it. Two writers can still both send one "your turn" notification.
- Each run handed on reads `/usage` itself after each of its sessions, so several runs ending at once still read it at once; their first reading is the check's.
- A detached run, or a full check started by a tick, goes on after `launchd.mjs uninstall` or `mode off` (the runner reads the mode when it starts): it ends by itself, or by its pid (`handOns` in `watch/forge.json` and `watch/feed.json`, the full check's own in `watch/active/owner.json`). The full check and the forge check keep apart `notified` memories, so one reason can be told twice in a day; and two processes writing `progress.json` at once (above) happens more often now.
- The morning run, and a run that finishes a ticket for another step, answer comments with no quiet wait: the start rule is held at the watcher's hand-on only. A review submitted with one line comment and no text reads as a single comment, and waits its 2 minutes.
- `status` reads git in the target repos at `targets[].path`, after fetching a head the forge has and the clone doesn't; a head that still isn't there (the fetch failed: offline, a password asked) is noted, and hand edits and stale stages aren't checked for it until a later check fetches it.
- A step with no worktree checks only the clones of the targets its tickets name, for the branch and the base: a clone with uncommitted changes to tracked files on its base gets no note, and the brief's note is advice, not a rule a session can't break.
- The daily session cap (`limits.sessionsPerStageDay`) counts every session of the stage, the ones that succeeded too, and it holds a manual run as well: by design, as a safety net for a loop of any cause. `set retry <key>` lifts it.
- The retry up the model ladder runs right after the failed session, with no look at the cap in between, so a pair that starts below the cap can end one session over it.
- The resume of a session that stopped on a text message runs right after it, with no look at the guard or the cap: it finishes a step already paid for, and the pair counts as one session.
- A resumed session restores the first one's cost, so a role with `maxBudgetUsd` may meet its budget soon after the resume, or at once: that ends as a failed step, as it did with no resume.
- A move of the card there and back counts as a person's action by the card's own moves, and those include the pipeline's own scripted moves (another PR's recorded move, say). That costs at most one extra try, and the daily cap bounds it.
- A dead token goes untold when no awake stretch reaches an hour (the hour counts awake time only: a laptop opened for 45 minutes between sleeps of over an hour), or when the Mac is awake only before `schedule.morning` (the tracker and the forge are told from then on). A host job that keeps failing in such short stretches is never disarmed either: it is tried at each check.
- A network drop that starts in the middle of a check, after its reads (in `status`, a run or a watched list's lists), fails that part at once, and its urgent notification goes out at once (the first time that day).
- A gap day gives two urgent notifications, the daily one and the gap's, and the gap's isn't held until `schedule.morning`: on a Mac that stays awake, a token that dies at 02:00 sounds at 02:00 the next night.
- `import` and the morning removal's close write ledgers without taking the group's lock: a `handover` that lands between their read and their write is lost (run it again). Neither runs a session, and the morning one writes only a ticket still in the owner's hands with nothing recorded into it since the import.
- A `runner.mjs` run started by hand without `--manual` is a scheduled run: it is guarded, and the groups it starts count for the limits.
- After a sleep of more than 24 hours, if the first check fails, that check is the gap: the source starts again from it, and the events of the sleep are never read. A card that arrived in a watched list meanwhile doesn't arm its job. The tickets are still reconciled by the morning run, and the report lists the cards left in each watched list. To be fixed before a host relies on a watch job.
- The `git -C` allow rules name the worktree's path literally, so a session that writes the path another way (a trailing slash, a `..` in it, a link to it) is denied, and so is a quoted path; the brief writes it in full and unquoted. A plain read after a `cd` works only as two calls: `cd <worktree> && git …` is denied. A commit message that names `--output` is denied too (`git * --output *`). A `*` in a deny rule can span words, so the `-C` denials name the worktree rather than `*`; the other mutating commands have no `-C` allow rule, and their plain spelling is denied.
- A hub's own unscoped write rule (`Edit(**)`) keeps its checkout writable for role sessions until the host drops it ("Writes are an allow list"). What a role writes with a Bash command isn't on the allow list at all.
- A step with no worktree may write in any `.sources/` folder of a target clone, the hub's too when the hub is a target, not only the ticket's section, and so in a state folder under one wherever a denial names nothing: its ledgers, locks, reports and Markdown ledgers are denied, another top-level file there isn't.
- A plan step's spec stays in the clone after the ticket closes: `screenshot-tests/` is git-ignored, so no commit or merge takes it, and the close step's cleanup doesn't touch it (it removes only what a stage recorded, inside the host repo and the state root). `_plan-*` files build up there until someone removes them. A spec runs with the session's own rights, as any Playwright run does.
- A key with a hyphen shares its spec names with a longer one: `_plan-d9-*` also matches `_plan-d9-8-x.spec.ts`. Keys are a team number or a short link, so this doesn't arise today.
- The docs lookup matches terms as written, case and all: a page that names a field in other words, or a UI label in another form, is not found. A sibling doc repo is read at its `origin/<base>` as last fetched: the runner fetches a target's clone for a read checkout, but not a `docRepos` repo that is no target, so its pages may be behind, and a session cites such a page from its excerpt alone (three lines at most), with no way to read the rest. The earlier tickets' work folders are read as they are on disk, never at a ref.
- The ticket's commits are read from the history of each repo's fetched base only: a commit on a branch not merged into it yet, or older than the last 500 commits that hold the key as text, isn't listed. The runner's clone fetches only the base.
- A worktree folder that exists but isn't the clone's worktree (a leftover) stops the stage until it is moved away; the runner never removes it.
- The image check of `record align` runs only where the PR's worktree is on this machine; elsewhere the record says it was not checked.
- A finding is matched to an open card by the session (`card`) or by its fingerprint, an exact match once case, punctuation and spacing are set aside: two sessions that word one problem differently, and name no card, file two cards (triage's `duplicate` verdict is the net). The runner reads no board for people's cards on its own: a bug filed by hand is linked only when the session names it. Two runs that route the same new finding for two tickets at the same moment, each under its own group's lock, can both file it.
- A skill job that keeps failing is tried at each check until its hour is up: about 12 model sessions at the default 5 minutes, against 2 when two failures in a row disarmed it. The guard reads `/usage` before each try and stops it at the day's allowance.
- The style check of a person's edits is the writer's session: the scripts give it the commits and the pages, keep its fixes, notes and the shas it read, and refuse a malformed record, but whether a fix keeps the edit's meaning, and whether a plain comment quotes a sentence of the page, is the session's reading, checked by no script.
- Without `styleCheck.since`, the first check after the style check arrives reads every UA hand commit on an open PR in the owner's queue that no style check read and that came after the PR's last ready head (with no ready head, all of them). Set it to leave the existing PRs alone.
- A hand commit pushed together with the owner's move to In translation (within 10 minutes) is not style-checked: the move approved it. A check already running when the owner moves the card later than that still pushes its fixes; the chain translates them, and the owner reads them on the summary's numbered list.
- A hand commit's own diff is computed again at every check until a style check records it (one `git diff` per such commit); an EN-only commit is never recorded, so its diff runs at every check.
