# Проєктні конвенції форматування

Цей файл — **rank-0 шар** проєктних правил. Він вантажиться для **кожного** профілю гайда
(`gdsg@uk`, `gdsg@en`, `mssg-en@en`, `mssg-ua@uk`, `ua-grammar@uk`), і під час написання, і
під час перевірки. Процедуру завантаження визначає
`${CLAUDE_PLUGIN_ROOT}/context/style-guide-registry.md`, розділ «Project rank-0 layer» — вона тут
не дублюється.

**Як цей файл співвідноситься з корпусами:**

- Правило звідси **переважає** будь-яке правило корпусу. Конфлікт із корпусом розв'язується
  **мовчки**: проєктна форма — правильна, це не відхилення й не привід для findings.
- Порушення правила **звідси** — звичайна знахідка перевірки з посиланням на цей файл.
- Там, де правило корпусу вже все сказало, тут стоїть **посилання** на нього, а не переписаний
  текст. Копіювати правила корпусу сюди заборонено — корпус лишається єдиним джерелом.
- Там, де правила в корпусі **немає**, стоїть позначка **проєктне рішення**.

### Ж1 — Жирний = видима мітка UI (Bold = visible UI label)

Жирний позначає **тільки** видиму мітку елемента інтерфейсу (кнопку, поле, пункт меню,
вкладку, підпис поля в адмінці) **і мітку пункту списку** (термін, що визначається, у форматі
`- **Термін:** пояснення`). Це два дозволені випадки, і за їхні межі жирний не виходить. Назва
елемента керування лише з іконкою (його підказка чи `aria-label`) — теж мітка UI для цього правила (Ж8). Для
мітки UI написання зберігається дослівно таким, як його показує інтерфейс — **з єдиним
винятком**: декоративна кінцева пунктуація нормалізується за Ж1a нижче.

- **Жирний як емфаза — заборонено.** Ані для «важливого» речення, ані для назви модуля чи
  фічі. Якщо факт важливий — винеси його в окреме речення або в `:::note`, а не виділяй.
- **Мітка пункту списку — структурний виняток, не емфаза.** У пункті списку, що визначає
  термін (`- **Термін:** пояснення`), жирний покриває **термін разом із двокрапкою**; решта
  пункту — звичайний текст. Коли термін — це мітка UI, двокрапка стоїть **зовні** жирного, бо
  вона пунктуація речення, а не частина мітки (Ж1a): `- **Receiving**: транзакції, що…`. Так жирний
  span дорівнює рядку застосунку, і його можна звірити зі словником інтерфейсу. **Як розрізнити:**
  термін — мітка UI, коли це назва елемента, який читач бачить на екрані (поле, колонка, кнопка,
  вкладка, розділ, фільтр), і `ui-labels lookup` знаходить її серед рядків застосунку; інакше це
  звичайний термін (поняття, тип, категорія), і двокрапка всередині жирного. Літеральне значення
  статусу — Ж1, рядок про жирний і `code font`: `- **`QUASI`**: …`. Це той самий принцип, що й мітка UI: жирний
  позначає структурну роль (тут — заголовок пункту), а не важливість вмісту.
  Приклад: `- **Картка:** поля CardNumber і CardCoded заповнені; поле Link порожнє.` Якщо
  жирним виділено більше за термін із двокрапкою — увесь пункт, речення без структури
  «термін: пояснення» — це вже емфаза, і вона заборонена (перший пункт вище).
- Літеральне значення, показане в UI, — **жирний і `code font` разом**.
- Не жирни назву продукту, фічі, модуля чи репозиторію, якщо це не мітка UI.

**Джерела корпусу:** `GDSG-FORMAT-TEXT` (`formatting/text-formatting.md`) — «Do not combine
styles for general emphasis», «A literal value shown in the UI uses both bold and code
formatting»; `GDSG-UI-001` (`technical-content/ui-elements-and-interaction.md`) — «Do not bold a
product or feature name unless it is the visible name of the UI element», «preserve its displayed
wording».

**Проєктне рішення понад корпус:** корпус каже «formatting sparingly», проєкт каже
**ніколи** — заборона жирного як емфази беззастережна, винятків немає. Мітка пункту списку
(вище) не є винятком із цієї заборони: вона взагалі не емфаза, а структурна роль, як і мітка
UI, — тому й підпадає під той самий рендер.

| ⛔ Не так | ✅ Так |
|---|---|
| **Транзакція закривається повністю автоматично**, без участі оператора. | Транзакція закривається повністю автоматично, без участі оператора. |
| у відповідь повертається **лінк на віджет** | у відповідь повертається лінк на віджет |
| Модуль **REST Proxy** є посередником… | Модуль `REST Proxy` є посередником… (назва модуля — Ж4) |
| The transaction **is closed fully automatically**. | The transaction is closed fully automatically. |
| **Картка, IBAN, посилання, квазі, телефон: заповнене тільки поле `Link`.** (жирний на весь пункт — емфаза) | **Картка, IBAN, посилання, квазі, телефон:** заповнене тільки поле `Link`. (жирний на термін разом із двокрапкою — мітка пункту) |
| поле **A-Bank Collection ID** | поле **A-Bank Collection ID** — мітка UI, жирний правильний |

### Ж1a — Нормалізація декоративної кінцевої пунктуації в мітках UI

Це **проєктний override rank-0** над «написанням дослівно» з Ж1 і над `GDSG-UI-001`
(«preserve its displayed wording»): у документі мітка UI **не** зобов'язана нести декоративну
кінцеву пунктуацію, яку кнопка чи заголовок показують у самому інтерфейсі. Конфлікт із корпусом
розв'язується мовчки; порушення цього правила — звичайна знахідка з посиланням на Ж1a.

**Дві репрезентації однієї мітки — розрізняй їх:**

1. **Точна спостережувана мітка** — те, що інтерфейс показує буквально. Живе там, де важлива
   точність збігу: у доказах (`app-notes.md`), селекторах, значеннях для автоматизації. Тут
   пунктуація **зберігається повністю** — `Create!`, `Receiving:`, `What's new?`.
2. **Документаційний рендер** — форма всередині жирного span у прозі. Тут **декоративна кінцева
   пунктуація прибирається** зсередини `**…**`; речення отримує власну пунктуацію **зовні**
   жирного.

**Що прибирати, а що лишати в документаційному рендері:**

- **Прибери** кінцевий декоративний знак: `!`, `:`, `?`, `.`, `…` — коли він є лише
  оформленням кнопки/заголовка, а не частиною сенсу мітки. Три крапки, якими кнопка показує, що
  відкриє вікно (`Зберегти як…`), — теж оформлення.
- **Збережи внутрішню пунктуацію й символи** всередині мітки: `Save & close` лишається
  **Save & close**, `What's new` — апостроф на місці.
- **Пунктуацію речення став зовні жирного span**, а не всередині: `натисніть **Create**.`, а не
  `натисніть **Create!**`.

| Спостережувана мітка | Документаційний рендер | Коментар |
|---|---|---|
| `Create!` | натисніть **Create** | декоративний `!` прибрано, крапка речення — зовні |
| `Receiving:` | у розділі **Receiving** | декоративна `:` прибрана; «section/розділ» — звичайний текст поза span |
| `What's new?` | відкрийте **What's new** | декоративний `?` прибрано, апостроф збережено |
| `Save & close` | натисніть **Save & close** | `&` — внутрішній символ мітки, зберігається |
| `Receiving:` у пункті списку | `- **Receiving**: транзакції, що надходять на рахунок` | двокрапка списку — пунктуація речення, тож зовні span |

**Не змінюй ніколи** (нормалізація стосується лише кінцевого знака мітки UI в прозі):

- сам інтерфейс і скріншоти;
- селектори й сирі докази з застосунку (`app-notes.md`, значення для автоматизації);
- ідентифікатори коду й літеральні значення статусів (`**`QUASI`**`, `code font`);
- дослівно процитовані системні повідомлення (у лапках, з усією їхньою пунктуацією);
- внутрішні апострофи, дефіси, скісні риски, крапки версій і символи, що ідентифікують елемент
  (`What's new`, `Re-send`, `Import/Export`, `v2.1`, `Save & close`);
- крапку скорочення, що є частиною слова (`Ред.`, `Тел.`).

**Якщо після нормалізації від мітки не лишається корисного тексту** (мітка була лише знаком чи
іконкою — напр. кнопка з самим `+` або `→`) — не залишай порожній жирний span; веди елемент за
**Ж8** (елемент керування лише з іконкою), а не за декоративною міткою.

**Джерела корпусу:** `GDSG-UI-001` (`technical-content/ui-elements-and-interaction.md`) —
«preserve its displayed wording». **Проєктне рішення понад корпус:** саме нормалізація
декоративної кінцевої пунктуації в документаційному рендері (при збереженні точної мітки для
доказів і селекторів) — проєктна; корпус вимагає дослівності, проєкт її тут пом'якшує.

### Ж2 — Плейсхолдери (Placeholders)

Плейсхолдер записується як **`*PLACEHOLDER_NAME*`**: великими літерами, з підкресленнями як
роздільниками, курсивом.

**Заборонено:** рядок зірочок (`**********`), рядок `x` (`xxxxx`), одиничний `x`, «щось»,
«…», `<тут ваш ID>`, присвійні префікси `MY_` / `YOUR_`, дефіси й пробіли в імені.

**Стосується і плейсхолдерів усередині URL-прикладів.** Це окремо названо, бо саме там їх
пропускають: URL виглядає як цитата з UI, і замаскована частина проїжджає непоміченою.

| ⛔ Не так | ✅ Так |
|---|---|
| `https://pay.a-bank.com.ua/collection/**********` | `https://pay.a-bank.com.ua/collection/*COLLECTION_ID*` |
| `POST /transaction/xxxxx` | `POST /transaction/*TRANSACTION_ID*` |

Кожен плейсхолдер пояснюється при першому вживанні, навіть якщо значення здається очевидним
(`GDSG-PLACEHOLDER-001`, розділ «Explain placeholders»). У fenced-блоці форматування не здатне
відрізнити плейсхолдер від коду — там працює тільки ім'я та пояснення поруч.

**Джерела корпусу:** `GDSG-PLACEHOLDER-001` (`technical-content/placeholders.md`) — «Use a
descriptive uppercase name with underscore delimiters», «Do not use a single `x`, a row of x
characters…», «Do not include possessive adjectives».

**Проєктне рішення понад корпус:** корпус для Markdown пропонує курсивний код — *`PROJECT_ID`*.
Проєкт обрав **курсив без зворотних лапок** — `*PROJECT_ID*` — і тримається його всюди. Корпус
це прямо дозволяє («If uppercase underscore form conflicts with the host language or interface,
use a clear project convention consistently»). Перевірка **не** повідомляє про це як про
відхилення.

### Ж3 — Одна сутність, один рендер (One entity, one render)

Для кожної сутності обирається **рівно один** спосіб написання, і він тримається по всьому
документу — і далі, по всьому набору документів.

Змішування рендерів — помилка **навіть тоді, коли кожен окремий рендер сам по собі
правильний**. Читач сприймає зміну рендеру як зміну сутності.

**Антипатерн із реального кейсу** — одна сторінка, одне поняття, чотири рендери:

```
`QUASI`   «квазі»   quasi   квазі
```

**Як розв'язувати.** Спочатку визнач роль за Ж4 — і рендер зафіксовано. Якщо під однією
англійською фразою реально ховаються **різні** сутності (константа в коді, значення в запиті,
поняття для читача) — це не одна сутність із чотирма рендерами, а три сутності, кожна зі своїм
рендером. Тоді вони мусять і **називатися по-різному** в прозі:

- поняття → метод квазі *(звичайний текст)*
- внутрішня константа → `QUASI` *(code font)*
- значення `paymentMethod` у запиті → `quasi` *(code font)*

Що не можна: писати «метод `QUASI`» в одному абзаці і «метод quasi» в наступному, маючи на
увазі те саме.

**Реєстр обраних рендерів — глосарій.** Колонка **Рендер** у `glossary-ua.md` / `glossary-en.md`
набору продукту є нормативною: рендер сутності береться звідти, а не вигадується на місці. Сутності, якої там
немає, місце в глосарії, а не в прозі з імпровізованим рендером (див. Ж4, останній пункт).

**Проєктне рішення** — прямої норми в корпусі немає; `GDSG-FORMAT-TEXT` вимагає лише «use
formatting consistently and sparingly».

### Ж4 — Код-сутність проти поняття (Code entity vs. human concept)

Це правило вирішує, **якою мовою** і **яким рендером** записати англомовний термін.

| Роль сутності | Мова | Рендер | Приклади |
|---|---|---|---|
| **Існує в коді**: константа, поле БД, query-параметр, назва структури, назва модуля, назва репозиторію, ендпоінт | англійською, **як у коді** | `code font` | `paymentMethod`, `QUASI`, `CardCoded`, `MonoCFG UUID`, `WidgetMonoHost`, `REST Proxy` |
| **Людське поняття** | мовою документа, термін із глосарію | звичайний текст | `payment method` → платіжний метод; `payment type` → тип платежу |
| **Видима мітка UI** | дослівно, як показує інтерфейс (декоративна кінцева пунктуація — Ж1a) | **жирний** (Ж1) | **A-Bank Collection ID**, **Додати картку** |

**Четверта ситуація — сигнал про діру в глосарії.** Англійський термін стоїть у прозі, для
нього **немає** затвердженого перекладу і його **немає** в коді. Це не привід вигадати рендер на
місці. Дії, у цьому порядку:

1. Додати запис у `glossary-ua.md` / `glossary-en.md` набору продукту разом із колонкою **Рендер**.
2. Синхронізувати двомовний `glossary.md`, якщо набір продукту його має.
3. Поки термін не затверджено — поставити поруч
   `{/* NEEDS CONFIRMATION: термін «…» не має затвердженого перекладу */}` і вжити робочий
   варіант **однаково по всьому документу** (Ж3).

Без набору продукту глосарію немає, тож лишається тільки крок 3.

Що не можна: лишити англійське слово в українській прозі «як є» тільки тому, що так казав SME.
Мова інтерв'ю — не рендер документа.

**Джерела корпусу:** `GDSG-CODE-001` (`technical-content/code-in-text-and-samples.md`) — перелік
код-сутностей, які йдуть у `code font`, і «Do not use code font for an ordinary product, service,
organization, domain name»; `GDSG-UI-001` — про мітки.

**Проєктне рішення:** саме тришарове розділення ролей (код / поняття / мітка) і вимога брати
поняття з глосарію — проєктні; корпус описує рендери, але не процедуру вибору ролі для
іншомовного терміна.

### Ж5 — Назва репозиторію (Repository name)

Назва репозиторію — у `code font`, як і шляхи всередині нього.

| ⛔ Не так | ✅ Так |
|---|---|
| `src/handlers/refunds` у репозиторії billing-api | `src/handlers/refunds` у репозиторії `billing-api` |
| **billing-api** | `billing-api` |

**Проєктне рішення.** У корпусі прямої норми **немає**: `GDSG-CODE-001` перелічує «filenames and
paths, package names», але репозиторій не згадує, а протилежний пункт того ж правила («Do not use
code font for an ordinary product, service, organization») можна прочитати і як заборону. Проєкт
знімає цю неоднозначність на користь `code font` — назва репозиторію є літеральним технічним
ідентифікатором і в реченні майже завжди стоїть поруч зі шляхом усередині нього.

### Ж6 — Документуємо as-is (Document as-is)

У тілі сторінки — **тільки поточна поведінка**.

Плани, майбутні зміни, наміри команди («планує вивести з використання», «буде замінено»,
«скоро додамо»), не оголошені публічно фічі — **тільки** у вигляді закоментованого маркера:

```
{/* ToDo: <що планується> — оновити, коли зміна з'явиться в коді */}
```

Ніколи — у тілі сторінки. Ніколи — у `:::note`, `:::tip` чи `:::warning`: admonition є частиною
сторінки, а не коментарем.

⛔ Не так — у тілі сторінки:

```
:::note
Команда розробки планує вивести спосіб підтвердження через `approve` з використання,
але на цей момент цей метод активний.
:::
```

✅ Так — факт у тексті, план у коментарі:

```
Метод `approve` активний і не позначений у коді як застарілий.

{/* ToDo: команда планує вивести `approve` з використання — оновити, коли в коді
з'явиться позначка deprecated */}
```

**Джерела корпусу:** `GDSG-PRINCIPLES-PRECISION` (`principles/precision-and-longevity.md`) —
«Document available behavior, not unannounced or planned functionality», «Do not pre-announce a
feature in product documentation without the required legal and release approval», «Prefer present
tense for current behavior», а також розділ «Timeless documentation» щодо «на цей момент»,
«наразі», «currently», «recently», «soon».

**Проєктне рішення:** конкретна форма винесення — `{/* ToDo: … */}` — проєктна; вона діє в парі
з `{/* NEEDS CONFIRMATION: … */}` для непідтверджених фактів.

### Ж7 — Мова заголовків (Heading language)

Заголовок пишеться **мовою контенту документа**. Змішаний заголовок заборонено.

- Код-сутність у заголовку допустима — у `code font` (Ж4).
- Поняття, що має термін у глосарії, у заголовку вживається українською/англійською за
  документом, а не мовою джерела чи інтерв'ю.
- Регістр — sentence case (`GDSG-STRUCTURE-HEADINGS`, `GDSG-LANGUAGE-ABBREVIATIONS`).

На українській сторінці:

- ⛔ `### Payment method і payment type` — змішаний заголовок, англійські поняття мають терміни
  в глосарії.
- ✅ `### Платіжний метод і тип платежу` — обидва поняття українською.
- ✅ <code>### Параметри `paymentMethod` і `paymentType`</code> — якщо розділ справді про
  параметри запиту, а не про поняття: тоді це код-сутності й вони лишаються англійськими в
  `code font`.

**Проєктне рішення** — корпус одномовний (`languages: [en-US]`) і питання змішування мов у
заголовку не розглядає взагалі. Регістр заголовків при цьому лишається за корпусом.

### Ж8 — Іконки та кнопки без підпису (Icon-only controls)

Деякі елементи керування мають лише іконку, без тексту. Крок усе одно називає такий елемент
словами. Іконка в кроці — лише орієнтир, щоб читач знайшов елемент на екрані.

**Дерево рішень.** Пройди його для кожного такого елемента в кроці:

1. **Елемент має корисну текстову мітку після нормалізації за Ж1a** → лише жирна мітка (Ж1),
   без іконки. Мітка з самого знака (`+`, `→`) після Ж1a порожня — такий елемент іде гілками 2–3.
2. **Лише іконка, назва відома** — підказка (tooltip) або `aria-label` з доказів: `app-notes.md`,
   нотатки автора, інтерв'ю SME → жирна назва й дескриптор, а перед назвою — іконка в рендері
   `Icon rendering:` (таблиця нижче). Назву пиши дослівно, як у підказці, з нормалізацією за Ж1a.
3. **Лише іконка, назви в доказах немає** → опиши елемент словами за формою й контейнером («кнопка з
   трьома крапками в рядку платежу»), а не за напрямком (Ж9), постав у кінці рядка
   `{/* NEEDS CONFIRMATION: назва кнопки з <форма> — у доказах немає підказки чи aria-label */}`
   мовою сторінки (на англійській сторінці — англійською) і все одно додай іконку як орієнтир.
   **Ніколи не вигадуй назву за формою іконки:** кошик не
   означає «Видалити», доки цього не каже інтерфейс.

Iconify дає зображення, а не назву. Назва приходить тільки з доказів.

**Іконка не дублює текст.** Зображення іконки має `alt=""`: назва вже стоїть поруч текстом.
Крок мусить читатися правильно, якщо зображення прибрати. Колір і розмір іконки не задаються з
пам'яті: компонент успадковує колір тексту (`currentColor`), тому правильний і в темній темі;
висота — `20`.

**Рендер задає поле `Icon rendering:`** у блоці «Documentation toolkit configuration» проєкту,
поруч зі `Style guide:` (`${CLAUDE_PLUGIN_ROOT}/context/project-paths.md`). Поле розв'язують лише
скіли, що пишуть нову розмітку іконки: три `*-writer`, `doc-page-updater` і `identify-ui-icon`, і
лише тоді, коли сторінка справді має елемент лише з іконкою. Якщо поля немає:

- **Сторінки сайту вже мають компонент `<Icon`** (`grep -rl '<Icon' <корені контенту>`) → не бери
  типове значення. Один раз запитай, який рендер використовує сайт, першим запропонуй
  `iconify-component`, і запропонуй дописати відповідь у декларацію. До відповіді не пиши
  розмітку іконки й не зберігай сторінку. Це питання конфігурації, як шляхи в `project-paths.md`:
  «пропусти питання» його не скасовує.
- **Компонента `<Icon` на сайті немає** → бери `screenshot-crop` без питання, скажи про це у звіті
  й один раз запропонуй дописати декларацію.

`doc-translator`, `doc-style-reviewer` і `doc-style-fixer` поле не розв'язують, нічого не питають і
дописати декларацію не пропонують: вони працюють з розміткою, яка вже є на сторінці.

**Стару форму іконки на наявній сторінці** (напр. `<Icon … height="24" style={{ color: … }} />`)
не виправляють механічно. Рецензент повідомляє її як знахідку, що потребує рішення (група 3,
judgment-required, у `doc-style-fixer`), а не як заміну розмітки: форма могла бути свідомою, а
рендер сайту, можливо, не задекларовано.

| Значення | Що пише автор | Що потрібно сайту |
|---|---|---|
| `iconify-component` | `<Icon icon="mdi:delete-outline" height="20" /> **Видалити**` | Пакет `@iconify/react`; компонент `Icon` зареєстрований глобально в `MDXComponents` (swizzle) |
| `iconify-svg` | `<img src={require('./.assets/delete-icon.svg').default} height="20" alt="" /> **Видалити**` | Перевірка до увімкнення (нижче) |
| `screenshot-crop` (типово) | `<img src={require('./.assets/delete-icon.png').default} height="20" alt="" /> **Видалити**` | Нічого понад звичайні скріншоти |
| `describe` | Без зображення: назва й дескриптор, а в гілці 3 — опис | Нічого |

У таблиці — лише рендер іконки й назви. Дієслово й дескриптор стоять за правилами мовних
розділів нижче. Вирізка й SVG лежать у `./.assets/` сторінки. Ім'я файлу — за дією, якщо її
відомо, інакше за формою: `delete-icon.png`, `dots-vertical-icon.svg` (`screenshot-selection.md`,
«Rename»). Компонентові `<Icon>` не додавай `style`,
`color` чи `width`.

**`iconify-svg` вмикай лише після перевірки сайту.** У Docusaurus `require('./x.svg').default`
повертає або URL файлу, або React-компонент (SVGR). З компонентом `<img src={…}>` не працює, і
тоді правильна форма — `require('./.assets/delete-icon.svg?url').default`. Збери одну сторінку з
такою іконкою, подивися, що вийшло, і лише тоді декларуй `iconify-svg` з потрібною формою. SVG у
`<img>` не бачить колір тексту сторінки, тож перевір іконку і в темній темі.

**Коли потрібен скіл `identify-ui-icon`.** `iconify-component` і `iconify-svg` потребують id
Iconify, `screenshot-crop` — вирізку кнопки. Якщо докази вже їх дають (id в `app-notes.md`, файл
`*-icon.png` у `.assets/`), бери їх. Інакше виклич `identify-ui-icon`: він знаходить id або робить
вирізку, а коли певності немає — повертає маркер. Назву він не визначає. Для `describe` скіл не
потрібен.

**Джерела корпусу:** `GDSG-UI-002` (`technical-content/ui-elements-and-interaction.md`) — «click a
button, icon, link»; `GDSG-VISUALS` (`visuals/images-and-media.md`) — «Use empty alt text for a
purely decorative image»; `MWSG-SHARED-UI-INTERACTIONS` (`shared/procedures/ui-interactions.md`) —
«Include the noun after an icon label when needed»; `MWSG-SHARED-VISUAL-ACCESSIBILITY`
(`shared/accessibility/visual-and-media-accessibility.md`) — «Do not duplicate nearby text in alt
text», «Do not hard-code colors that become unreadable in high-contrast themes».

**Проєктне рішення:** дерево з трьох гілок, маркер для невідомої назви, поле `Icon rendering:` і
типове значення `screenshot-crop`.

### Ж9 — Місце елемента: контейнер, а не напрямок (Locate by container, not direction)

Текст сторінки не показує читачеві дорогу напрямком: ліворуч чи праворуч, вгорі чи внизу, над
чи під іншим елементом, у куті екрана, на лівій панелі. Екранний читач не бачить, що «праворуч»;
у мовах, що пишуться справа наліво, і на вузькому екрані розкладка інша. Слова для кожної мови —
у мовних розділах нижче.

**Що писати замість напрямку:**

1. **Контейнер** — сторінка, вікно, панель, вкладка, розділ, рядок, поле, меню, панель
   інструментів, де стоїть елемент. Контейнер з видимою міткою — жирним (Ж1), перед дією
   (`procedure-steps.md`, правило 4): «У вікні **Переказ** натисніть **Підтвердити**».
2. **Власна мітка елемента** часто знімає питання «де» зовсім: кнопку **Прибрати** читач знайде
   за назвою, напрямок нічого не додає.
3. **Зв'язок з названим елементом без напрямку** — лише коли контейнера немає: «біля поля
   **Тема**», «у рядку файлу». Він однаковий в будь-якій розкладці.
4. **Скриншот** (`screenshot-capture.md`, рамка навколо елемента), коли елемент усе одно
   складно знайти.

Місце в самому документі — так само без напрямку: «у наступній таблиці», «у попередньому
розділі», а не «у таблиці нижче», «вище».

**Контейнер не вигадуй.** Його назва береться зі сторінки або з доказів (`app-notes.md`,
скриншот, інтерв'ю SME), як і назва елемента (Ж6, Ж8). Якщо доказ дає тільки напрямок («кнопка
ліворуч від поля»), напиши зв'язок без напрямку (пункт 3) або, коли й елемента-орієнтира
немає, `{/* NEEDS CONFIRMATION: де стоїть <елемент> — у доказах лише напрямок */}`.

**Не порушення:** напрямок, який є самою дією або вмістом, а не дорогою до елемента: провести
чи перетягнути в бік, клавіші зі стрілками, мітка UI зі словом напрямку (**Закріпити праворуч**,
Ж1 — дослівно), значення налаштування (вирівнювання **Ліворуч**), порівняння («сума вище
ліміту»). Опис поведінки, на який читач не спирається, щоб знайти елемент, теж не порушення.
Рецензент його не позначає, а наявну сторінку автор не переписує заради нього.

**Джерела корпусу:** `GDSG-A11Y-001` (`principles/accessibility.md`) — «Don't use directional
language to orient the reader»; `GDSG-PROCEDURES` (`procedures/procedures.md`, «Step details»);
`MWSG-A11Y-005` (`shared/accessibility/writing-for-accessibility.md`) — «Do not rely on direction
alone».

**Проєктне рішення:** правило діє в кожному профілі, і в `mssg-*` теж, хоча Microsoft допускає
напрямок поряд з іншим орієнтиром: сторінки йдуть далі в інші локалі та до екранних читачів.
Також проєктні — зв'язок «біля **X**» як запасний варіант і маркер, коли доказ дає лише напрямок.

- [ ] Назви репозиторіїв — у `code font` (Ж5)?

Стара форма іконки на наявній сторінці, яку зараз не пишуть, — знахідка-рішення (група 3, judgment-required), ніколи не механічна.

## Українською

Розділ діє для документів українською мовою. Правопис сюди не входить — він у
`${CLAUDE_PLUGIN_ROOT}/context/doc-rules/ua-grammar/`, маршрутизація через `INDEX.md`.

### Термінологія

- Канонічні терміни — з `glossary-ua.md` набору продукту (`${CLAUDE_PLUGIN_ROOT}/context/project-paths.md`, «Product kit»)
  разом із колонкою **Рендер**. Глосарій нормативний: він задає і термін, і його написання.
- Ключові заміни термінів, якщо продукт їх має, — у `product-rules.md` набору продукту.
- Новий термін, якого в глосарії немає, спершу додається в глосарій — див. Ж4.

### Назви, бренди, латинка

- Назва продукту та її скорочення — за `product-rules.md` набору продукту.
- Технічні абревіатури — латинкою, без кирилічної транслітерації: API, UUID, IBAN, JSON, HTTP,
  URL. Не «АПІ», не «апі», не «джейсон».
- Назва платформи, продукту чи фічі — звичайним текстом, не жирним (Ж1).
- Назви розділів інтерфейсу продукту, якщо вони мають особливе написання, — у `product-rules.md`
  набору продукту.
- При першій згадці нового скорочення — повна форма + скорочення в дужках, далі тільки
  скорочення (`GDSG-LANGUAGE-ABBREVIATIONS`).

### Лапки

Правописна основа — «ялинки» «…», вкладені — „…" (правопис § 164; файл
`ua-grammar/05f-quotes-slash.md`). Проєктне уточнення до неї:

- UI-мітки в лапки **не беруться** — вони жирні (Ж1): натисніть **Зберегти**, а не натисніть
  «Зберегти».
- Системні значення й статуси в лапки **не беруться** — вони в `code font` (Ж4): статус
  `success`, а не статус «success».
- Дослівний текст системного повідомлення береться в «ялинки» і виділяється жирним:
  з'являється **«Токен недійсний»**.

### Заголовки, списки, процедури

- Sentence case у заголовках і пунктах списків: «Фільтрування транзакцій», не «Фільтрування
  Транзакцій».
- Вступне речення перед нумерованим списком — **повне**, із двокрапкою: «Щоб {ціль}, виконайте
  такі дії:». Не «Щоб {ціль}:» і не «Поля:».
- Однокрокова процедура — коротка форма: `**Щоб {ціль}:**` + маркер `—`. Формула «виконайте такі
  дії» лишається тільки для нумерованого списку.

### Стиль речення

- Інструкція — наказовий спосіб 2-ї особи множини: **натисніть**, **виберіть**, **перевірте**.
  Не інфінітив: ⛔ «Вибрати транзакцію».
- Поведінка системи — теперішнім часом: ✅ «система відкриває форму», ⛔ «система відкриє форму».
- Активний стан, друга особа: ✅ «Ви переглядаєте транзакцію», ⛔ «Транзакція переглядається».
- Порядок «мета → дія»: ✅ «Щоб застосувати фільтр, натисніть **Застосувати**.»
- Числа: до 10 — словами («три кроки»), від 10 — цифрами («12 транзакцій»); точні дані завжди
  цифрами («128 символів»). Між числом і одиницею — нерозривний пробіл.
- Косу риску не вживай замість «та/або»: ✅ «переглянути або редагувати», ⛔
  «переглянути/редагувати».

### Елементи керування лише з іконкою (Ж8)

- Порядок: контейнер, дія, дескриптор, іконка, назва. ✅ «На панелі інструментів натисніть кнопку
  `<іконка>` **Більше**.»
- Дієслово — за дескриптором: кнопку **натисніть**; піктограму **клацніть**, на сенсорному екрані —
  **торкніться** (`MWSG-UK-DOCUMENTATION`, `uk-ua/documentation/titles-typography-and-ui.md`,
  «Посилання на UI»). «Клацніть» — норма для піктограми, а не калька «клікнути».
- Дескриптор: **кнопка**, коли елемент виглядає як кнопка; **піктограма**, коли це сама іконка й
  її форма важлива. Не нанизуй два дескриптори: ⛔ «піктограма кнопки»
  (`MWSG-UK-CAP-DESCRIPTORS-PREPOSITIONS`, `uk-ua/language-standards/capitalization-descriptors-prepositions.md`,
  «Дескриптори»).
- Гілка 3, назви немає: ✅ «У рядку платежу натисніть кнопку з трьома крапками `<іконка>`.» і
  маркер у кінці рядка. ⛔ «натисніть кнопку **Меню**», коли «Меню» ніде в доказах немає.

### Місце елемента (Ж9)

- Слова напрямку, які Ж9 забороняє для орієнтації: **ліворуч, праворуч, зліва, справа, вгорі /
  угорі, внизу / унизу, зверху, знизу, над, під, вище, нижче**, «у правому верхньому куті», «на
  лівій панелі», «у правій частині», «наведений нижче».
- ⛔ «Кнопка зі скріпкою ліворуч від поля **Напишіть повідомлення**.» → ✅ «Біля поля **Напишіть
  повідомлення** натисніть кнопку зі скріпкою `<іконка>`.» (Ж8, гілка 3, з маркером).
- ⛔ «Натисніть **Прибрати** праворуч від назви файлу.» → ✅ «У рядку файлу натисніть
  **Прибрати**.»
- ⛔ «Перевірте комісію під полем.» → ✅ «Перевірте комісію у вікні **Переказ**.»
- ⛔ «У таблиці нижче…» → ✅ «У наступній таблиці…»; ⛔ «як описано вище» → ✅ «як описано в
  розділі [Назва](/шлях#id)» або «у попередньому розділі».
- Не плутай із порівнянням і дією: «сума вище ліміту», «проведіть картку ліворуч» — не порушення.

### Кальки й слова-заборони

Правопис цього не покриває — це проєктні заборони.

| ⛔ Не так | ✅ Так |
|---|---|
| натисніть **на** кнопку | натисніть **кнопку** / виберіть **кнопку** |
| на стороні API | з боку API |
| клікнути | натиснути |
| заскролити | гортати |
| зайти у систему | увійти в систему |
| являється | є |
| даний (у значенні «цей») | цей |
| в залежності від | залежно від |
| не дивлячись на | попри / незважаючи на |
| здійснити | виконати |
| відкрити доступ | надати доступ |
| по API / по інструкції | через API / згідно з інструкцією |
| при відправці | під час відправлення |
| слідуючий | наступний |
| вірний (у значенні «правильний») | правильний |

## English

This section applies to English-language pages. The Core section above applies unchanged — the
ban on emphasis bold, the placeholder form, the one-entity-one-render rule, the code-entity/concept
split, repository names in code font, as-is documenting, and heading language are not
language-specific.

### Terminology

- Canonical terms come from the product kit's `glossary-en.md`
  (`${CLAUDE_PLUGIN_ROOT}/context/project-paths.md`, "Product kit"), including its **Render**
  column. The glossary is normative for both the term and its rendering.
- Key term substitutions, when the product has them, are in the kit's `product-rules.md`.
- A term that isn't in the glossary yet gets added to the glossary first — see Ж4.

### Names, brands, abbreviations

- The product name and its abbreviation follow the kit's `product-rules.md`.
- Technical abbreviations stay as-is: API, UUID, IBAN, JSON, HTTP, URL.
- A platform, product, or feature name is ordinary type, never bold (Ж1).
- Expand a new abbreviation at first mention, then use the short form only
  (`GDSG-LANGUAGE-ABBREVIATIONS`).

### Quotation marks

- Straight double quotation marks; punctuation placement follows the corpus
  (`punctuation/quotes-parentheses-ellipses-and-slashes.md`, which is `scope: mixed` — its
  US-English clauses apply on an English project).
- No quotation marks around a UI label — it is bold (Ж1): click **Save**, not click "Save".
- No quotation marks around a system value or status — it is code font (Ж4): the `success`
  status, not the "success" status.

### Headings, lists, procedures

- Sentence case for headings and list items (`GDSG-STRUCTURE-HEADINGS`).
- A full introductory sentence ending in a colon before a numbered list: "To {goal}, do the
  following:". Not "To {goal}:" and not "Fields:".
- A single-step procedure uses the short form: `**To {goal}:**` followed by an em-dash bullet.

### Sentence style

- Steps use the imperative: **click**, **select**, **enter**, **press**. Not the infinitive.
- System behavior in present tense: "the system opens the form", not "the system will open the
  form".
- Active voice, second person (`language/grammar-person-and-voice.md`).
- Numbers: spell out under 10 in prose, use numerals from 10 up; exact data always in numerals.
  Non-breaking space between a number and its unit (`GDSG-FORMAT-NUMBERS`).
- Don't use a slash for "and/or": "view or edit", not "view/edit".
- US spelling per the corpus. A literal code value keeps the spelling of the code, even when it
  differs (Ж4); the prose around it still follows US spelling. A product's own exceptions are in
  the kit's `product-rules.md`.

### Icon-only controls (Ж8)

- Name the control with its bold name and a noun, the icon in front of the name: "In the toolbar,
  click the `<icon>` **More** button." The noun names the element type: **button** or **icon**.
  It also keeps a name that reads like an action from standing bare (`MWSG-SHARED-UI-INTERACTIONS`).
- The verb follows the project's declared style guide (`${CLAUDE_PLUGIN_ROOT}/context/style-guide-registry.md`):
  **click** for `gdsg` (`GDSG-UI-002`), **select** for `mssg-en`. Don't mix the two on one page.
- Branch 3, no name in the evidence: "In the payment row, click the three-dots button `<icon>`."
  with the marker at the end of the line, in English: `{/* NEEDS CONFIRMATION: name of the
  three-dots button — no tooltip or aria-label in the evidence */}`. Never "click the **Menu** button" when "Menu" appears
  nowhere in the evidence.

### Where an element is (Ж9)

- The direction words Ж9 rules out for orientation: **left, right, left-hand, right-hand, top,
  bottom, upper, lower, above, below, over, under**, "in the upper-right corner", "in the left
  pane", "the following diagram" rather than "the diagram below".
- ⛔ "The paperclip button to the left of the **Write a message** field." → ✅ "Next to the
  **Write a message** field, click the paperclip button `<icon>`." (Ж8, branch 3, with the marker).
- ⛔ "Click **Remove** to the right of the file name." → ✅ "In the file's row, click **Remove**."
- ⛔ "Review the fee below the field." → ✅ "In the **Transfer** window, review the fee."
- ⛔ "In the table below" → ✅ "In the following table"; ⛔ "as described above" → ✅ "as described
  in the preceding section" (`GDSG-A11Y-001`).
- Not a breach: a comparison or the action itself, such as "an amount above the limit" or "swipe
  left".
