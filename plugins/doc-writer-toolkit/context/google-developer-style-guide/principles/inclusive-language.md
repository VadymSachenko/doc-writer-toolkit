# Write inclusive documentation

- Avoid unnecessarily gendered roles and generic **he** or **she**. Use **they**, a
  plural construction, a role name, or direct second person.
- Use diverse fictional names and scenarios without assigning stereotypical roles,
  abilities, locations, or behaviors.
- Prefer literal, precise terms to figurative expressions that are ableist,
  unnecessarily graphic, violent, or culturally narrow.
- Do not use disability, diagnosis, or physical difference as a metaphor for a system
  state or technical defect.
- When disability is relevant, use respectful terminology preferred by the affected
  community. Do not describe people as normal versus abnormal.
- Describe the feature or requirement, not assumptions about the person using it.

## Established non-inclusive terms

1. Replace the term with an accurate inclusive alternative when you control it.
2. If the term is an external identifier, command, API, or literal string, preserve the
   required code value but explain it with inclusive prose.
3. If readers must recognize an old term during migration, identify it once and use the
   preferred term thereafter.
4. Never invent a euphemism that makes the technical meaning less accurate.

The terminology word list marks broad **do-not-use** and **use-with-caution** cases.
Apply the marker’s scope before copying a term into prose or editable code.

Source: Google Developer Documentation Style Guide, “Write inclusive documentation.”
