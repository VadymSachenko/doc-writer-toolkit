# Working unattended

The runner of the ticket flow (`scripts/ticket-state/`) appends this to every role's instructions. It started you with `claude -p` for one stage of one ticket or group, with no person present.

- **No one answers.** A question in the chat goes nowhere, and a tool call your permissions don't allow is denied, not asked. When the stage can't go on, record it failed with the reason and stop.
- **One command per Bash call.** No `&&`, `||`, `;`, pipes, heredocs or `$(…)`. Headless runs deny compound calls. Change directory with a `cd` call of its own; it carries to the next call. A check reads each command as a shell would, and refuses what it can't read without running it: a variable, a substitution, a glob at the start of a word, a redirect into a file, an environment assignment. A `$` in a commit message goes in single quotes. When a command is refused, do the same work in a form that passes: one plain command per call, literal paths, or the Read, Grep and Write tools. That means another form of allowed work, never another way into something forbidden: never go around a refusal of a path or of a thing your role may not do. Only when no such form exists, record the stage failed with the reason.
- **Files with the Write tool.** A comment text, a description or a long JSON result goes into a file you write with the Write tool, under the ticket flow state folder (`tmp/` in it), and its path goes to the script (`--text-file`, `--body-file`, `--result-file`). Write your files only in the folders your brief lists; if a write is refused, never try another way around it.
- **The owner's checkouts stay as they are.** Never `git checkout`, `git switch` or `git pull` in them. Write and edit pages only in the worktree, by its path, and give a skill the worktree's path, never a clone's or the hub's: a clone's content roots are not writable on a step with a worktree, and a `write` record is refused unless the worktree holds the commits, pushed. Work in the worktree your brief names: the runner made it at the branch's head, detached, with the clone's `node_modules` (and any other file the settings name) already linked, and it removes it after the merge. This replaces the worktree and link steps of the host's git rules: never create, move or remove a worktree, never link a file into one, and never run `npm ci` or `npm install`. Run git there as `git -C <worktree> <command>` with the path exactly as the brief writes it, unquoted. A read (`status`, `diff`, `log`, `show`) may also run as plain git after a `cd` to the worktree as a separate call; an `add`, a `commit`, a push and a fetch run only as `git -C <worktree>`, and any other spelling is denied, a quoted path and `cd <worktree> && git …` among them. Your session starts in the hub, the owner's checkout: a plain add or commit would land there. Never write a file with git's `--output`, and search with the Grep tool, not `git grep`. A command that contains `--output` anywhere is denied, so a commit message must not contain it. Push with the exact command your brief gives (`git -C <worktree> push origin HEAD:refs/heads/<branch>`), fetch with `git -C <worktree> fetch origin` (or `… fetch origin <branch>`), never a refspec of your own. Every other push, fetch, `git branch`, `stash`, `cherry-pick` or `mv` is denied: the worktree shares the owner's branches. A rejected push means someone else pushed to the branch: record the stage failed with that reason and stop. Never force a push (`--force`, `-f`, `--force-with-lease`, a `+` refspec), never push with `--no-verify`, and never delete a remote branch. A brief with no worktree for a stage that needs one, or a worktree note you can't get past, is a failed stage: record it with the reason.
- **Scripts by name.** Run the toolkit's scripts as `node <the path your brief or skill gives>` and nothing else: never `node -e`, `-p` or `--eval`, a script of your own, `python3`, a shell (`sh -c`, `bash -c`), `find -exec` or `xargs`; they are denied. Of `ticket-state`, run only `record`, `status` and `config`; the other commands are the owner's. Never pass `--source` to `ui-labels` or `--playwright-from` to `visual-pack`. Never read a `.env` file (denied; `.env.example` is fine): where a skill says to read `.env` for credentials, the Playwright spec reads it in its own process, so name the variables, never their values. Never write to a `.git/`, `.claude/` or `.github/` folder, a `CLAUDE.md` or `CLAUDE.local.md`, `node_modules/`, the toolkit's own scripts, `package.json`, a lockfile, the ticket flow's settings, or its state outside `tmp/`.
- **Every tracker and forge change goes through the scripts:** `scripts/tracker/tracker.mjs` for cards (comment, labels, moves, descriptions) and `scripts/forge/forge.mjs` for PRs (open, edit, review comments on lines, replies, suggestions, labels). Never compose a REST call, a `curl`, or a `gh` command.
- **Texts the team reads** follow the host's templates, in the team's language, impersonal, with no tool, model or plugin names and no commit trailers.
- **The comments you post** on the tracker and the forge (a triage, a plan, a question, a summary, a reply, a line comment) start with the settings' comment header, which the scripts put in front: write the message only, never the header, and keep its first line the one the host's template gives, which `--unless-header` and the pipeline's markers read. The layout is the host's template's, by these rules, and changes no number and no wording: sections, each under the template's heading, in its order, and an empty one left out; an item of a numbered list of edits gives its number in bold, then `` `file` · section · block ``, then the before and after texts, each on its own line in a quote, and on the forge a block longer than about 300 characters is folded in `<details>`; the questions are numbered, each with what the template asks of it (the place, why it is a question, the proposal) as items under it, but on a PR a question about an item of the list of edits names that item's number and takes none of its own, so a number in the owner's reply always means an item. On the tracker only bold, lists and `code`: no headings, quotes or folding. PR descriptions and commit messages take no header.
- **Never** merge, approve, dismiss a review, resolve a conversation, close a PR, delete a branch, archive or delete a card, or set the owner's merge-ready label. The scripts have no operation for any of these.
- **Record the stage when it ends**, with the command in your brief: `done` with its result, or `failed` with the reason. A writer's `plan` or `write` that ends by asking records only `questions`, not the stage itself. A record the tracker, the forge or the files don't support is refused: fix the cause, never the record. Run `ticket-state status --ticket <key>` to see what the ticket's state is now, unless your brief says the stage needs no status call.
- **Name the work files you leave outside git.** Every file or folder the stage created or downloaded that git doesn't track and the pages don't need (a video and its parts, audio, a transcript, frames, a downloaded attachment, a run folder, a clone) goes into the record's result as `"files": [{ "path": "<from the host root>", "kind": "video|videoPart|audio|transcript|frames|attachment|runDir|clone|other" }]`. When every PR of the ticket is merged, the close step moves them to the Trash; the distilled notes (`sme-interview.md`, `app-notes.md`) stay. A path you don't record is never removed, and you never remove one yourself.
