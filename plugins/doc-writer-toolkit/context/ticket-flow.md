# Ticket flow

A docs ticket is a card on the team's board that changes the documentation. The ticket flow takes it from the intake to the merged PRs, mostly unattended: a script decides what runs next, and each step that needs a model is one `claude -p` session in one role. `${CLAUDE_PLUGIN_ROOT}/scripts/ticket-state/` holds the decisions (`ticket-state.mjs` and `runner.mjs`, see its `README.md`); the host holds the rules of the work itself (triage, templates, the page locator, git), named in its settings under `hostRules`.

**The world wins.** The tracker, the forge, git and the files are the truth. The ledger keeps only what they can't show (verdicts, the PRs' review kind, the heads a stage saw, the questions, the places, the costs), and the rule reads the world on every call. A person can move a card, edit a branch or answer on the card at any time; the next run follows.

## Statuses

The tracker module speaks in statuses, which the host maps to its lists (`tracker.statuses`): `intake`, `drafts` (never read), `ready`, `inProgress`, `blocked`, `smeReview`, `finalReview`, `translation`, `done`, `outOfScope`. `finalReview` is the owner's queue; `smeReview` is the expert's review, which a person calls; `translation` is where the chain runs, and only a person's move starts it. The flow reads every status except `drafts`; it reads `done` and `outOfScope` only for the cards of open ledgers.

## Ticket states

| State | | Counts as |
|---|---|---|
| `new` | In the intake, not triaged. | |
| `ready` / `needsInfo` | Triaged; `needsInfo` while the needs-info label is on. | |
| `planning` | Started: gathering, the plan, the answers back. | in progress |
| `questions` / `planGate` / `videoGate` | Waiting on the owner: answers, the section plan, the video transcripts. | waiting |
| `writing` | The UA pages, the UA review, the answer pass (with the host's company repos), the PRs. | in progress |
| `smeReview` | A PR in the expert's review: a person moved the card there from the owner's queue, or requested a reviewer on the forge. The expert's Approve, or a person's move, takes it on to the owner's queue. | |
| `reworkWait` / `ownerBlock` / `paused` | A person moved the card back to In progress, to Blocked, or to the ready status. | waiting (`paused`: nothing) |
| `finalReview` | The owner's read of the UA: right after the `pr` stage for every PR, `sme` and `places` alike, with or without places, after a reviewer's move, after the expert's Approve, and after a UA change on a PR that was ready for merge. Starts nothing. | |
| `translation` | A person moved the card to In translation: the chain on the PR. | |
| `readyForMerge` | The chain done for the head: the owner's final edit and merge. | |
| `merged` / `closed` | Every PR merged; closed after the close step or a person's move to done. | |
| `outside` | The card archived, gone or outside the flow, or a PR closed unmerged. | |
| `locked` | A run holds the group; `derivedState` is what it is doing. | as derived |

A ticket in `mode hand` (the owner's, or rebuilt with no ledger) is observed only: its state is shown, nothing runs, it counts for nothing. `handover` gives it to the pipeline.

## The rule

A pure function of the ledger and the world. First match wins:

| # | When | State; next step |
|---|---|---|
| 1 | A live lock on the group | `locked`; nothing |
| 2 | `mode hand` | the derived state; nothing; reported |
| 3 | The card archived, gone, or in a list outside the flow | `outside`; reported |
| 4 | Every PR merged | `merged`; `close` |
| 5 | A PR closed unmerged | `outside`; reported |
| 6 | The card's list differs from the one the ledger left it in | a person moved it: follow the move (below) |
| 7 | A stage recorded `running` with no live lock | interrupted: run it again |
| 8–12 | Per PR, each on its own: with the translated label, first a UA change in words since the translations were made → `untranslated`, no model step; commits the pipeline didn't make (a hand edit: kept and noted; in the owner's queue, once the new comments are answered, the UA ones no style check read → `styleCheck`, below; at In translation they are recorded as seen); after ready for merge, a UA change, whoever made it → `move` back to `finalReview`, no model step (a hand commit that left UA alone → `readyForMerge` for its head, the pack first if it changed an image); a PR at `finalReview` with a new review a person requested → `move` to `smeReview`, with the target's card members; new review comments (not the pipeline's own, a line comment of a review it posted included; not a review the owner hasn't submitted yet; the owner's are instructions, a reply by number and a suggestion among them, below) → `answerComments`; a PR at `smeReview` that a reviewer approved since it entered the review → `move` to `finalReview`, no model step (after its new comments); `translation` → the first chain stage not done for the head, then `readyForMerge`; for a PR that was ready for merge before, `resync` over the range since the ready head instead; with `forge.keepFresh`, from ready for merge on, the base merged in when it moved (`baseMerge`, no model), a conflict resolved by a session (`baseFix`), and `readyForMerge` only once CI passed on the head (below) | the least advanced PR's |
| 13 | `videoGate` | with `video.transcriber` and `video.browserProfile` set, the automatic try (`videoTry`: uploads, at most `partsPerDay` a day across every ticket, the oldest gate first; in a later run, every `fetchMinutes`, the look for each uploaded part's transcript); the fallback to the person on the first failure, or with the try off (`videoBlock`: Blocked, with the gate comment); once every part has its transcript, the runner's frame sweep (`videoExtract`), then the import (`videoImport`) |
| 14 | `ready` and a free slot | `start` (the `startable` groups) |
| 15 | Otherwise | the state's own step: `start`, `plan`, `write`, `uaReview`, `answerPass` (only with the host's company repos), `pr` |

**The video gate (row 13).** The automatic try is a script with no model (`scripts/transcriber/`, the adapter `video.transcriber` names): a browser in a persistent profile outside every repo, where the owner signed in once by hand; no password is stored and no session value printed. Every role is denied reading or writing the profile and its lock, and the role hook refuses a command that names them; a Playwright spec a writer session writes could still open the profile by its path, so it is signed in with an account of its own for the service. The try opens a browser only inside `limits.startHours`. Each part is uploaded once (one try per part per run, never a retry loop); a later check fetches what is ready, saving the plain-text export with timestamps under the part's `transcript` name. Any failure (a sign-in wall, a captcha, the day's limit, an unexpected page, no transcript within `transcriptHours`) is one fallback: the card to Blocked with the gate comment, and the report lists the parts to upload by hand, with the reason. A transcript dropped in by hand is taken the same way. Once every part has its transcript, whatever the video settings, the runner sweeps the video's frames itself (`videoExtract`: `sme_video_context.py` with every part's transcript at its start, so Whisper never runs), and the writer's `videoImport` session runs `convert-sme-input` on the merged transcript and the frames. Without the venv, `tesseract` or `ffmpeg`, or when the sweep fails or times out, it is skipped with the reason, never held, and the import runs on the parts' transcripts with no frames. The interview it gives is supplementary evidence: the code, the app and the API come first (context/ticket-roles/writer.md). Whisper runs only on the owner's word. scripts/ticket-state/README.md, "The video gate", has the details.

**The answer pass (row 15).** With the host's company repos set (`companyRepos`), a writer's session runs between the UA review and the PR whose only job is to answer what the write, the branch's markers and the UA review left open: each item has an answer in the company's systems, and the session is told to find it, with every company repo, the docs, the earlier tickets and the test environment in reach. Each item ends answered (with its evidence), confirmed (a place seen working) or kept (with every source tried), and only the kept ones reach the owner. A stage's own question is never an item. With review rounds, the questions a round asks wait for the same pass on the PR before they are shown. An item settled later from a source already in reach is a line of the misses log, which the week's report groups by the kind of source and turns, for a kind seen twice, into one proposed rule line. Unset: no pass, the PR follows the UA review.

**A person's move (row 6).** Ready → In progress: a manual start, unless the runner recorded a start for the ticket before (its own start session moved the card, or a person moved it after that start failed): then that start goes on, as it was started. Blocked → In progress: the answers (the question's PR only, if it was a PR's), the plan approved (or a new gate if the plan file changed), the video import (or on without the video). To Blocked or back to ready: the owner's block or a pause, nothing runs. To review, final review, In translation or done: the PRs at the card's stage follow, with their stage label; done closes the ticket. To review, the move calls the expert (below). A move past the final review status (to In translation or done) takes the check label off the PRs it moves (below). A move to In translation is the only UA approve: from any status, it keeps the head (`approval`) and takes every open PR of the ticket below ready for merge, so one card approves the whole ticket and no PR left behind pulls the card back while the chain runs; a ready PR stays ready, unless its head moved since it was marked ready by the owner's own commits only, with no session of the pipeline's on it since (a hand edit the pipeline had no time to send back to the owner's queue): the move approves that change, and the PR goes too. A commit of the pipeline's in that range (an answer pushed while the owner moved the card) is one the owner hasn't read: that PR goes back to the queue first. Back from In translation stops the chain between steps. On a PR with two cards, a move of either into In translation or back out of it takes the other card along.

**The expert review is the owner's call.** After the `pr` stage every PR opens with no reviewer and lands in the owner's queue, whatever its review kind; the two kinds differ only in what the writer adds (places) and who the expert is. The writer's `pr` record says per PR whether it recommends an expert review and why (`expertReview`: the open questions for the expert, the facts not found in the code or the UI), and `status` and the report show it; nothing waits on it. A person's move of the card to the review status calls the expert of each PR that follows the move: its target's `review` label, a review request to its targets' `reviewers` on the forge, and its targets' `cardMembers` on the card, each PR its own targets' people. A review a person requested on the forge from the owner's queue moves the card the same way and adds the card members; the person chose the reviewer. A second call asks no one twice and adds no one twice. Nobody is ever removed from a PR or a card, whichever way the card moves: a move back from the review takes the pending requests along, so they move nothing again. A recommended one also puts `forge.expertLabel` on the PR when it opens (the `pr` record adds it; nobody takes it off). Each time a PR enters the review, by a person's move or a review requested from the owner's queue, it gets the comment `forge.reviewComment`, when the host set one (in the team's language; there is no default): the link to its Files changed tab and GitHub's way to approve, «Review changes» → «Approve» → «Submit review». The pipeline posts it from the owner's login and keeps its id in `posted`, so it is never read as the owner's.

**The expert's Approve moves the card** (D-082). A PR in the review that one of its experts (its targets' `reviewers`, or a reviewer requested on it) approved since it entered the review goes on to the owner's queue by itself: the card to the final review status (or, with two PRs, where the slower one is), the review label to the final review's, and the approval kept at the head the expert approved (`expertApproval`). The approval is read from the reviews: only the PR's experts count, each one's last verdict counts, one asking for changes holds the PR, the latest approval since the PR entered the review moves it, and an approval from an earlier round, before a move back into the review, moves nothing. New comments are answered first; while no one approved, the summary of an answer to the expert's comments ends with one line asking them to approve, with the link and the path. A person's move on from the review stays the override, for an expert who says it is fine elsewhere: it is recorded as the approval at the head then (`by: person`). The owner can't approve their own PRs on GitHub, and silence is never an approval: the report lists each PR in the review whose expert has been quiet for `schedule.expertQuietDays` working days (2), with the text to send them when `forge.reviewComment` is set. When the triage moves a card into the ready status, its record adds the owner (`tracker.owner`) to the card; a failure to add is a warning, and nothing is refused for it.

**After the chain** every PR of the ticket is ready for merge, each with the ready label, and the card goes back to the final review status with `tracker.readyComment`, so that status always means the owner's turn. A person moving it to In translation again with nothing changed starts no model step: a ready PR stays ready, and the card comes back. A question on a PR in the chain brings it back to the owner's queue after the answer, not into the chain.

**A session that stops on a text message** (in `claude -p` a message with no tool call ends the session) with nothing recorded for its step is resumed once, with the same command and a prompt to finish the stage or record it failed; only if it still records nothing is the step failed, once. Only the first attempt is resumed, never the retry up the ladder, and the resumed process gets what is left of the session's timeout. A session the runner killed, one at max turns, one that recorded anything, one whose record was refused, and one on a PR branch a person moved meanwhile are never resumed.

**A failed step** runs again only after a person acts on the ticket later than the failure (a comment, a review, a hand commit, a move of the card), after `ticket-state set retry <key>`, or once at the next morning run. The pipeline's own writes never count. Two failed sessions with no person's action between them hold the ticket for the owner: no next step, one notification, one line in the report. A failed start counts the same: the runner records each start before its session, so a start whose card never left the ready status leaves the ticket `ready` (counted for nothing; its group waits and holds no slot), and one whose card is in work is `planning`, counted, its start going on as it was started. Whatever the cause, a ticket has at most `limits.sessionsPerStageDay` (3) sessions of one stage a day; beyond them it is held the same way until the next day.

**Two PRs** (one repo per review kind, or two repos). Each PR moves on its own; the card stands where the least advanced PR is. Both land in the owner's queue after `pr`; a move to the review calls each PR's own expert. An approved PR in the review goes on to the owner's queue by itself; while the other is slower the card waits with it, and the report lists the approved one. Both wait for the card: one card can't approve half a ticket. A question on one PR stops only that PR.

**The chain** of a PR at `translation`: `translate`, `enReview`, `locales`, `align`, `labelSync`, `build`, `visualPack`. Each stage keeps the head it saw; a UA page changed after that head makes it and every later stage stale, unless the change is id-only (`scripts/ticket-state/README.md`, "The id-only change"). The approval (a person's move to In translation) keeps its head the same way: a later word change in UA is reported as a mismatch, not undone. `align` is recorded only when no UA image the branch changed lacks its EN counterpart, in a host whose screenshot locales include `en`. `build` is the runner's own step, with no model: the host's `build.command` (default `npm run build`) in the PR's worktree at the head, recorded ok or failed with the error's tail. It is the PR's one full build: the `locales` stage runs the locale-translator with `--no-build`, and the visual pack reuses the build of its head. One pipeline build runs at a time on the machine (the build lock); a session that still builds the site (a re-sync, a visual pack with nothing to reuse) runs under it. A session that fails because a person's commit moved the branch under it (a push rejected, a record refused as stale) is no failure: no bigger model, no hold, and the step the status gives at the new head runs (`scripts/ticket-state/README.md`, "A branch moved under a session", "The site build", "The build lock").

**The stage label** of a PR follows its stage: `inProgress` at writing and rework, `review` at the review, `finalReview` in the owner's queue and at ready for merge (the target's `labels`, set by `forge set-stage-label`, which adds the new label and removes the target's other stage labels in one request). In the chain a PR carries the target's `translation` label, when the target names one: the `follow` of a person's move to In translation sets it on every PR the move takes, a ready PR taken along for the owner's own commits too (once its record took it); `readyForMerge` puts the `finalReview` label back on that PR at once, whether or not the card is still waiting for another PR; a move back out of In translation sets the label of the stage the PR goes back to. A ready PR sent back to the owner's queue (row 8) keeps the `finalReview` label. A label the forge refuses after a record stood is a warning; the step stays done. A target with no `translation` label keeps its `finalReview` label through the chain, as before the label existed. The check label (`forge.checkLabel`, which asks the owner to look) follows the questions put to the owner (D-138): after each `answerComments` and `styleCheck` record the runner sets it from the PR's open questions, the ones the round left open (the answer's record states them; a style check answers none, so they stay): any, the label goes on, and back on if the owner took it off; none, it comes off, except at the first such record of a PR with none kept (one from before the questions were recorded), which only puts it on. Between two such records it stays as a person left it. It comes off every PR a person's move past the final review status takes, to In translation or done (D-128): the owner's check is done, and the open questions with it. A move into the final review keeps it, from In progress, from the expert's review or by the expert's Approve, since the owner's check only begins there; so do moves between In progress and the expert's review, and every move back. Only the runner adds it or takes it off: no role may. **The ready label** (`forge.readyLabel`, when the host names one) is the pipeline's recommendation to merge: the runner puts it on a PR when the PR is marked ready for merge and takes it off when the PR leaves ready for merge (sent back to the owner's queue, taken into the chain again, a question on it, the card moved back), and makes it on a repository that lacks it. The owner's own merge label is never touched. **The translated label** (`forge.translatedLabel`, when the host names one) says whether the PR's translations match its UA, a fact of its own next to the stage label and the ready label: the runner puts it on when the chain or a re-sync is done for the PR's head (the `readyForMerge` and `resync` records keep that head, `translated`), and takes it off as soon as it sees UA changed in words since that head, at any stage (an `untranslated` step, no model; not an id-only change, not the runner's own id commits, not an image). So a PR the owner moves back after the translation with UA unchanged keeps it while the ready label comes off, and the owner's final edit or a comment's answer that changed UA takes it off, so the PR shows that it needs translating again. A card's move and an EN-only commit leave it, and a merged or closed PR is never touched; a merge of the base into the branch that brings UA changes to a page the PR changes takes it off, as it sends a ready PR back. A PR of a pipeline ticket merged without it is named in the report and the progress file, with its link: its translations may be behind its base (the close records it). **After a person's edit of EN on a translated PR** the runner checks the heading ids of the EN pages the hand commit changed against UA (`idSync`, no model, `scripts/doc-align`; heading-anchors.md, rules 2, 4, 6 and 7): a heading new in the PR gives its UA `{/* #id */}` the EN heading's anchor, and so does every further locale's page, with every link to the old id in the content roots rewritten; a heading already on the base (its id there as a UA comment or as an EN anchor) keeps its published id, which the EN heading then gets explicitly (`\{#old-id}`). A page's renames are made together, so a chain of them is whole; one that can't be made leaves the page as it is, with a line comment saying why, and a ready PR waits for a later commit that fixes it. One pipeline commit, pushed, and a line comment under the heading (`forge.idComments`); under a kept id, how to ask for the rename instead, and the owner's reply in that thread (`forge.idComments.rename`) runs the first branch for it, with no session. Only ids change, so the PR stays where it is and both labels stay.

**After ready for merge**, a UA change, whoever made it (the owner's final edit by hand or by a suggestion, an answer to a comment), translates nothing by itself: the PR goes back to the owner's queue (`move` to `finalReview`, no model step) and the card stays in, or goes back to, the final review status. More rounds there (comments, hand edits) translate nothing either; a UA hand edit gets its style check (below). The owner's move to In translation then runs `resync` once, over the whole range from the head last marked ready to the current head (both in the brief), then `visualPack` again if the range changed an image, then `readyForMerge` for the new head; no chain stage runs again. An id-only change keeps the PR ready, and so does a commit of the pipeline that left UA alone; a hand commit that left UA alone gets `readyForMerge` for its head (the pack first if it changed an image), with no re-sync.

**Keeping a PR up to date with its base** (D-113, D-127; `forge.keepFresh` in the shared file, off by default). The owner merges a branch that already holds what was merged before it. From ready for merge on only, and never at In translation, in the owner's queue or before (the owner edits the branch there): at the end of the chain the PR is marked ready first, then for a ready PR whenever its base moves the runner, not a model, merges `origin/<base>` into the branch in the PR's worktree (`baseMerge`: a merge, never a rebase or a force-push, since the owner reads the branch) and pushes it as a session would. It comes after every other row: a UA hand edit sends the PR back first, new comments are answered first, and no merge follows another while CI on the last one still runs. The merge commit is the pipeline's own: never a hand edit or a style check, and never a UA change of the PR's unless it changed a UA block of the PR's own pages (a block the base brought came translated with the base, and nothing is re-synced for it). The push takes the ready label off and starts CI; the PR is marked ready for merge, at any stage, only once CI passed on its head: the checks of that very commit, never another's (a check running, or none reported yet within 10 minutes of the head, waits). A failed check is a mismatch that names it, in the report: the PR stays out of ready for merge until a later head passes. CI that never reports, or stays pending for over an hour, opens a gate to the owner. A conflicting merge is aborted, nothing is pushed, and the PR goes back to work: `baseFix`, a session of the writer (the translator when no conflicting file is under a UA root: EN, a further locale, or any other file, a config or a code file included), with the conflicting files in the brief. A conflict no edit resolves (a file one side deleted or renamed and the other changed) goes to the owner, and so does a PR's second conflict with its base. The runner starts the merge again for it; the session resolves the files and adds them, and only the runner commits the merge and pushes it. A resolution that changed a UA block of the PR's own then goes back to the owner's queue (D-112), and the owner's move to In translation re-syncs it, not the chain. Each full check of the watcher looks at every ready PR, so a moved base or a finished CI is seen within `schedule.watchMinutes`; `status` shows how far behind each open PR is (`prs[].behind`), and the report lists the day's merges and conflicts. Out: rebasing, squashing, who merges and the merge method.

**The pipeline's comments** (D-138). It posts from the owner's accounts, so every comment it posts on the tracker and the forge (triage, plan, questions, the ready comment, summaries, replies, line comments; not a PR's description or a commit) starts with the host's `commentHeader` line, then an empty line, then the message; the tracker and forge modules put it there, and with none set there is no header. Everything that finds a pipeline comment by its first words reads it without the header, so a comment from before it counts the same (`--unless-header`, the triage marker), and a PR comment that starts with the header is never read as the owner's. The texts follow the host's templates, laid out for reading (the shared role rules, "The comments you post"): sections under the template's headings, an empty one left out; each edit with its number in bold, the page, section and block, and «було» and «стало» on their own lines in a quote, a long block folded on the forge; questions numbered with the place, why it is a question and the proposal, a question on a PR naming the item it asks about instead of a number of its own; on the tracker only bold, lists and code. The layout changes no number and no wording, so the reply by number reads as before.

**The list of edits and the reply by number.** Every list of edits the owner reads on a PR is numbered: the UA review's rewrites in the description (from 1, at `pr`), the answer pass's page edits after them, the EN review's rewrites added to it, and the summary comment of each `answerComments`. An item gives the page and the block, and the exact «було» and «стало» (never a paraphrase), the EN pair too where both changed. One PR numbers on: a later list starts after the last number (the brief gives it), and a number once posted keeps its item. The ledger keeps the items (`prs[].edits`). The owner answers in one PR comment, free form, the number first: «N — поверни» puts back that item's exact «було» (and its EN «було» when it has one); «N — "текст"» puts the text in verbatim; «N — <опис>» rewrites by the description; an item not named stays. The rule reads the reply against the lists with no model (`scripts/ticket-state/README.md`, "The list of edits and the reply by number") and the brief spells out each item; a number the PR doesn't have, one two lists share, one with nothing to do, items named together, a comment that reads as the owner's own numbered list, and a restore of a block a later item changed again are asked back, never guessed. A word of assent («ок», «залиш») changes nothing, while «не треба» is asked back; a line of the reply that belongs to no item is passed on as the owner's word to the whole PR. A numbered comment on a PR with no list yet is an ordinary instruction. The writer's summary lists what it did, numbered on the same way, so the owner can answer it again. The owner writes UA only: EN and the further locales follow by the re-sync after the owner's move. A `suggestion` block the owner left in a review comment is the same as «N — "текст"» on its lines: put in as written, with only the words outside it as an instruction; one the owner committed is a hand edit, kept.

**The trigger word** (D-142, `forge.triggerWords` in the shared file; none set: everything above holds as it is). On the forge, an owner's comment is for the pipeline only when it starts with one of the words and a colon (any case, a space before the colon and leading space allowed), in the pipeline's own threads too; the word is cut off before the brief, the reply by number and the suggestion reader see the text. A submitted review whose text starts with it covers its line comments. An owner's comment without it is a note for people and starts nothing. The PR's experts (the targets' `reviewers` and the reviewers requested on the PR) are answered as before, with no word, in their own comments and reviews and in the threads an expert opened (a thread whose first comment was deleted counts as no one's). A reply in anyone else's thread, the pipeline's or the owner's, is for the pipeline only when it is the owner's with the word: anyone else's there, an expert the owner tagged included (decision 3: the owner may tag the expert to reread, and hands the answer on with the word under it), starts nothing. Such a reply and anyone else's comment are listed in the progress file's «Waiting for you» with a link, for the owner to hand on (a comment with the word that says so) or leave; one goes off the list only once it was handed on: a session took it with the owner's worded comment that points at it (a reply under it «зроби, як каже SME», a quote, a link, its author named) and recorded its id. A reply that only comes after it («поверни» under the pipeline's line comment) hands nothing on. One the owner leaves stays listed until the PR is merged or closed. The brief lists the comments the step takes, word cut off, each in a thread with the thread's first comment and its last earlier ones, and the session acts on no other, except a comment the owner's worded comment hands on. The tracker is unchanged: the card's move is the signal.

**Reactions as status** (TASK-095, `forge.reactions` and `tracker.reactions` in the shared file; off: no reaction). The runner, never a role, marks the comments a session takes with the pipeline's own reaction: 👀 when it picks one up (a new comment, or a new version of an edited one), also when the owner took 👀 off, with its earlier result taken off; then 🚀 (✅ on the card) when the step applied it, 😕 (❓) when the session asked back about it or couldn't do it, and on each comment of a failed step. On the PR these are the comments of `take` (with the trigger words: the owner's worded ones and the experts'), a review's text included; on the card, the answers after the open question that the `answers` step reads. Which result comes from the record alone: the session's own `result` in each `handled` entry (`applied` or `asked`), and for an entry with none, the rest of the record (the script README, "Reactions as status"). The state stays in the ledger: a reaction the owner takes off with no edit starts nothing, and the next pickup sets the marks again. A reaction that fails is a warning, never a failed step.

**Review rounds** (D-142, `forge.reviewRounds` in the shared file, with the description's words in the team's language; absent: the summary comments above). A round is two commits and one review. `answerComments`: commit 1 the edits the comments asked for, commit 2 the style check's fixes over those blocks (none, no commit 2); `styleCheck`: one commit of fixes; `enReview`: the EN style commit after the translation commit, both named in its own review over the EN lines; the first version (`pr`) commits as before and gets no line comment per style fix, only the places. The round's review (`forge review-on-lines`) replaces the summary comment: its text names each commit and says how many line comments and questions, with the mechanical fixes (the words stay the same) folded with their lines; a line comment goes only where the owner has something to decide: an instruction interpreted, not carried out or carried out with more than asked, a substantive style fix (only the changed fragment, the rule and why), a fix not applied, a deleted block (one line with its line count and a diff link, never its text), a block nobody asked for. A comment on a line outside the diff goes into the review's text. The items stay in the ledger with their numbers and the line comment each was posted with (`commentId`); the posted texts show no number, and the reply by number keeps working on the lists already posted. A reply with the word in an item's thread is that item's reply by number, the number taken from the thread: the writer does it, answers in the thread with the commit, and never settles the thread (the owner does, or leaves it: a thread left alone is a change accepted, and nothing waits for it, ready for merge included). A restore names the item it undoes, whose rule is then recorded as rejected. The owner's reply with the word in a place's thread answers the place. After each step the runner, with no model (`scripts/ticket-state/README.md`, "Review rounds"): rewrites the description's open questions (by reader, the answered ones folded under «resolved» with their links), places and rounds between the template's markers, leaving everything else and a section a person edited since (a description with none of the markers, a PR opened before the switch, gets the three sections at its end at the PR's first round); settles the pipeline's own place thread once a place is confirmed or its block deleted (the writer's one-line reply says why); and removes the summary comments a new review superseded after the PR's rounds began (a summary from before the first round, with its numbered list and questions, stays). Only the pipeline's own: a person's comment or thread is never edited, settled or removed, and a submitted review can't be removed. A pipeline comment the owner deleted breaks nothing: a 404 is a warning, and nothing is posted again.

**The style check of a person's edits.** A person's edit says what they want, however it is written, and the style guide passes over it before the text is final (the writer role, "The style check"). After `answerComments` applies the comments, the owner's and a reviewer's alike, it reviews the UA blocks they changed. Hand commits get the same check as a step of their own, `styleCheck`: a commit on the branch the pipeline didn't make, after the head last marked ready for merge, that changed a UA page of the PR's own (not an id-only change, not a page a merge of the base brought), is read once, whatever the head, while the PR is in the owner's queue (a ready PR goes back there first; at an earlier stage the commits wait for it), after the new comments. A person's move is approval: hand commits the card was moved on to In translation with are recorded as seen with no session and no move back, with the note "style check skipped: the card was moved on" in the run log and the progress file. A hand commit waits 10 minutes before its check, so the owner's usual push and then move finds no check running, and the move approves the commit. A check that was already running when the owner moved the card keeps its fixes: the chain goes on with them, the record notes that they landed after the move, and the owner finds them on the summary's numbered list, to undo by number. `styleCheck.since` in the settings (an ISO date-time) makes every hand commit written before it (its author date) count as seen: the check is for the PRs to come (D-080). A hand edit that puts back the «було» of an earlier style fix is the owner undoing it: that block is left out, so no fix comes back. The check records the shas it read (`styleChecked`), so a second check at the same head, or after its own fix, runs no review. Only the changed blocks are reviewed, never a block a reply by number restored or kept, never EN. A fix keeps the edit's intent and goes on the PR's numbered list, its «було» the person's text, so «N — поверни» gives back their wording. A fix that would change what the edit meant is not applied: the text stays as written, and the fix is a note after the list, unnumbered. A plain comment that quotes a sentence of the page with words removed or changed is read as the reviewer's replacement for that sentence. The reason a comment or a commit message gives for an edit is recorded with it, for the learning from the owner's edits.

**Learning from the owner's edits** (D-045, D-134; `learning` in the shared file; none: nothing of this runs). The model proposes, the scripts dispose. (1) After each run a script, no model, appends the owner's edits to a log in the state folder, block by block, «before» → «after» with the page, the PR and the owner's words: an applied review comment of the owner's (`prs[].edits`, its `by`), a style fix the owner undid, a commit of the owner's (`learning.authors`) at any stage, and the final edit after the first ready for merge, a merged PR's commits read through its merge commit; `ticket-state learn collect --since` backfills the PRs merged before the switch, and adds nothing twice. No learning session runs inside a check: the full check hands a learning pass on to a process of its own (`watcher.mjs --learn`), and every learner session waits for today's morning run, for no ticket run going (D-131: the tickets first) and for the start hours (D-109). (2) Once a week, from the week after the one it was switched on in, at the first pass from Monday's morning run on with that gate open and the allowance left, one session of the `learner` role (`${CLAUDE_PLUGIN_ROOT}/context/ticket-roles/learner.md`) groups the edits into patterns, drops fact fixes, states the reason (D-081), checks each against the style guide and the rules, and gives it a kind: `продукт`, `загальне`, `виняток із загального`. Its only output is a result file; the runner keeps only a pattern with two examples or more on two PRs or more, of edits no earlier proposal used, and never a rule the owner rejected. (3) In each host repo where a kept pattern was seen, the runner opens one PR that adds the rules to the kit's `product-rules.md` (a general one too, so it works at once), its description in the host's PR structure, opened by the trend of the owner's edits per PR, then the numbered rules with their reason and «було → стало» examples; a notification and a line in the progress file announce it. (4) The owner answers by number on that PR, with the trigger word or without it (yes, no, the owner's text, a kind; a rewording by description takes one session); only the owner's comments are obeyed, and one that reads as no reply is listed in the progress file; the runner commits the change and replies, and keeps the new states only once the push went through. The merge is the yes; a rule said no to, or left in a PR closed unmerged, is rejected and never proposed again. (5) A merged general rule becomes a toolkit PR the runner opens, the owner's alone, in English with no product, company, host or person name, the rule added to an existing rule file by subject in that file's language, numbering, heading form, parts and cross-references, the lint run before the push; once the toolkit's own file holds it, the next weekly host PR removes the host's copy. (6) An exception stays in the host's kit; a toolkit rule found wrong gets a toolkit PR that corrects it, a distilled corpus only with its primary source, and never with a taste rule. Nothing reaches a kit or the toolkit without the owner's merge. `scripts/ticket-state/README.md`, "Learning from the owner's edits", has the details.

**The ticket worktree.** The runner, not a role, makes the worktree a session works in: one per PR branch, beside the target's clone, detached at the branch's head, with the clone's `node_modules` (and any other name in `targets[].links`, such as `.env`) linked and excluded. The brief names it and the push command. No role makes or removes a worktree, links a file, or installs packages; a role changes a repo only as `git -C <worktree>` for the worktree the brief names (a plain read also runs after a `cd` to it), the only push allowed is the brief's, and every plain add, commit, push, fetch or branch change, every interpreter string or script of the session's own, and every write that would run code later is denied, whatever the owner's or the hub's settings allow. A worktree with unsaved work is kept after the merge and reported. A step with no worktree (the start, the plan, the answers, the video import) works in a read checkout of each target clone its tickets name: a detached worktree of the clone at `origin/<base>` as the runner fetched it, beside the ticket worktrees and outside every repo, named in the brief. The clone's working tree may be on another branch, at a detached HEAD or behind its origin, so a skill is never given the clone's path. The read checkout's pages are read-only; its `.sources/` folders, tracked or not, are the clone's (left out of the read checkout and linked in by the runner), so a skill reads and writes its evidence there as usual, and a `.sources/` folder made there for the first time is moved into the clone when the session ends. The plan's Playwright spec stays in the clone and runs from there. When the runner can't make a read checkout, the brief says so and names the clone as it stands, with how to read pages from `origin/<base>` (`git -C <clone> show`) when it is off its base or behind. Nothing is held for either. The runner never checks out, pulls or resets a clone.

**Commits made on the forge.** `status` fetches the branch of each open PR whose forge head the target clone doesn't have (with its base, into the remote-tracking refs only, at most once per check), so a suggestion accepted in the PR, an upload or an edit in the browser is read as a hand commit like one pushed from the clone, by the rule's rows 8 to 12. A page or an image a merge of the base brought in is not the PR's change, so the forge's "Update branch" keeps a ready PR ready. A fetch that fails leaves the head noted as not fetched.

## The ledger

`<state>/tickets/<key>.json`, in the host's git-ignored state folder (`state` in the settings, default `<Toolkit state root>/ticket-flow/`). Written only by `record`, `handover` and `import`, to a temp file and renamed. `key` is the card's team number, else its short link.

**The import.** `ticket-state import` turns a host's Markdown ledgers from before the JSON ones into JSON ledgers. A closed ticket's Markdown is removed only once the JSON is checked to rebuild it byte for byte; the morning run repeats that for tickets that closed since, recording the close of one still in the owner's hands and untouched since the import. An open ticket's Markdown stays. The details are in `scripts/ticket-state/README.md`, "The import".

## When a record is accepted

`record` writes a stage `done` only when the world supports it: the card in the status the stage leaves it in, each PR on the forge with its branch and stage label, the head the stage names being the branch's head, every chain stage done before `readyForMerge`, every PR merged before `close`; every place's claim and why in the language of its page, whatever `checks` say; and, with the host's `checks` on (D-044, D-052), every question naming the sources it checked and asked in a comment the card has, no marker a PR's UA pages gained at its `pr` record (the gate before any review: under D-114 every PR then goes to the owner, and a person's move to the review is never refused), every place naming its page, claim, source and why it isn't confirmed, listed in the description. Otherwise nothing is written and the reason is named (`scripts/ticket-state/README.md`, "`record`: what each stage checks"). A session fixes the cause, never the record. `running` and `failed` (with a note) are always accepted.

## Locks

One lock per group, `<state>/locks/<group>/owner.json`, taken with `mkdir` so two takers can't both win: a `kind` (`schedule` or `manual`), the stage, and a lease (`limits.lockLeaseMinutes`) that every record renews. A lock past its lease is stale; only the runner moves one aside (`<state>/locks/stale/`) and records its group's running stages failed. A manual session that finds a scheduled run's lock stops there.

## Limits and priority

Only tickets a scheduled run started, in `mode pipeline`, count. A scheduled run starts a ready group only if: tickets in progress + the group's size ≤ `limits.inProgress` (a group larger than that only when nothing is in progress); tickets waiting < `limits.waiting`; and the group's estimated cost plus what the tickets in work still need fits what is left of the day's allowance (`limits.dailyPercent` of the week per day of the week window, from `/usage`). Estimates are per size, measured on finished tickets, else `limits.estimates`; with none yet, one ticket at a time. With `limits.open` set, the open tickets + the group's size ≤ it (a larger group only when none is open). Open: a scheduled run started it, and it is from planning to the final review, In translation and ready for merge included; a paused ticket, one outside the flow, a merged or a closed one is not open. The reason a group didn't start names the tickets that hold the slots, and so does the report. A ready ticket waits for another only for an objective reason, a related ticket in work or starting now (a start handed to a process of its own counts until its run records it), where related means overlap: triage named the other in one repo (`#1221` and `1221` are one ticket), the card's text names its number, or the two have a page in common (its repo and path, without the block). Only `together`, the triage's judgement, joins tickets into a group, in either direction, within one repo. Priority is the card's label (`tracker.priority`): high first, then medium (no label), then low, the oldest card first within a level. The start order is `limits.startOrder`: `priority` (by priority, then the oldest; a group held back by the limits holds back every lower level, and within a level a younger group that fits may start) or `easiest` (the smallest triage size first, a size not known yet last; then fewer repos; then fewer pages; then priority and age; a group held back by the limits holds back every group after it, equally easy ones too). A group whose start failed waits as a failed step does, and holds no slot and no other group meanwhile; a run doesn't count a group it already tried, so it goes on to the next. Finishing comes before starting, and a higher priority first within each kind of finishing.

## Cleanup after the merge

The close step of a ticket whose PRs are all merged first removes its worktrees with `git worktree remove --force` and prunes the clone's list, then moves the work files in `files` into the Trash (`cleanup.mode`), except a path git tracks, a path outside the host repo and the state root, and a path `cleanup.keep` names (default `**/sme-interview.md`, `**/app-notes.md`). A path the ledger didn't record is never touched. While a PR is open or was closed unmerged, nothing is removed. A recorded folder that holds a worktree goes with git; one that is a repository of its own is kept whole; a `.git` entry is never moved alone. A worktree whose head is on no remote-tracking ref and is no head the forge had (nor behind one) is kept: what a session reported as its commits doesn't count, since its push may have failed. The close record keeps what went and the space freed.

## The watcher

`watcher.mjs` runs its full check every `schedule.watchMinutes`, started by a LaunchAgent (`launchd.mjs install`), with no model call of its own. It reads what changed since its cursor: the boards' actions, the PRs that changed and the PR events. It maps each event to a ticket through the ledgers, and asks `status` what each changed ticket does next. The runner decides, guarded and counted like a scheduled run, and hands each group with a next step to a run of its own in a process of its own, each once, and starts no ready group; the check never waits for those runs, so one ticket's long chain holds up no other ticket, nor the next check. A group over `limits.parallel`, or one a run of another process holds, waits for a later check. A check that finds nothing, with no start pass due, ends there: no status, no runner, no `claude`.

- **The cursor:** a window from 10 minutes before the last check, seen ids dropped. The cursor moves only after every event was handed on. A source that fails keeps its place until 24 hours after its last good read, then the gap is reported. A source that has failed for an hour while the Mac was awake (a token gone, say) is a failed part of the check, one per client, told each day from `schedule.morning` on; its 24-hour gap is told too. A failure right after a wake stays quiet.
- **The forge check:** the LaunchAgent ticks every `schedule.forgeSeconds` (60). Each tick runs the forge check, and, every `schedule.watchMinutes`, starts the full check as a process of its own unless one still runs. The forge check reads only the PRs that changed (cursors of its own), their tickets through the ledgers and those PRs' comments, so the owner's comments are picked up within a minute. No tracker read of its own, no morning run, no start pass, no host job. It hands a ticket with comments to answer to a run in a process of its own and never waits for a session, so a ticket's long chain doesn't hold up another ticket's comments. Its lock and its memory (`watch/forge.json`) are its own; the group locks decide who runs a ticket, and each check's record of its live runs (`watch/forge.json`, `watch/feed.json`) holds their tickets, for both checks, until the run took its lock. `limits.parallel` counts the runs of every process (the live group locks and both checks' runs that hold none yet), for both checks and the runner alike; a run always gets one slot. A step that waited in a run's pool is read again once its group's lock is taken, and skipped when another run did it meanwhile.
- **The start rule for comments**, held at both checks' hand-on: a submitted review (text of its own, a verdict, or more than one line comment) starts its session at once; single comments, the owner's or a reviewer's, once the newest is `schedule.commentQuietMinutes` (2) old with no newer one. A comment that arrives while its ticket's session runs waits for the next session. A review not yet submitted is never read.
- **The morning run:** once a day, at the first check after `schedule.morning` whose board reads. Its triage runs in the check; its finishing groups and its starts are handed on as above, each to a process of its own, and its date is recorded once that is done. A failed step's or failed start's one more try that it couldn't hand on, or whose run came back without using it (`mode off`, a run slot taken first), is kept for that day: the next check, or the next start pass for a start, gives it.
- **The start pass:** after the day's morning run, inside `limits.startHours` (default `10-22`, local time), when something changed that could let a start or a triage happen (a slot freed, a group newly ready, an intake card newly due, a new day), the runner triages the newly due intake cards and decides the starts as a scheduled run does: the same limits, allowance and start order, from one calculation, each start handed to a process of its own, its starts scheduled ones, counted and reported like the morning run's. A start handed on counts as starting now in every start decision until its run records it. A pass that started nothing runs again only after another change (or, when it had no `/usage` reading, after 30 minutes; when its start waited for a run slot, once a slot frees), and none runs when the counts leave no room (no `/usage` read then). A card whose triage failed in a pass waits for the next morning run or a person; a pass that failed before its first step is tried again after 30 minutes. Outside the hours there is no start and no triage: a change waits for the first check inside them or the morning run. Following the open tickets is the same at any hour. Each start gets a notification, not urgent.
- **Host jobs (`hostJobs`):** "when list X gets new cards and stays quiet for N hours, run job Y", or "every N minutes"; Y is a host script or a skill. A change in the list restarts the wait. A skill job is guarded like a scheduled step. A job that failed at each try for an hour is disarmed; if reads were failing with it, it re-arms once they read again, and `ticket-state set retry job <name>` re-arms it by hand. Its alert, before `schedule.morning`, waits for the morning.

`mode` (`off`, `observe`, `on`) and the limits are in the owner's local file. `ticket-state set` edits one key of it, the way a request in plain words is carried out. No `claude` the flow starts gets an API key or an auth token, so the plan pays. A macOS notification gives the morning counts, and names each ticket the start pass started. It is urgent only for a limit reached, a step that failed twice or hit its daily session cap, a host job that failed at each try for an hour while the Mac was awake (a shorter failure is tried again at the next check, quietly), or a part of a check that failed (the rest of the check goes on). The sign-in token goes to the `claude` processes only, never to a host script, `git` or `gh`.

## The report

`<state>/reports/<date>.md`, written by the runner (or `ticket-state report`) with no model call and sent nowhere: what waits for the owner, PRs in the expert's review whose experts have been quiet for `schedule.expertQuietDays` working days (with the text to send them, when `forge.reviewComment` is set), PRs with places, PRs with the check label, videos waiting for transcripts, ready for merge, with `forge.keepFresh` the day's merges of the base, their conflicts and the PRs still behind their base, PRs merged without the translated label, cards left in the host jobs' watched lists, what finished and started and why the rest didn't, mismatches and tickets in the owner's hands, the work files removed, the watcher (its last check, failing sources, host jobs waiting), failures and guard stops, the day's cost, and once a week the proposed changes to the roles. `/ticket-report [date]` reads it on demand.

## The progress file

`<state>/watch/progress.md`, rewritten with no model after each step and at the end of each full watcher check: a checklist of the runs and of each ticket's phases (done, running, not yet, failed, stale, and the gates with who they wait for), with the owner's own steps file at the end if the local settings name one (`progress.stepsFile`). The ledgers are its source; a failed write never fails a run. The watcher also sends one "your turn" notification for each gate that waits for the owner. The owner reads the file in an editor's Markdown preview (`scripts/ticket-state/README.md`, "The live progress file").
